# AGENTS.md

Orientation for coding agents working in this repository. Read this first, then the one document below that covers what you are about to change.

## What FitMap is

FitMap is a free, community-funded platform for tracking outdoor activities and seeing the accumulated shape of where you have been. It aggregates activity history the user already has — from watches, from cloud services, from files — and turns it into maps and exploration stats worth looking at. Three things it deliberately is **not**: it does not record workouts (no start button, no live GPS — it begins where the watch's recording ends), it has no social graph yet (no feed, follows, kudos, segments or leaderboards; see `docs/VISION.md` §5.5–§5.6 for why that ordering is deliberate rather than merely cautious), and it is not a health or fitness advisor (no HR zones, no training load, no recovery/readiness, no sleep tracking — pace and heart rate are shown per activity as route context, not analysed as a coaching product). It is funded by recurring community donations with public accounting, so there is no subscription tier to design around and no paywalled feature to hide behind.

## Current status

### Backend endpoints & ingest

Phase 0 / Phase 1 (`docs/VISION.md` §5.1–§5.2) is essentially complete — `docs/SPEC.md` is the authority on what's built, feature by feature (FR-1 through FR-8); this section maps that behavior to where it lives in code, not restates what it does.

`cmd/fitmap serve` (`internal/httpapi`) implements upload (FR-3.1–FR-3.3 — `handleUpload` branches to `handleZipUpload`/`handleTakeoutUpload` internally, all one route, IMPLEMENTATION.md §4.1 step 1), the upload-history endpoint (FR-3.4, `GET /v1/uploads`, joined against `activities` so a finished row carries its own date and distance without a second round trip), the three activity-history endpoints in `activities.go` (FR-5.1/FR-6 — each row's `bbox` is derived from `trajectory` on the fly, not a stored column, per §3.3's GiST-index reasoning; filter parsing is shared between these and the tracks-tile query below, so "absent means no restriction" can't drift between them), and `graph-stats` (FR-7.2). `cmd/fitmap work` dequeues `ingest` jobs and runs §4.1 steps 2, 3, 5, 6 of `IMPLEMENTATION.md`: parse, privacy-trim, simplify, persist to `activities`/`activity_streams`. `cmd/fitmap migrate` applies the schema.

`serve` also runs `GET /tiles/v1/tracks/{z}/{x}/{y}.mvt` — IMPLEMENTATION.md §4.3's live PostGIS→MVT query, unprecomputed by design (it has to answer filters that can't be baked into a raster ahead of time). `apps/web/src/map/tracks.ts` renders it, refreshed after a successful upload.

### Map: fog, heatmap & tracks

Fog of War (FR-4.2) and Heatmap (FR-4.3) are built (§4.1 steps 4/7, §4.2), rasterized with `github.com/fogleman/gg`, and **respect the currently-selected date range and the eye-icon hidden set** (§4.2.3) — reported live as two bugs ("an activity outside the blue belt still counts," "a hidden activity still counts"), both from the same root cause: fog/heatmap were a precomputed whole-history aggregate with no per-request filtering capability at all, unlike tracks (§4.3), which are live per request from the start. Fixed by rendering a **crisp mask per activity per z14 tile** at ingest (`internal/fog.RenderActivityMasks`, called from `ingest.Process` right after persisting — no raw-payload re-fetch for the activity that triggered it, unlike the old design) into `activity_tile_masks` (`services/server/migrations/0005_activity_tile_masks.sql`), rather than one aggregate raster per user. The unfiltered case (`fog_tiles`, still the same table/shape) still reads straight from a precomputed cache — zero new cost there — but now that cache is built by *compositing* already-rendered per-activity masks (`renderAndStoreTile`), not by re-parsing raw payloads. A filtered request (`?from=&to=&exclude=id1,id2` — `exclude` is new, for the eye-icon/TYPE/DISTANCE hidden set tracks already answers client-side but a raster tile has no per-feature identity for) composites on the fly instead (`internal/fog/filtered.go`'s `RenderFilteredTile`), bounded to one range query plus in-memory bottom-up downsampling — never a `4^(zoom depth)` blowup at low zoom, and never a raw-payload re-parse. See §4.2.3 for the full account, including a real gotcha already hit once: anything joining `jobs`↔`activities` by external id has to match the job's own `source`, not assume `'upload'` — the exact same bug class as this session's Takeout-import `uploadsListQuery` fix, caught the same way (opening the actual UI, not a unit test). Heatmap mode (§4.2.2) shares this entire redesign — one crisp mask feeds both rasters, fog maxing then blurring once, heatmap blurring each mask then summing. `apps/web`'s `fog.ts` and `heatmap.ts` composite the two rasters (mutually exclusive — only one is ever visible), and `mapMode.ts` owns the three-way Normal/Fog/Heatmap toggle specifically because both Fog and Heatmap also hide the track layer (§4.2.2 — the raster already encodes where, and the drawn lines on top read as visual noise rather than adding information), which neither raster module alone could express.

`useMapInstance.ts` also wires MapLibre's built-in `GeolocateControl` next to the zoom buttons (top-right) — a one-shot "find me" via the browser's geolocation API, `trackUserLocation: false` deliberately, since continuously following the device as it moves would read as live GPS tracking, which `VISION.md` §1.1 draws a hard line against. Nothing about a click is persisted or sent to the backend; it only moves the camera. What's still not built: a dark-theme fog veil variant, raw-payload re-parse caching, cross-source dedup (§4.6 — only Path 3 exists), Paths 1 and 2, explorer tiles, and export rendering.

All three upload formats now extract a real `activity_type` (GPX's `<type>`, FIT's `session` message via `internal/parse/fit_sport.go`, TCX already did) — verified live through the actual upload endpoint for GPX and FIT, not just unit-tested.

**Per-activity pace/heart-rate (FR-9, §4.5) is built, alongside distance trends — three ingest gaps closed to get there.** Scoping §4.5 against the real ingest code found `activity_streams` was write-only — populated at ingest, never read anywhere — and that `parse/gpx.go` silently dropped HR even when a GPX file carried it (only FIT/TCX populated it), `moving_seconds` was declared in §3.3 but never computed, and no per-point cumulative distance existed anywhere. `gpx.go` now reads `gpxtpx:TrackPointExtension`'s `hr`, same flat `curField` mechanism the file already used for `ele`/`time`. `internal/ingest.computeMetrics` now also returns `movingS` (a ~1.8 km/h per-segment speed threshold excludes GPS jitter while stationary without excluding real slow walking) and a cumulative `distM` array, computed in the same point-walk that already existed for `distanceM` — no second pass. Both are wired into the existing INSERTs (`moving_seconds` was already a column, just unused; `dist_m` is a new `activity_streams` column, `migrations/0001_init.sql`). Existing activities keep both fields NULL — no backfill, that would mean re-parsing every raw payload — so anything reading `moving_seconds` falls back to `duration_seconds` per row rather than going silently short for older data. **Trends** (`GET /v1/activities/trends?bucket=week|month`, FR-9.1) needed no schema change of its own — it reuses §4.8's stat-query shape (`date_trunc` grouped by bucket instead of by day) — so it shipped alongside the ingest fixes rather than waiting on the rest. Best-effort curves and personal bests were built at one point and then cut, along with cadence/power capture — FitMap's scope is outdoor GPS tracking, not performance analysis or a sports-computer sensor product (`VISION.md` §1.1); their tables were dropped (`migrations/0012`, `0013`).

**The private per-user activity graph (FR-7, §4.8) sits behind real accounts now.** `apps/web/src/ui/ActivityGraph.tsx`/`YearGrid.tsx`, reached from the account menu's "Profile" item (`UserMenu.tsx`). It was originally built single-user, scoped to the one seeded placeholder account, on the reasoning that every backend query was already parameterized by a `user_id` so nothing would need redoing once real accounts landed — that bet paid off unchanged. `GET /v1/activities/graph-stats?year=` is the one endpoint FR-7.2 needed; the grid's cells (FR-7.1) reuse `GET /v1/activities/histogram`'s existing `?from=&to=` calendar-window mode, year-scoped, no new endpoint at all. `App.tsx` switches between the map and this page with plain `useState`, not a router — see IMPLEMENTATION.md §4.8 for the full account of what's built and why.

`apps/web/`'s multi-file upload panel (`src/ui/UploadPanel.tsx`, `src/api.ts`, FR-3.1–FR-3.4) is *not* `VISION.md` §8.2's no-signup demo (FR-2) — there's no client-side preview, every upload persists immediately, and it requires being signed in at all. Don't conflate the two when working on either.

**Colored zone segments (§4.3.1) show speed/heart-rate variation on whichever single activity is currently selected** — `apps/web/src/map/trackBands.ts`, a second GeoJSON layer drawn over the shared `tracks` MVT layer, since a vector-tile source can't carry the per-vertex color this needs. No schema change: `GET /v1/activities/track-metrics/{id}` (`internal/httpapi/activities.go`) reads `trajectory`'s own simplified vertices back out (`ST_DumpPoints`, same shape `simplifyXY` already produces) for position/time, and `activity_streams.elapsed_s`/`heartrate` for the rest — speed derived directly from consecutive vertices (`ingest.HaversineM`), heart rate matched to the nearest raw point by elapsed time (`sort.Search`, a nearest-neighbor search — simplified vertices don't land on exact raw timestamps the way they land on exact raw coordinates, unlike `matchSimplifiedTimes`). Heart rate is all-or-nothing per activity: any gap in coverage and the response omits it entirely, rather than understating effort with a partial curve. Route had to be `track-metrics/{id}`, not `{id}/track-metrics` — Go's `net/http` `ServeMux` rejected the latter outright at startup as ambiguous against `status/{external_id}` (confirmed live: the api container panics on boot), since neither pattern is more specific than the other when a wildcard sits in the same position one pattern has a literal. **Real, found-live limitation, not fixed here**: banding reads the already-*simplified* trajectory, so a geometrically straight or short segment can lose all its vertices to Douglas-Peucker regardless of how much its speed/HR actually changed there — confirmed directly, a synthetic slow-then-fast activity on a barely-winding path simplified down to 8 vertices, all from the fast segment. A properly winding real route kept 16 vertices spanning all its speeds correctly. **Re-matching against raw data alone would not fix this** — a band segment can only be as fine as the line's own vertices, so the geometry itself would also have to switch from `trajectory` to a re-parsed, full-resolution polyline, not just the colors matched to it. See IMPLEMENTATION.md §4.3.1 for the full account. The Pace/Heart rate toggle only renders when `heartrateAvailable` — a single-option toggle has nothing to switch between, so it's omitted rather than disabled; there's no separate color-key legend either (removed per user feedback, "hover is enough") — exact values are read from the §4.3.2 panel's hover tooltip instead. Row-click focus is also cleared by **clicking away from every track**, not just by focusing something else: a single plain `map.on('click', ...)` in `tracks.ts` (replacing what used to be a separate layer-scoped `onSelect` handler plus this one) hit-tests via `queryRenderedFeatures` and calls `onSelect(id)` if it found a track, `onClickAway` → `setFocusedActivityId(null)` otherwise — one query decides both outcomes, so they can't disagree with each other. That query is against a small **box** around the click (`CLICK_TOLERANCE_PX = 4`), not the bare pixel: `NORMAL_WIDTH` is only 2.5px, and an exact-pixel hit-test left almost no room for error — found live, switching focus from one activity to another by clicking the second one's thin line would often miss by a couple of pixels, and since a miss now means `onClickAway` (not nothing, like before this feature existed), the *first* activity's focus was wiped with no replacement selected. The box, not the exact click, is what fixed it.

**The same floating card also shows a pace/heart-rate + elevation profile now (§4.3.2)** — a straight-line companion to the colored zone segments above, answering "how did effort track against climb" rather than "where on the map was I fast/slow." Placement was a direct user call, not a default: "I like how it is now... this is why existing panel look good to me," so this extends the *same* floating card (its toggle already there) rather than a new docked panel or a bigger overlay — small and unlabeled (no axis ticks), a general overlook. This panel's hover tooltip is the only place exact band values show at all; there is no separate legend. `GET /v1/activities/track-metrics/{id}` (§4.3.1's own endpoint) gained `distance_m` (always present, cumulative, computed in the same loop that already calls `ingest.HaversineM` for speed) and `elevation_m` (gated `elevation_available`, same all-or-nothing pattern and same `nearestElapsedIndex` lookup `heartrate_available` already uses) — x-axis is real distance, not vertex index, since index-based spacing would distort exactly the pace-vs-elevation correlation this exists to show (vertex density follows Douglas-Peucker, not distance). `trackBands.ts`'s band-merging loop is now an exported `computeBandRuns`, shared by the map's curved `LineString` segments and this strip's distance-proportional `<div>` widths — one merge algorithm, two renderings. Hover (one handler, since the strip and elevation chart share the same x-axis) finds the nearest vertex and shows a small fixed tooltip, the same shape `Trends.tsx` already uses.

**High-resolution map export (§4.3.3, `VISION.md` §4.2) is client-side, not the headless worker-pool render §5.5 originally specified** — a deliberate, confirmed deviation, not an oversight; §5.5 itself now carries a "Revised" note explaining why and what would bring the original plan back into play. `apps/web/src/map/exportMap.ts`'s `exportMapImage` spins up a second, temporary, hidden `MapLibreMap` (off-screen via `position: fixed`, not `display: none` — the latter leaves no real layout box for WebGL to size a canvas against), constructed with `canvasContextAttributes: { preserveDrawingBuffer: true }` — nested there, not a top-level `MapOptions` field, in maplibre-gl 6.9.0 (confirmed against its own type declarations, not assumed) — since the *live* map deliberately never sets this, keeping that cost confined to the one instance that only exists while exporting. Once loaded, it gets the exact same `ensureFogLayer`/`ensureHeatmapLayer`/`ensureTrackLayer`/`setMapMode`/ `setHiddenTracks` calls `reattachOverlays` already makes on the live map, so Normal/Fog/ Heatmap and the current filters export faithfully with zero new rendering logic — then waits for `'idle'` plus the same 150 ms settle buffer the `isStyleLoaded()` gotcha below already established, captures via `canvas.toBlob`, and tears itself down. `ExportButton.tsx` is a `Header` prop (`exportControl`, same reasoning as `uploadControl`), not a floating map-corner control — every corner was already spoken for. **Found and fixed along the way**: `.track-metric-toggle` (colored zone segments) had been placed at the exact same `bottom-left` corner MapLibre's own `ScaleControl` already occupies — moved to stack above it rather than sharing coordinates.

### Accounts, demo sessions, password recovery & settings

**§4.9 Real accounts — simple email+password (FR-1, `internal/httpapi/auth.go`, `migrations/0006_sessions.sql`).** Every prior "no real auth" caveat in this file is now obsolete. Signup/login/logout/me live at `POST /v1/auth/signup|login|logout` and `GET /v1/auth/me`; every other route is wrapped in `requireAuth` and reads the caller via `userIDFromContext`, not `PlaceholderUserID` (which now exists only as the row `claimOrCreateUser` claims on the very first-ever signup — see its doc comment for why that in-place claim, not a migration, is what keeps pre-auth uploads attributed correctly). Deliberately simple, matching the user's own "go, simple email+password" instruction: bcrypt password hashes, opaque session-id-as-cookie-value (no separate token hash — the `sessions` table's own `gen_random_ uuid()` primary key *is* the cookie, judged sufficient for this app's current single-user threat model), 30-day sessions, no OAuth, no email verification. Password reset is built now (§4.11) — no email-sending infrastructure existed to build it on until then. Real gaps for a multi-user deployment, not oversights — revisit if that ever changes. Cookies need credentialed CORS (`corsAllowedOrigins` in `server.go` — an explicit allow-list, not `*`, which credentials forbid) and `credentials: 'include'` on every fetch, including MapLibre's own internal tile fetches (wired via `transformRequest` in `useMapInstance.ts`, since those bypass `api.ts` entirely). `apps/web/src/auth/` holds the frontend half: `AuthContext.tsx` (a small Context so `UserMenu`, three levels deep, doesn't need `user`/`signOut`/`requestUpgrade` prop-drilled) and `AuthGate.tsx` (the combined signin/signup screen `App.tsx` renders in place of the app until `getCurrentUser()` confirms a session — also reused full-page for §4.10's demo-upgrade path, see below). `api.ts`'s `AuthUser`/`DemoUser` is a real discriminated union (`SessionUser`), not a boolean flag — `DemoUser` is deliberately empty, which is what lets `'email' in user` narrow one from the other with no explicit tag.

**§4.10 The no-signup demo (FR-2, `VISION.md` §8.2) reuses §4.9's entire pipeline behind an ephemeral account — it is not a separate code path.** `POST /v1/auth/demo` creates a real `users` row (synthetic `demo-<uuid>@fitmap.invalid` email, never shown — `handleMe` strips it to `""`) marked via `demo_expires_at`, then a real session, so upload/ingest/fog/tiles/the activity graph all run completely unchanged for a demo visitor. This *is* rate-limited (`demoLimiter`, per-IP, 5/hour) — the one place §4.9's "no rate limiting" gap couldn't be left alone, since it's the one endpoint reachable with no credentials at all. `internal/worker/demo_purge.go` sweeps expired accounts on its own 5-minute ticker in `worker.Run`: `DELETE FROM users` cascades the DB side for free, but object storage has no foreign keys, so `raw/{userID}/`, `fog/{userID}/`, `heatmap/{userID}/` are swept first via a new `Store.RemoveByPrefix` — known gap, not swept: `activity-masks/{activityID}/`, namespaced by activity rather than user id, left orphaned as a low-cost simplification. **Signing up while a demo session is live claims that same account in place** (`claimDemoUser`, checked via `currentDemoUserID` before `handleSignup` falls back to `claimOrCreateUser`) rather than starting a second, empty one — reachable from AuthGate's own signup form directly, or from `UserMenu.tsx`'s "Demo session — save this", which just calls a new `requestUpgrade()` on `AuthContext` that has `App.tsx` swap in that exact same `AuthGate` (full-page, `onCancel` set so it shows "← Back" instead of "Try it now" and starts in signup mode) — not a second, separate form. Nothing about the uploaded data is at risk either way it's reached: it's rows in Postgres tied to the still-valid session cookie, never tied to whether `MapView` happens to be mounted.

**§4.11 Password recovery (FR-1.5/FR-1.6) closes the one gap §4.9 named from the start.** A new `internal/mail` package — a generic SMTP client (stdlib `net/smtp`, zero new go.mod dependencies), not a vendor's HTTP API, so it works with any SMTP-speaking service including a personal Gmail account via an app password. `SMTP_HOST` unset (the compose.yaml default) picks a `logSender` over a real one, so the whole flow — including reading the real reset link back out of `docker compose logs api` — works with no real credentials configured. `migrations/0008_password_resets.sql` mirrors `sessions` exactly (opaque token = the row's own `gen_random_uuid()` PK), 1-hour TTL. `POST /v1/auth/forgot-password` (rate-limited the same way `demoLimiter` already was — a second `fixedWindowLimiter` instance, `forgotPasswordLimiter` — since it's the other endpoint reachable with no credentials at all) always gives the same generic response regardless of whether the email matches a real account. `POST /v1/auth/ reset-password` sets the new password, retires every outstanding reset token *and* every existing session for that account (a reset is exactly the moment an already-compromised session should stop working), then starts one fresh one. Frontend reuses `AuthGate` again, the same resolution §4.10 already reached: two more internal screens (`'forgot'`/`'forgot-sent'`) alongside the existing signin/signup toggle, plus a `resetToken` prop that bypasses all of it for a "set a new password" screen when `App.tsx` finds `?reset_token=` in the URL (read once, stripped via `history.replaceState` in the same pass, checked ahead of every other branch including an already-live session).

**§4.12 Account settings (FR-1.7) — Avatar, Name, Country, Privacy Trim — is a new "Settings" item in the account menu (`UserMenu.tsx`), a separate screen from `ProfilePage.tsx`, not wired into `profile-v1.png`'s still-unbuilt "Edit profile" button.** `migrations/0001_init.sql`'s `users` table carries `display_name`/`country`/`avatar_key`/`avatar_content_type`/`avatar_updated_at`, alongside `privacy_trim_m` (default 200) with no UI until now. `auth.go`'s `loadAuthResponse(ctx, userID)` is now the *one* place that builds `authResponse`, and signup/login/demo-start/reset-password/`handleMe` all call it — a naive per-endpoint version would report a fresh signup's `privacy_trim_m` as the Go zero value `0` (looks like trimming was explicitly disabled) rather than the real column default `200`. New `internal/httpapi/account.go`: `PATCH /v1/account/settings` is a full replace of all three text/numeric fields at once (one Save button, not per-field auto-save); avatar gets its own three endpoints since it's a different content type — `POST /v1/account/avatar` sniffs the real content type via `http.DetectContentType` against an allowlist rather than trusting the client's claimed extension (that sniffed value is exactly what `GET .../avatar` serves it back as), stored at a **fixed** per-user key (`avatars/{userID}`, overwritten on re-upload — no orphaned blobs, unlike upload.go's content-hashed per-upload keys). `storage.Store` gained a plain `Remove(ctx, key)` for `DELETE .../avatar`, since the existing `RemoveByPrefix` is built for list-then-bulk-delete, overkill for one already-known key. `avatar_url` carries a `?v=<avatar_updated_at>` cache-busting param, making `GET .../avatar`'s week-long `Cache-Control` safe — a stale cached copy at the *old* URL is never requested again once the avatar actually changes.

**Country drives a real, app-wide unit system now — nothing did any km↔mi/m↔ft conversion before this.** New `units.ts`: `useUnitSystem()` is a hook (reads `useAuth().user.country` through a small `IMPERIAL_COUNTRIES` set — `US`/`LR`/`MM`), not a prop threaded down through `MapView → ActivitiesPanel → DistanceFilter`-style chains — every component that formats a distance calls it directly. `format.ts`'s formatters were rewritten to **own their own unit suffix** rather than have callers append a hardcoded `"km"`/`"m"`: `formatDistanceKm` → `formatDistance`, `formatTotalKm` → `formatTotalDistance`, `formatTotalElevation` → `formatElevation`, all now returning the full string ("12.3 km"/"7.6 mi"); `formatPace` converts the actual pace value for miles, not just its label. That exact hardcoded-suffix-at-the-call-site pattern is what let `useMapInstance.ts`'s own `ScaleControl` sit at a hardcoded, unexplained `unit: 'imperial'` — inconsistent with every km display elsewhere — for as long as it did; fixed alongside this, now synced live via MapLibre's own `ScaleControl.setUnit()` (a ref + a small effect keyed on `scaleUnit`, separate from the mount effect) whenever Country changes, no reload and no control rebuild needed. See `IMPLEMENTATION.md` §4.12 for the full account, including which files' call sites were updated.

**Profile and Settings each show the *other* one in their account menu, not just "back to map."** Reported live as the two menus looking inconsistent — both `ProfilePage.tsx` and `SettingsPage.tsx` originally called `<Header onBrandClick={onBack} />` bare, so neither could reach the other without detouring through the map first. `ProfilePage` now takes `onOpenSettings` and `SettingsPage` takes `onOpenProfile`, each forwarded straight to `Header`; `App.tsx` wires both from the `setView` it already had. Neither screen gets the prop that would link to itself, matching `Header.tsx`'s existing "nowhere further to open this to when it's already open" reasoning — now applied to both screens symmetrically instead of just one.

### Upload

**Upload is a dropdown panel now, not a hover popover (FR-3.1/FR-3.2) — `IMPLEMENTATION.md` §4.0.1 is fully built.** `UploadPanel.tsx` replaced the old single-file `UploadWidget.tsx` entirely. `.zip` archives extract server-side (`handleZipUpload`, one `ingest` job per contained file, under §5.1's zip-bomb bounds — declared-size check before decompressing, a bounded read to catch a lying declared size, a bad entry skipped rather than aborting the batch). The real resolution beyond what was decided: live in-flight status and the persistent upload history turned out to be the *same list*, not two separate surfaces — `GET /v1/uploads` (`services/server/internal/httpapi/ uploads.go`) shows a freshly enqueued job immediately (state `pending` → `"processing"`), so `useUploadHistory.ts` just polls that list's current page while anything's still processing, and the dropdown panel *is* the live view, no separate per-batch toast needed. Pagination there is real `LIMIT`/`OFFSET` (5 per page), the one place in the upload flow it's actually justified per §4.7's own reasoning for dropping it elsewhere. Progress bars during the network-transfer phase (before a job even exists to poll) come from `XMLHttpRequest` directly (`uploadFile` in `api.ts`) — the one place in this codebase that isn't `fetch`, since `fetch` has no cross-browser-reliable upload-progress event. **That same poll is also what MapView's `onUploaded` (Activities list, totals, histogram, tracks layer) needs to fire on, not just the initial "upload request resolved" moment** — reported live as a freshly uploaded track missing from the Activities list until a manual reload, since the request only confirms the job was *enqueued*, well before the worker has actually parsed it into a real `activities` row. `useUploadHistory` now takes an `onPoll` callback invoked after every poll-driven read (not the initial or `refresh()`-triggered ones), and `UploadPanel` passes `onUploaded` there too.

**A dropped file whose content dedupes as "already processed" gets its own notice (FR-3.5) — it's the one outcome that otherwise leaves no trace anywhere.** Reported live: a user uploaded a file, got a 200 `already_processed` response, and saw nothing change in the UI, which read as broken. It wasn't — `persistAndEnqueue`'s dedupe check short-circuits before creating a job at all for this outcome, so unlike "enqueued" (which shows up as a new `GET /v1/uploads` row once polling or a refresh catches it), an already-processed file was correctly changing nothing, just without saying so. `UploadPanel.tsx`'s `uploadOne` now pushes an info notice ("*filename* was already uploaded before") for exactly this case — confirmed live by uploading the same file twice: silent the first time (genuinely new content), the notice appearing only the second time.

**Google Takeout import (FR-3.3, §4.0.2) is built, through the same upload endpoint, not a separate one.** Dropping a Google Health/Fitbit Takeout `.zip` onto the same `UploadPanel` that takes a plain `.zip` gets auto-detected (`isTakeoutArchive`, `takeout_upload.go`, by a `Takeout/Google Health/` entry prefix) and routed differently, because the real export shape has no `.gpx`/`.fit`/`.tcx` files in it at all — GPS lives in per-day CSVs, activities in a separate JSON family, useless apart. Shells out to `pathify` (a separate Rust CLI, same author, MIT-licensed) rather than reimplementing that join — see §4.0.2 for the full account of why, and for the two features (`--list --json`, `--per-activity`) requested and shipped in pathify 1.4.0 specifically to make this possible. `services/server/Dockerfile` now has a Rust builder stage installing a pinned `pathify-cli` version, and the final image moved from `distroless/static` to `distroless/cc` for the libc a normal Rust binary needs — still no shell, no package manager. Verified against a real ~2000-file export, not synthetic fixtures: 118 activities imported, zero failures, cross-checked one activity's numbers by hand against `pathify info` on the same extracted file. **Gotcha already hit once, worth not rehitting**: anything that joins `jobs` back to `activities` by `external_id` must match on the job's own `source`, not a hardcoded `'upload'` — `uploadsListQuery` in `uploads.go` had exactly this bug, and it's an easy one to reintroduce since `'upload'` was the only source that existed when that query was first written.

### Activities panel & date-range picker

**The Activities panel (FR-5.1), header badge, and bottom histogram (FR-6) are three different hooks over two endpoints, not one shared fetch.** `ActivitiesPanel.tsx` renders `MapView.tsx`'s `GET /v1/activities` result (`src/ui/useActivityList.ts`); the header badge, the panel's "km loaded" subtext and the histogram's stats line all read one `GET /v1/activities/summary` response instead (`src/ui/useActivityTotals.ts`); the bars read `GET /v1/activities/histogram` (`src/ui/useActivityDays.ts`). A dev database only ever holds a handful of activities, so expect the screen to look sparser than a heavily-populated account would.

**The panel is a permanent left sidebar, not a collapsible dropdown** — there is always at least one activity to look at once anything has been uploaded, so hiding the list behind an open/close toggle had nothing to justify it. `MapView.tsx` renders it unconditionally alongside `.map-root` inside a flex `.app-body`; `Header.tsx` no longer takes an activities-toggle prop at all.

**`GET /v1/activities` stopped paginating** (`services/server/internal/httpapi/activities.go` — no more `cursor`/`limit`/`next_cursor`). The panel needs the full date range's rows at once regardless: the map draws every one of them, the TYPE/DISTANCE facets below are computed across all of them, and there was never a page 2 a caller could use without already having fetched page 1. Phase 0/1 has one seeded user with activity counts in the hundreds to low thousands at most — revisit if that stops holding, which a real multi-user Phase 2 likely changes.

**TYPE and DISTANCE (FR-5.2/FR-5.3, `src/ui/activityFacets.ts`) are unioned into the same `tracks.ts` filter the eye icon uses** (see below) for what the map draws — there's no second, separate map-filtering mechanism per control. Both live behind the panel head's "Filter" toggle (`ActivitiesPanel.tsx`'s own `filtersOpen` state, collapsed by default — most sessions don't start by narrowing TYPE/DISTANCE, so the row list gets the space until "Filter" is clicked) and share one "Reset filters" link. TYPE rows show `activity_type` humanized (`format.ts`'s `formatActivityType` — spaces out `snake_case`, title-cases each word) but never remapped: §4.7's "not a controlled vocabulary" resolution means there is still no fixed Ride/Run/Gravel vocabulary to reintroduce here.

**TYPE rows toggle in place; they don't disappear when excluded.** An earlier version rendered a removable chip per type — clicking it dropped the chip from the list entirely, which meant the only way to bring a type back was "Reset filters," and that also threw away the distance filter. Excluding a type now just unchecks its checkbox (real `<input type="checkbox">`s since §4.7.6's header-toolbar rework, not the earlier chip/`aria-pressed` markup) rather than removing the row — clicking it again restores it. `MapView.tsx`'s `toggleType` is a real toggle (add-or-delete in the `excludedTypes` Set), not the one-way `excludeType` it replaced. The list scrolls (`.activity-filters__type-list`, `max-height: 12rem`) rather than collapsing behind a "Show all (N)" control past a fixed count — §4.7.6's own dropdown already bounds its height, which made the earlier collapse-by-count mechanism redundant once it existed.

A long list of things about how that screen behaves, each easy to undo by accident:

- **The upload control belongs to the header, not the map.** It sits in the nav bar's trailing group between Donate and the account menu (`Header.tsx` takes it as an element). It's `UploadPanel.tsx`'s dropdown now, not a hover popover (§4.0.1 — see the "Built" bullet above), but the reason it lives in the header rather than floating over the map is unchanged: a 56px bar has nowhere else to put upload status, and nothing floats over the map canvas any more except the coverage notice. `.app-header` carries its own `z-index`, without which both this dropdown and the account menu's render *behind* MapLibre's zoom controls.
- **Donate is still a placeholder and says so out loud; "Sign out" and "Profile" aren't, any more.** `DonateButton.tsx` has no payment integration and goes nowhere — it opens `PlaceholderNotice.tsx` explaining what it'll do and why it does nothing today, a real choice over rendering it unclickable, since a control that visibly does nothing reads as a broken build and a greyed-out one still leaves "not yet" and "not for you" indistinguishable. Don't wire it to a real flow without the work behind it, and don't quietly convert it to `disabled` either, which loses the explanation. "Sign out" (`UserMenu.tsx`) now ends a real session via §4.9's auth system — `useAuth().signOut()` — and "Profile" navigates to `ProfilePage.tsx` (§4.8's activity graph); neither opens a notice any more. **Revised: the account menu now also has a `Settings` item** (§4.12, `SettingsPage.tsx` — Avatar, Name, Country, Privacy Trim), added after this paragraph was first written; the menu is no longer just Profile and Sign out. The dropdown shows the signed-in account's real email (`.user-menu__email`). `DonateButton.tsx`'s orange (`#a85412`) was a deliberate, specific choice, not eyeballed — deliberately not the app's usual blue, so Donate doesn't recede into looking like just another neutral nav action.
- **The bottom timeline draws one bar per day that has activity, packed — not one per calendar day (FR-6).** Empty days get no slot at all, so adjacent bars are adjacent *recorded* days however far apart their real dates are. Everything in `RangePicker.tsx` is therefore measured in bars, not days: a drag converts pixels to whole slots, and real dates reappear only when a selection is committed, since `selectedRange` is a date filter the list and summary endpoints have to understand. `useActivityDays.ts` pages the bars in from `?days=&before=` (§4.7) and owns the pan position as an *anchor date* rather than an index, because prepending a page shifts every index while the anchor still names the same bar. Arrow-key panning was removed rather than left as a redundant second path alongside the drag gestures and Earlier/Later buttons (FR-6.2–FR-6.4). `selectedRange` is not the sentinel "send no from/to"; it resolves to concrete dates once the first page lands, because the handles need real dates to sit at. **The FR-6.1 default (5 most recent activity-days, not all-time) exists because an all-time default spans every bar loaded on first paint, pinned to both edges with nowhere to slide** — dragging the band did nothing the first time anyone tried it, since there was nothing outside the selection to slide into. Dragging a handle renders from local state inside `RangePicker.tsx`, so a resize refetches the list only on release; panning needs no such treatment now that it moves a window over data already in memory. **This default has to keep re-deriving itself as new data arrives, not just once** — a zero-history account (every demo, on first load) degenerates it to `{today, today}`, and freezing there the first time `selectedRange` left `null` meant a demo's very first upload, on any other day, never showed up without a manual reload. Re-guarded on a `userChangedRangeRef` (set only by a real drag/click) instead, reconsidering on `useActivityDays.ts`'s new `generation` counter — bumped by a real reload, never by plain panning — see `IMPLEMENTATION.md` §4.7 for the full account.
- **Bar width/density is tightly packed now, not just packed in shape.** Confirmed live, not assumed: at the old `BARS_PER_VIEW` (45) and bar `max-width` (22px), a full screen's worth of bars sat in ~35px flex slots, each 22px bar floating in a ~13px gap — reported live as exactly that ("days too wide, gaps too big"). Two constants move together: `useActivityDays.ts`'s `BARS_PER_VIEW` (45 → 120, `PAGE_SIZE`/`PREFETCH_MARGIN` scale with it automatically since both are derived from it) and `.range-picker__bar`'s `max-width` (22px → 10px, `index.css`) — raising one without the other either keeps the same gap (more, still-fat bars) or shrinks bars without shrinking the slots around them (thinner bars, same fat gaps). A history shorter than 120 activity-days still shows exactly that many bars, each still capped at 10px — a sparse account's bars sit further apart because the history genuinely is sparse, not because they're rendered oversized to fill the space, the same "packed" reasoning as before, now at the right resolution to match. Verified live: dragging a handle, sliding the band, clicking a single bar, and paging via Earlier all still work correctly at the new density — none of RangePicker.tsx's own hit-testing math is keyed to a specific bar width or count.
- **The Earlier/Later buttons live in the header row now, not flanking the chart.** `ActivityHistogram.tsx` renders them next to the pan-window label on the header's right, and `RangePicker.tsx` no longer renders any buttons at all — it only takes `onPan` now (for its own drag-the-strip gesture), not `pageStep`/`canPanEarlier`/`canPanLater`, which moved to `ActivityHistogram`'s own props. That's what lets `RangePicker`'s chart span the footer's full width instead of sharing it with two button columns.
- **Panning must never touch the selection, and the layout is what keeps that honest.** The pan position lives in `useActivityDays.ts` and `selectedRange` lives in `MapView.tsx`; nothing writes across. Paging back to a user's very first activity leaves the selection exactly as it was, and when it scrolls off screen the band is simply not drawn — verified by driving the real UI, not assumed. The band itself is the slide target, but stays `pointer-events: none` in CSS — `RangePicker.tsx`'s `onChartPointerDown` does the "is this click inside the band" hit-test in JS instead, comparing the pointerdown's pixel position against the band's own rectangle. A first version made the band itself `pointer-events: auto` so CSS hit-testing could decide, which is simpler but swallows a covered bar's hover (title tooltip included) for as long as it's selected — a real cost, since a selection commonly covers most of the strip. Confirmed directly with `elementFromPoint` at the band's own center: it resolves to the bar underneath, not the band, so hover reaches every bar regardless of selection state. The edge handles still win at their exact pixels regardless of any of this, since they're children painted above their own parent with their own `pointer-events: auto` and their own `onPointerDown` that stops propagation first. The month rail along the bottom is excluded from the hit-test on purpose — it's the one strip of the chart a selection band can never claim as a slide target, so a selection spanning the whole visible width (still possible by dragging a handle all the way to an edge) always leaves somewhere to grab for panning.
- **Bar height is log-scaled against the busiest day on screen, not linear.** A single outlier day (a big multi-activity ride) would otherwise flatten every ordinary day on the same strip down to the visibility floor, since a linear scale makes height *proportional* to the peak rather than merely *ordered* by it — confirmed directly: an 0.9 km day that rendered at single-digit percent height under the old linear scale renders past 60% under `log(distance + 1) / log(peak + 1)`, without changing which bar is tallest.
- **The footer header is two independent corners, not one stacked column.** The left block (`.activity-histogram__summary`) names the *selection* — its date range, then how many of its calendar days actually have activity (`"N-day range · M active days"`, computed in `MapView.tsx` from the same `activities` list the map and badge already use, not from the picker's own `days`, which is the pan window and can be scrolled somewhere else entirely). Worded that way — not the original `"N days · M with activity"` — after a real report: at a single selected day with 2 activities on it, the original read "1 day · 1 with activity", indistinguishable at a glance from an activity count of 1, when the actual count (2, correct everywhere else — badge, row list) was never wrong. `M` was always a *day* count; the label just didn't say so a second time. It deliberately does not repeat km/activity-count/duration/elevation — those already live in `ActivitiesPanel`'s "km loaded" subtext and ACTIVITIES badge, and showing them twice was the previous design. The right corner, absolutely positioned against the footer's own padding, names the *pan window* instead — a different question the selection doesn't answer, which is why it moved out of the left column rather than just changing font size.
- **Rows have four interactions again (FR-5.4–FR-5.7), and row-click focus and the checkbox group are two fully independent pieces of state now, not one shared `Set`.** History: a checkbox (multi-select) and a row-text "focus" toggle (single activity, immediate fly) were once collapsed into one clicking-the-text-toggles-membership mechanism — reported live as the wrong merge (no way to build a group without losing the first click) — then unified into one `selectedActivities` `Set` two ways in (checkbox added/removed, row-text click replaced). That unification turned out wrong too, reported live a second time: a row click was silently checking/unchecking boxes it had no business touching. `MapView.tsx` now keeps `checkedActivityIds` (the checkbox group, additive/subtractive, `toggleActivityChecked`) and `focusedActivityId` (the row-click focus, `string | null`, replace-on-click, `focusActivity`) as two separate `useState`s that never write to each other in either direction. Hovering a row still bolds it on the map with zero camera movement, cleared the instant the pointer leaves — unrelated to either. What's bold on the map (`setSelectedTracks`) is the **union** of the two (`boldedActivityIds`, `useMemo`), computed once and consumed by both the map effect and each row's own `.activities-panel__row--selected` class (`checked.has(id) || focusedId === id`) — so a row checked *and* currently focused still renders as one indistinguishable bold, not two competing states. **Two separate fly triggers, not one**: a row click flies immediately to that one activity's own bbox (`focusActivity` calls `fitToSelection` directly, the same imperative single-click style `clearSelection` already used); the checkbox group still flies via the debounced effect (`SELECTION_FLY_DEBOUNCE_MS` = 300ms), now keyed on `checkedActivityIds` alone — checking a box never re-flies to wherever the focused row happens to be, and vice versa. The footer's `.activities-panel__clear` button is dual- purpose now: "Select all" (checks every row `filteredActivities` currently lists, flies to fit them) when `checked.size === 0`, "Clear" (empties the checked group only — a focused row keeps its own highlight — flies to fit everything visible, unchanged from before) once it isn't. A new `.activities-panel__show-selected` button next to it re-triggers the same fly-to-fit-checked-group on demand, with no state change, for after panning away from it. Colored zone segments (`trackBands.ts`, §4.3.1) key off `focusedActivityId` directly now, not the old "checked set happens to have exactly one id" derivation — checking a single box no longer incidentally shows bands; only a row click does.
- **The map's tracks layer is now actually scoped to the selected date range** — it wasn't, for a while. `tracks.ts`'s tile source silently omitted `from`/`to` entirely, so it drew every track ever uploaded regardless of `selectedRange`, while the Activities list beside it correctly narrowed — confirmed live via the actual tile request URLs, not assumed. `MapView.tsx` now calls `refreshTrackLayer(map, activityQuery)` whenever `selectedRange` changes, alongside a second effect that auto-flies to fit whatever's now actually visible (`activities` minus `mapHiddenIds`, read through a ref so TYPE/DISTANCE/eye-icon changes don't also trigger a fly — only a genuine range or upload change does, since those are the only things that produce a new `activities` array at all). Without that second effect, narrowing the tracks layer to a new range could leave the camera pointed at empty water if the old view didn't overlap the new one. Skips firing the very first time `activities` has anything in it, so an initial or shared URL view isn't overridden on first load.
- **Clicking a track directly on the map is the row-text "focus" behavior** (`tracks.ts`'s `onSelect`, wired to `focusActivity` in `MapView.tsx`) — bolds just that one track, flies to it, and replaces whichever track was focused before, the same as clicking its row's text would. Originally wired to the checkbox's add/remove instead, with no fly ("the camera's already wherever it needs to be for the user to have clicked it") — reported live as wanting the row-text behavior instead, since there's no visible checkbox on the map to mirror, and "acts like the row you'd click" reads as the more natural match for a direct click on the track itself. A checked row's own bold treatment (FR-5.6) is untouched by this — a map click never adds to or removes from the checked group, in either direction. `setSelectedTracks(map, ids)` bolds every currently-selected id, not just one — it diffs against the previously-applied set (module-level, mirroring `setHiddenTracks`'s own diffing below) so a change only touches the feature-states that actually flipped. **Hovering a track goes through `MapView`'s shared `hoveredActivityId` React state, the same state a row's own `onMouseEnter`/`onMouseLeave` write to** — this is what makes hover a two-way mechanism (FR-5.4): hovering a row bolds the matching track (as it always did), and hovering a track underlines the matching row's title in `ActivitiesPanel.tsx` (a new `hoveredId` prop compared against each row's own id → `.activities-panel__title--hovered`) — reported live as one-directional and missing the map-to-row case. `tracks.ts`'s own `hoveredId` module variable (distinct from React's) is what keeps this cheap despite going through state: it only calls `handlers.onHover` when the id actually changes, not on every `mousemove` pixel, so this isn't a per-pixel re-render — MapView's effect then calls `setHoveredTrack(map, hoveredActivityId)` to apply the actual feature-state bold, cleared on `mouseleave` the same way it always was. Two things worth not re-breaking if you touch this: the vector source needs `promoteId: 'id'` for feature-state to key on the real activity UUID instead of a meaningless per-tile numeric id, and hover/click listeners are attached exactly once per map instance (a module-level `WeakSet`), not once per `ensureTrackLayer` call — that function re-runs on every theme/mode `styledata` because `setStyle` discards custom layers, but the listeners are layer-id-scoped and keep working across a layer being removed and re-added, so re-attaching them there would silently stack duplicate handlers per toggle.
- **Each row's eye icon (FR-5.8), client-side only** — `tracks.ts`'s `setHiddenTracks` applies a layer `filter` excluding the hidden ids, unioned in `MapView.tsx` with whatever TYPE/DISTANCE currently filters out, since both answer the same question for the map ("don't paint this one"). There is no backend request either way, and hiding a track doesn't clear its selection — those answer different questions (what's drawn vs. what's selected). Changing the selected date range clears the hidden set, the selection, and both TYPE/DISTANCE filters together (`MapView.tsx`'s `changeSelectedRange`) — all three could otherwise silently describe activities the new range doesn't even list, and a stale DISTANCE band in particular could exclude everything if the new range's real min/max don't overlap it. See "Gotchas worth not rediscovering" below for why `setHiddenTracks` diffs against the layer's current filter before calling `map.setFilter` — it isn't a stylistic choice.
- **The Activities panel's resize handle (FR-5.9)** — added after a plain title like "Sep 11, 2026, 09:00 AM" plus its TYPE label clipped at the old fixed 320px. `panelWidth` is local component state (260–560px, default 380px), not lifted to `MapView.tsx`: nothing outside this component's layout needs it, same reasoning as `filtersOpen`. Not persisted across reloads — no other UI preference here is, and this one didn't seem worth being the first. The drag handle uses Pointer Capture (`setPointerCapture`), the same pattern `RangePicker.tsx` uses for its own drag, so the drag keeps tracking even if the cursor leaves the 6px hit target mid-drag. It's positioned at `right: 0` inside the panel, not straddling the edge (e.g. a negative offset) — the panel has `overflow: hidden` for its scrolling list, which clips and makes unclickable anything positioned outside its own box.
- **Single-day select on the histogram (FR-6.5)** (`RangePicker.tsx`). Bars carry no click handler of their own — the chart already has to hit-test pan vs. slide on every pointerdown, so a click is recognized the same way: in `endDrag`, a pan-mode pointerdown/up pair that ends within `CLICK_MOVE_THRESHOLD_PX` (4px) of where it started *and* never actually panned (`drag.panned === 0`) is read as a click on whichever bar is underneath rather than a pan that went nowhere. Both conditions matter, not just one: the pixel check alone would miscount a real pan across many wide bars that happens to round to zero slots as a click, and the `panned === 0` check alone would miscount a click with a few pixels of incidental jitter (trackpad, touchscreen) as an intentional drag. Clicking *inside* the current band still slides it (mode `'slide'`, unaffected by this — confirmed live: clicking the band's own center leaves the selection unchanged rather than collapsing it to one day).
- **Fixed: selecting a hidden activity flew the camera to empty space.** Clicking a row's text is independent of its own eye icon (hiding its track) — a hidden-but-selected activity is a normal, reachable state — but the auto-fly-on-selection effect (`MapView.tsx`) flew to every selected activity's bbox regardless of whether it (or a TYPE/DISTANCE filter) was currently hiding it, so selecting a hidden one flew the camera to wherever its track would be if it were drawn. Now excludes `mapHiddenIds` before flying, matching the same exclusion the band-change auto-fly effect already applied for the identical reason. If every selected activity is currently hidden, `unionBBox([])` is `null` and the fly is a no-op.
- **Fixed: a pan drag could hijack a later handle drag into a native browser drag, in Firefox.** `RangePicker.tsx`'s `beginDrag` never called `event.preventDefault()`; a pan that crossed the month labels' text let Firefox start its own "select this content" gesture, and a later drag — a resize handle included — then got reinterpreted as dragging that native selection instead of being delivered as `pointermove` events, so the handle visually did nothing (or dragged the whole component like an image). Chromium doesn't trigger this as readily, which is why this session's own Chromium-only regression suites never caught it. Fixed with `preventDefault()` in `beginDrag` plus `user-select: none` on the chart as a second line of defense. See `IMPLEMENTATION.md` §4.7's own writeup for the full account.

### Mobile browser support

**Built, but not actually usable yet — reported directly as unusable, not just rough, and needs rework, not polish.** The rest of this section is the design record for whoever picks that up.

**One new `@media (max-width: 768px)` layer at the end of `index.css` (§5.9, `SPEC.md` §13) — no mobile mockup ever existed for this; it was designed from scratch.** Scope, decided directly with the user: "core flows fully touch-usable," not full parity — `TrackProfile.tsx`'s colored-band/elevation hover values (FR-4.9) and the map-track-hover ↔ Activities-row-underline highlight (FR-4.1/FR-5.4) stay mouse-only, a documented boundary, not an oversight (both are a continuous-position hover read with no discrete point to tap, unlike Trends below).

**The Activities panel becomes an overlay bottom sheet, not a layout-affecting sidebar, under the breakpoint** — `position: fixed` removes it from `.app-body`'s flex row entirely, so `.map-root` (`flex: 1`, the only child left) fills the width automatically with no `.app-body` change needed. This also means the map's own container size never changes with the sheet open or closed, so no `map.resize()` call is ever needed — deliberate, not an oversight, since a width/height-affecting panel would risk resize-thrashing jank during a drag. `ActivitiesPanel.tsx` gained a local `sheetExpanded` boolean (same shape as its own `filtersOpen`), collapsed by default; the tap target is the existing count/distance subtext line, now a `<button>` reset to look pixel-identical to plain text at desktop width (`cursor: default` there, `pointer` only under the mobile query) so clicking it at desktop width is an invisible no-op. `panelWidth` moved from an inline `style.width` to a CSS custom property specifically so the mobile query's `width: 100%` can cleanly override it — an inline style otherwise always wins over an external rule short of `!important`.

**Two real bugs found live, not anticipated going in — both worth remembering beyond this feature:**
1. **The histogram/date-range-picker footer was completely unaddressed in the first CSS pass** despite being persistent map-screen chrome — its header row (range summary + pan-window/Earlier/Later buttons) has no shrink/wrap at all, and at ~390px the two sides together forced the *whole page* wider than the viewport, which then corrupted the Activities panel sheet's own `width: 100%` (a `position: fixed` element's percentage width resolves against that same widened layout viewport). Fixed at the actual source (`.activity-histogram__header { flex-wrap: wrap; }` + a bit more height on the histogram itself), not by patching the sheet.
2. **A tap's own browser-synthesized compatibility mouse events broke the tap fallback they were supposed to coexist with** — `Trends.tsx`'s new `onClick` handler worked, but a `mouseleave` synthesized right after the tap (for the benefit of mouse-only listeners elsewhere) immediately re-cleared the state it had just set. Fixed by switching `onMouseEnter`/`onMouseLeave` to `onPointerEnter`/`onPointerLeave` guarded by `event.pointerType === 'mouse'` — `PointerEvent` carries which input actually produced it, `MouseEvent` doesn't, so a touch-synthesized one is now correctly ignored while a real mouse hover is untouched.

**Verified live**, phone-emulated (Playwright `devices['iPhone 13']`, 390×844, real touch events): zero horizontal overflow anywhere; the sheet collapses/expands correctly on tap with the map staying interactive while collapsed; the resize handle is hidden; the range-picker handle's computed width is the widened 30px; `Trends` tooltips show on tap and clear on tapping elsewhere; zero console errors. Desktop's `verify:map`/`verify:build` suites both still pass unmodified.

### Deployment

**Minimal single-VPS deployment scaffolding exists now (`docs/DEPLOY.md`, `IMPLEMENTATION.md` §5.8) — repo-side pieces only, never run against a real server.** `compose.prod.yml` (repo root, standalone — not a `compose.yaml` overlay): db (Postgres+PostGIS), `migrate`, `api`, `worker`, and `web` (Caddy + the built frontend, the only publicly-published service). `apps/web/Dockerfile` gained `build` (`tsc --noEmit && vite build`) and `serve` (a `caddy:2-alpine` image copying that output plus `apps/web/docker/Caddyfile`) stages. One Caddy container does reverse-proxying *and* static serving from one origin — `/v1/*`/`/tiles/*`/`/healthz` to `api`, everything else the SPA — which is why the production build sets `VITE_API_BASE_URL=""` unconditionally and why `httpapi/server.go`'s `corsAllowedOrigins` needed no production entry: same-origin fetches are never cross-origin, so CORS doesn't apply. `auth.go`'s session cookie `Secure` flag is now `strings.HasPrefix(s.appBaseURL, "https://")` instead of a hardcoded `false` — reuses `APP_BASE_URL` rather than a second env var that could disagree with it; dev's `http://localhost:5173` default keeps this `false`, unchanged.

**The style document is served by the API, and the Go side does not define it** (`ARCHITECTURE.md` §2.1). `GET /v1/map/style/{flavor}` (`services/server/internal/mapstyle`, `internal/httpapi/map_style.go`) hands native clients the same style the web client renders — the Android app's first hard dependency (`apps/android/docs/ROADMAP.md`). The load-bearing rule: **`apps/web/src/map/style.ts` is the only definition of the style.** `apps/web/scripts/build-style.mjs` renders `buildStyle()` to one JSON file per flavor under `internal/mapstyle/styles/`, which `go:embed` picks up; those `.json` files are build output, so change `style.ts` and re-run `npm run build:style` rather than editing them. `npm run verify:style` regenerates in memory and fails on any difference, which is what stops the Go copy drifting from the TS one — the exact failure §2.1 was written to prevent. Asset URLs are generated with an `__FITMAP_BASEMAP_ORIGIN__` placeholder the server substitutes from `BASEMAP_ORIGIN` (defaulting to `APP_BASE_URL`) per request, so one binary serves both a bundled-archive and a CDN deployment. Deliberately unauthenticated, unlike every other `/v1` route: it is derived from the public Protomaps basemap and carries no per-user data. Verified live against all five flavors — the served document is byte-identical to `buildStyle()`'s own output for the same origin.

**The basemap archive can never be baked into any image** — `apps/web/.dockerignore` excludes every `*.pmtiles` from every build context on purpose (dev reads it via a bind mount instead). New `config.ts` `basemapOrigin()` reads a build-time `VITE_BASEMAP_ORIGIN` (a Docker build ARG, threaded through `apps/web/Dockerfile`'s `build` stage and `compose.prod.yml`), falling back to the existing `browserOrigin()` when unset; `useMapInstance.ts`/`exportMap.ts` call it instead of `browserOrigin()` directly for the `origin` passed to `style.ts`'s `buildStyle` — which needed no change at all, since its `origin` parameter already accepted an arbitrary absolute origin by design. `docs/DEPLOY.md` documents two ways to actually supply the archive (bind-mount it into the `web` container, or host it on R2/a CDN and set the env var) and defaults to the former as the simpler start.

**Verified directly**: `apps/web/Dockerfile`'s new stages build end to end; `caddy validate` against the built image's own Caddyfile passes once `DOMAIN` is set (and fails a different, informative way when it isn't — an empty `{$DOMAIN}` gets parsed as Caddy's *global options* block instead of a site block, confirmed live); `docker compose -f compose.prod.yml config` resolves cleanly; the dev stack's `verify:map`/`verify:build` suites still pass unchanged; a live signup against the running dev `api` confirms the cookie still carries no `Secure` attribute under dev's plain-HTTP `APP_BASE_URL`.

### Edit activity type and description

**A user can rename an activity's type and attach a free-text description after upload (FR-5.10, `IMPLEMENTATION.md` §4.7.4) — reached from a new pencil icon per row (`.activities-panel__edit`), a `<dialog>` modeled on `PlaceholderNotice.tsx`'s existing pattern.** Direct product ask: a fitness tracker with no "Solowheel" category gets logged as something else and renamed after sync; a non-sport GPS trace (a road trip) gets uploaded and described the same way any activity is, then filtered out later like any other TYPE. Both "just work" once the dialog exists, because §4.7.2 already made `activity_type` free-form — a manual rename needed no schema or filter change, only a way to make the edit. `PATCH /v1/activities/{id}` (new, `internal/httpapi/activities.go`) follows `account.go`'s `handleUpdateSettings` shape (full-replace-on-save, `NULLIF($n, '')` for "empty description means cleared"), ownership-scoped like `track-metrics/{id}`. `activities.description` (nullable `TEXT`, `migrations/0001_init.sql`) is the one new column this needed — `activity_type` itself needed no schema change at all, already `VARCHAR(50) NOT NULL` with no CHECK constraint. Saving calls `useActivityList`'s `reload()`, the same "just refetch" convention an upload completion already uses, rather than patching local state — `activityFacets.ts`'s TYPE chips and the row's own tooltip (the description's only display surface, confirmed directly with the user — no second visible line) then recompute for free from the refreshed list. Trends and Fog/Heatmap are unaffected and verified live, not just reasoned about — neither keys on `activity_type`.

### Delete an activity — a full purge, not a soft delete

**`DELETE /v1/activities/{id}` (FR-5.11, `IMPLEMENTATION.md` §4.7.5) removes an activity and everything derived from it — track, fog/heatmap coverage — with no undo.** Most of that is free: `activity_streams`/`activity_tile_masks` are both `ON DELETE CASCADE`, and Trends is live-aggregated, not cached, so it self-corrects once the cascade lands. **The one piece that genuinely needed investigation first**: the *unfiltered* Fog/Heatmap view reads a precomputed per-user, per-tile cache that only ingest ever marks dirty or re-renders — deleting an activity would otherwise cascade its masks away while leaving that cache's already-rendered PNGs stale indefinitely. Fixed by exporting `ingest.MarkFogTilesDirty`/`ingest.EnqueueRenderFog` (previously ingest-only) so the delete handler can re-trigger the same machinery, reading the activity's own touched tiles out of `activity_tile_masks` *before* the cascade removes that information. `RenderUser`'s own render is already "idempotent and complete per tile, not incremental," so no new compositing logic was needed — just re-triggering it. **Verified live, not just reasoned about**: uploaded two activities with overlapping tile coverage, confirmed both visible on the unfiltered Fog tile, deleted one and confirmed the served PNG actually changed (localized, not the whole tile), deleted the second and confirmed the tile became a single uniform fog color — exactly what zero coverage renders as. `raw_payload_key` cleanup checks for a still- referenced sibling first (content-addressed, not source-scoped, so two activities can share one key on byte-identical content) rather than risking deleting a blob another activity still points to. Frontend: row icon order is now **Visible, Edit, Delete** (the eye icon moved before the pencil), a direct product decision; a new `ConfirmDialog.tsx` (generic, not delete-specific — reuses the same `<dialog>` shape `PlaceholderNotice.tsx`/ `EditActivityDialog.tsx` already established) gates the click since there's no undo. `MapView.tsx`'s delete handler reuses `handleUploaded` verbatim (deleting changes totals/histogram, unlike editing) and clears `focusedActivityId` specifically if it pointed at the now-deleted activity, so the colored-zone-segments panel doesn't keep trying to fetch `track-metrics` for something that no longer exists.

### Android app: map, session and the three map modes

**`apps/android/fitmap` is a real client now, not a placeholder** — a Kotlin/Gradle app on MapLibre Native 13.6.1 that signs in against the same accounts the web client uses and renders Normal / Fog of War / Heatmap over the served basemap. `apps/android/docs/ROADMAP.md` is the authority on what is built and what is next (Health Connect ingestion); `apps/android/fitmap/README.md` covers building it and pointing it at an API. The toolchain is on the host, not containerised, deliberately: the SDK, `adb` and the physical device Health Connect testing needs all live there.

**Two things are worth knowing before touching it.** First, **the session is a bearer token, not a cookie, and the reason is MapLibre**: the map SDK fetches the style, the basemap archive and every tile through its own HTTP stack, which the app's API client never sees, so `FitMapApplication` hands MapLibre the app's own `OkHttpClient` (`HttpRequestUtil.setOkHttpClient`) and one interceptor attaches `Authorization: Bearer <session id>` to both surfaces. The server side of this already existed — `sessionIDFromRequest` in `internal/httpapi/auth.go` reads the cookie first and falls back to the header, the same `sessions` row either way. The interceptor scopes itself to FitMap's own API origin so a CDN-hosted basemap never receives a live credential. Second, **a restored token is verified against `GET /v1/auth/me` before any user layer is attached**: an expired or revoked session would otherwise surface only as 401s in logcat, behind a map that looks merely empty — which is the same failure the on-screen error banner already exists to prevent.

**`pmtiles://` needs nothing extra on mobile, and the caching caveat in MapLibre's docs is half out of date.** MapLibre Native reads the scheme natively (Android 11.8.0+), so the style document is consumed exactly as the API serves it. Its docs' "PMTiles sources do not support offline pack downloads or caching" pre-dates the 13.3.0 ambient cache: inspecting `files/mbgl-offline.db` on a device found the archive's header, directories and tile byte ranges all cached across launches (keyed `?_mlnRange=<start>-<end>`). Offline *packs* genuinely still don't work for a pmtiles source, which FitMap does not use.

**A gotcha that only a real screen finds**: at `targetSdk` 35+ the system draws every app edge to edge and ignores the old opt-out, so anything laid out at the bottom of the window sits under the gesture navigation pill, and an action bar overlays a scrolling layout that hasn't asked for `fitsSystemWindows`. Verified end to end on a Pixel 10a against a live `db`/`minio`/`api`/`worker` stack — sign-in, demo account, session survival across a cold start, sign-out revoking server-side, a server-revoked token detected on the next launch, and one screenshot per map mode.

### Android: Health Connect sync (Path 2)

**The app ingests from Health Connect now** — `SyncActivity` over `health/` and `sync/`, posting to `POST /v1/sync/activities`. Three Health Connect permissions covering **one data type**: `READ_EXERCISE`, plus `READ_EXERCISE_ROUTES` (part of a session, not a type) and `READ_HEALTH_DATA_HISTORY` (a time window, not a type). That list is the Play Console declaration, and it is deliberately the shortest one that works — heart rate is not read, because the product draws outdoor GPS routes and a fourth type would be requesting more than it demonstrably uses.

**Three platform limits, each found by running it rather than reading about it.** `READ_EXERCISE_ROUTES` cannot be requested programmatically at all — the user grants it in Health Connect, two screens below the app's own permission page, and nothing links there, so the onboarding names the taps. `ACTION_MANAGE_HEALTH_PERMISSIONS` would land the user on exactly the right page but is guarded by a signature permission, so launching it from an ordinary app is a `SecurityException` that kills the process; `HEALTH_HOME_SETTINGS` is what third-party apps can open. And **Health Connect serves only the last 30 days** without `READ_HEALTH_DATA_HISTORY`: the first real sync returned exactly 30 days and Health Connect's own screen named the cutoff date.

**The watermark is the part to be careful with** (`sync/SyncCursor.kt`, `docs/IMPLEMENTATION.md` §4.0). It only ever moves over records that are *terminal* — the server took it, already had it, permanently refused it, or it has no route and never will. A route that exists but could not be read, or a request that failed, stops it dead and stops the run, because advancing past those produces a history complete in every respect except the map. It is also an instant **plus the ids handled at that instant**, since `TimeRangeFilter.after` is inclusive and two sessions can share a start time. Verified on a device: a second sync reads 0 sessions; a cursor reset re-walks to 24 `already_processed` and 0 duplicate rows; a run against an unreachable API reports where it stopped and leaves the watermark untouched, and the retry recovers all 27.

**Activity types are normalized, and it is not cosmetic**: Health Connect says `biking`, a `.FIT` upload of the same ride says `cycling`, and cross-source deduplication (§4.6) matches on the activity type — so leaving them different would split TYPE facets and defeat the dedup outright. `health/ExerciseTypes.kt` maps them, written against public constants because the library's own `EXERCISE_TYPE_INT_TO_STRING_MAP` is `@RestrictTo`.

### Cross-source deduplication, and what "live" now means

**`activities` has a `superseded_by` column, and almost every read has to respect it** (`internal/ingest/dedupe.go`, `IMPLEMENTATION.md` §4.6). One ride can arrive from a watch and from a file with two genuinely different `external_id`s, which `idx_activities_dedupe` cannot catch, so identity is fuzzy: same user, same activity type, start within half a minute either way, distance within ~1%. It is matched as a **window** around the incoming activity, not as equality on a pre-rounded bucket — rounding first makes matching a lottery at the bucket edges, measured on a real pair three seconds apart that landed either side of a minute boundary. The richest copy wins (geometry over none, then more stream channels) and the rest are marked rather than deleted, so `GET /v1/activities/duplicates` can say why something disappeared.

**If you add a query over `activities`, decide explicitly whether it wants `superseded_by IS NULL`.** Every user-facing read has it: list, summary, histogram, day pages, trends, graph stats, tracks tiles, and both fog and heatmap composites. The ones that deliberately don't are the receive-time idempotency checks on `(user_id, source, external_id)` — an already-superseded row is still "already processed" — and the per-id lookups behind editing and deleting, which have to keep working for a duplicate the user can see.

**Two traps worth not rediscovering.** `activity_streams.elevation_m` and `heartrate` are arrays and ingest writes one element per point, so a track that carried no elevation at all still has a **non-null array full of nulls** — `IS NOT NULL` on the column is always true, and the richness comparison silently never decided anything until it started checking for a non-null *element*. And `superseded_by` is `ON DELETE SET NULL`, which is the behaviour you want (delete the winner and the copy it displaced comes back) but releases *every* displaced copy at once, so the delete path has to re-rank them or the ride ends up live twice and visibly double-counted in the additive heatmap.

### Android: sync history and duplicates

`SyncStatusActivity` reads `GET /v1/uploads`, which lists **ingest jobs**, not syncs — a Health Connect session and an uploaded file are the same job kind, so they share one history. It polls every two seconds only while something is processing. Its second section lists duplicates, because once two ingest paths exist an activity can be missing either because it failed or because it was already here from somewhere else, and only the first is a fault.

## Markdown Formatting Style

- **No hard-wrapping:** Markdown files are not hard-wrapped at a fixed column (~90-100 chars) the way a plain-text file would be.
- **No single newlines in paragraphs:** Markdown treats a single `\n` inside a paragraph as a soft break (renders as a space, not a line break), so a mid-paragraph line break serves no purpose — write each paragraph as one line.
- **No blank lines in lists:** Do not add empty lines between consecutive list items or block elements unless explicitly requested.
- **No trailing newline at EOF:** Do not add a final trailing newline character (`\n`) at the end of `.md` files. Cut the file off immediately after the last character.
- **Strict writing:** When modifying or writing `.md` files, preserve the existing newline density exactly.
