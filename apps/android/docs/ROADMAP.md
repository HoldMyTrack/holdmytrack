# HoldMyTrack for Android — Roadmap

This document outlines the engineering and product roadmap for the native Android application. The Android app's primary responsibility is to serve as an on-device ingest path (Path 2, `docs/adr/0001-three-independent-ingest-paths.md`), reading platform health data via **Health Connect** and displaying the shared map interface using **MapLibre Native**. Phase 7 adds a second, unrelated way an activity can originate on this app: casual, GPS-only recording done directly in HoldMyTrack, submitted straight to the server rather than through Health Connect ([ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md), `docs/VISION.md` §4.1).

As stated in `apps/android/README.md`, the Android development environment is not containerized and runs directly on the host machine.

`apps/android/` holds two Gradle builds: `fitmap/`, the app itself, and `poc-healthconnect/`, the throwaway Phase 1 diagnostic that is deleted once its findings are all recorded here. Every server-side prerequisite the app depends on is built — see the list below.

## Where this sits in the wider plan

Read `docs/ROADMAP.md` (Phase 2 — Mobile) first; this document expands one item of it and does not override it.

- **The toolchain is on the host, not in a container** (`apps/android/README.md`), and it is installed: the Android SDK at `/opt/homebrew/share/android-commandlinetools` with platform 37, build-tools 37 and `adb` under `platform-tools/`, alongside JDK 21, which the Android Gradle Plugin supports. `ANDROID_HOME` is not exported by default, so export it (or write `sdk.dir` into `local.properties`) before invoking `./gradlew`. There is no Android Studio, but an AVD now exists (`fitmap`, a Pixel 7 image on Android 16/API 36, under `emulator/`) — used for Phase 7's own verification (`apps/android/docs/SPEC.md` §9); FR-1 through FR-4's own verification record still names a physical device specifically, and that distinction is worth preserving rather than blurring the two.
- **Android ships first of the two mobile apps**, so the Path 2 contract is designed against the more constrained platform. Android defines the payload shape and the sync-cursor semantics that `POST /v1/sync/activities` accepts, and iOS inherits them. Every server-side prerequisite below is on the critical path.
- **The design freeze is Phase 3 of the root roadmap, after Mobile**, and the root plan itself flags this ordering as diverging from `VISION.md` §5 and "not yet reconciled". Every screen here is therefore built to work and left unstyled, with Phase 5 below as the pass that finishes them — so the app has no icon set, type scale or token system yet, and that is a schedule, not an oversight. The visual design comes *from* that root pass rather than being decided again here: two clients that each invented their own palette and type scale would not read as one product.
- **Cross-source deduplication is part of this phase, not a later one.** Root `ROADMAP.md` calls it "unavoidable once a second ingest source exists, which mobile sync is" — see Phase 4 below.

## Technical Foundations & Platform Constraints

Before implementing any UI or sync routines, we must design around two hard platform constraints. Both are already verified against platform and vendor documentation in `docs/IMPLEMENTATION.md` §4.0 — this section does not re-derive them.

1. **Foreground-Only Route Sync**
   - **Constraint**: `READ_EXERCISE_ROUTES` cannot be requested programmatically; the user grants it manually in Health Connect settings. Routes written by other apps cannot be read in the background — `ExerciseRouteResult.ConsentRequired` is returned even with "Always allow" granted.
   - **Decision**: Android sync is strictly **foreground-only** (`docs/IMPLEMENTATION.md` §4.0). We will not build background route sync. The specific trap this avoids is named there: a background sync "advances the watermark past records whose routes were never read", producing a history that is complete in every respect except the map — worse than no sync at all.

2. **Samsung Health Route-Geometry Limitation**
   - **Constraint**: Samsung Health writes summary data but does not expose GPS route geometry (`EXERCISE_ROUTE`) to other apps via Health Connect, so Galaxy Watch sessions never carry a route (`docs/VISION.md` §4.1, `docs/IMPLEMENTATION.md` §4.0).
   - **Decision**: HoldMyTrack only ingests activities that have a route — this is a deliberate product boundary (`docs/VISION.md` §1.1), not just a platform limitation to work around. A session with no geometry is rejected at sync time with a clear reason (`POST /v1/sync/activities` already does this — see the server-side prerequisites below), not persisted and not silently dropped. In practice this means **Samsung Galaxy Watch sync is unsupported**: every Samsung-sourced session arrives with no geometry and is therefore always rejected.
   - **Route-less activities are ordinary, and indoor exercise is why.** A gym session, a swim or a rowing machine has no trajectory by its nature — `docs/IMPLEMENTATION.md` §4.0.2 already meets the same case from the Takeout side and skips it there too. Measured on a real store (Phase 1 below), half the sessions had no geometry on exactly these grounds, and all of Samsung's do, regardless of activity type. HoldMyTrack's scope is outdoor GPS tracking, so these are skipped by design rather than represented — a gap to close later would only make sense for a product that also wants to be a general fitness tracker, which this one deliberately isn't.

## Server-side prerequisites

These are **not Android work**, but no Android phase can complete without them. Each is listed against the phase it blocks so the dependency is visible when scheduling.

- [x] **Serve the basemap style as a document from the API** (`docs/ARCHITECTURE.md` §2.1).
  `GET /v1/map/style/{flavor}` serves it, for the five flavors `style.ts` defines. `buildStyle()` remains the only definition of the style: `apps/web/scripts/build-style.mjs` renders it to JSON, `services/server/internal/mapstyle` embeds and serves that, and `npm run verify:style` fails on drift between the two. Asset URLs resolve against `BASEMAP_ORIGIN` (defaulting to `APP_BASE_URL`) at request time. Unauthenticated, and `ETag`/`If-None-Match` revalidation is wired up so a phone re-fetches ~100 KB of layer definitions only when it actually changed.
- [x] **Build `POST /v1/sync/activities`** (`docs/IMPLEMENTATION.md` §4.0.3).
  Takes a JSON batch of `{external_id, activity_type, points[]}`, `source` one of `"healthconnect"`/`"healthkit"`. Idempotent on `(user_id, source, external_id)` using the client-supplied `external_id` directly, not a content hash — unlike Path 3's file upload, Path 2 already carries a stable platform id. Reuses the existing ingest pipeline unchanged: `internal/parse` gained a `.json` case (`ParseJSON`) so `ingest.Process` needs no Path-2-specific branch, and `persistAndEnqueue` gained an optional caller-supplied `ExternalID`. One bad activity in a batch is rejected individually rather than failing the whole request, mirroring `handleZipUpload`'s per-entry treatment. Verified live against a running `db`/`minio`/`api`/`worker` stack: synced a 3-point run, watched it reach `state = 'done'` and show up in both `GET /v1/activities` and `GET /v1/uploads`, confirmed the persisted `raw_payload_key` is scoped `raw/{userID}/healthconnect/{externalID}.json` rather than content-addressed, and confirmed a retried sync of the same `external_id` returns `"already_processed"` rather than a duplicate row.
- [x] **Decide the mobile auth surface, and build server support for it** (`internal/httpapi/auth.go`).
  Sessions are an opaque `fitmap_session` cookie holding a `sessions` row id, 30-day TTL. The CORS allowlist (`corsAllowedOrigins`, `server.go`) was never relevant to this decision — CORS is a browser-enforced concept a native HTTP stack (OkHttp, `URLSession`) is never subject to, so mobile was never going to need adding to it.
  **Decision: `Authorization: Bearer <session-id>`, reusing the same `sessions` table** — not a new token system, just a second way to present the same credential `currentUserID` already validates. The deciding factor wasn't whether a cookie jar could work (it can — both OkHttp and `URLSession` support one natively) but that the mobile app has *two* separate HTTP surfaces needing the credential: its own API client, and MapLibre Native's own tile-fetching layer, which bypasses the app's client entirely (see "Confirm MapLibre Native's built-in PMTiles support" and "Shared basemap style consumption" in Phase 2). A cookie sitting in the app's own cookie jar doesn't automatically reach MapLibre Native's separate internal network stack; a bearer token injected via a per-request hook reaches both, uniformly:
  - **Android**: `org.maplibre.android.module.http.HttpRequestUtil.setOkHttpClient(...)` — supply an `OkHttpClient` built with a custom `Interceptor` that adds the header to every request MapLibre Native makes. Confirmed as a core-SDK API, not a React-Native-only shim, by reading `maplibre-react-native`'s own `TransformRequestInterceptor.kt`/`MLRNTransformRequestModule.kt`, which call exactly this.
  - **iOS**: `MLNNetworkConfiguration.sharedManager.delegate`, implementing `MLNNetworkConfigurationDelegate`'s `willSendRequest:` — same mutate-and-return shape as the web SDK's `transformRequest`, confirmed public/exported (`MLN_EXPORT`) in MapLibre Native's own `platform/darwin/src/MLNNetworkConfiguration.h`. This supersedes an older, fragile iOS mechanism (`MLNCustomHeaders`/`addCustomHeader`, method swizzling) with a known, unresolved upstream bug where the header silently failed to attach specifically on tile requests in release/TestFlight builds while working fine in dev — a plain delegate-protocol method isn't swizzling and isn't subject to that failure class.

  Both hooks are global to the app process (one interceptor/delegate for every request MapLibre Native makes, not scoped per source), so the interceptor scopes itself: it attaches the header only to requests whose URL starts with HoldMyTrack's own API origin. The basemap assets are unauthenticated, and in a CDN deployment they are a third party's origin — a live credential in someone else's access logs is worth one line of code to avoid. Both hooks run per-request rather than once at startup, so they read whatever token is current at call time — login/logout/refresh flow through without re-registering anything.

  **Built.** `currentUserID` now resolves the caller's session via a new `sessionIDFromRequest` helper — the `fitmap_session` cookie checked first (unchanged, browser path), falling back to `Authorization: Bearer <session-id>` — the same `sessions` table and expiry check either way, just a second place to read the id from. `currentDemoUserID` (the demo-account-claiming check inside `handleSignup`) and `handleLogout` were switched to the same helper: logout previously read `r.Cookie` directly, which would have silently no-op'd (cleared a cookie that was never set, left the session row live) for a bearer-only caller — now it actually revokes the session either way. `startSession` returns the new session id, and the four endpoints that call it (`signup`/`login`/`demo`/`reset-password`) now return it in the JSON body too, via a new `authResponseWithSession{authResponse, SessionToken}` wrapper — a browser client ignores the field (it already has the credential via `Set-Cookie`), a native client stores it and sends it back as `Authorization: Bearer <SessionToken>`. `handleMe` is unchanged (plain `authResponse`, no field to reissue). Password reset's existing `DELETE FROM sessions WHERE user_id = $1` revokes a bearer token exactly the way it already revoked a cookie, since both are just the same session row read two different ways; `Secure`/`SameSite` cookie attributes are moot for mobile, since mobile never exercises the cookie path at all.

  **Verified live** against a running `db`/`api` stack: signed up with no cookie jar, confirmed `session_token` in the response body; called `GET /v1/auth/me` and `GET /v1/activities` with only `Authorization: Bearer <token>` and no cookie, both `200`; confirmed no credentials, an empty `Bearer `, and a malformed `Authorization` header all still `401`; called `POST /v1/auth/logout` with only the bearer token and confirmed the token stopped working immediately afterward (not just cleared client-side); confirmed the existing cookie-only flow (signup → `GET /v1/auth/me` via cookie, no `Authorization` header at all) still works unchanged, and that `POST /v1/auth/demo` also returns `session_token`.

## Phase 1: Research & Verification

One throwaway app, one physical device, both platform questions answered together. Framed as due diligence rather than an open blocker: root `ROADMAP.md` notes that Samsung's own developer docs already state `EXERCISE_ROUTE` is unreachable, and this is "double-checking in case reality is better than documented". Both checks need the same device and the same permission plumbing, and the Samsung answer changes what Phase 3 has to build, so neither can wait until after the app exists.

- [x] **Health Connect route-access proof of concept** — `apps/android/poc-healthconnect`, measured on a Pixel 10a running Android 17 (API 37) against a Health Connect store fed by Fitbit.
  - **`READ_EXERCISE_ROUTES` is not programmatically requestable.** Requesting it alongside `READ_EXERCISE` and `READ_HEALTH_DATA_IN_BACKGROUND` grants the other two and silently omits it — it never even acquires a `USER_SET` flag. The user grants it at **Health Connect → the app → Additional access → Access exercise routes → Always allow**, a screen two levels below the app's main permission page and not linked from it. Phase 3's onboarding has to walk the user there explicitly; "grant permissions" is not a single flow.
  - **Foreground-only is real, and "Always allow" does not lift it.** With all three permissions granted, the same query over the same 46 sessions returned `23 route / 23 no-route / 0 consent-required` in the foreground and `0 / 23 / 23` in the background. Background access being granted changes nothing for routes.
  - **`NoData` and `ConsentRequired` are distinguishable, and both are stable.** 23 of the 46 sessions read as `NoData` in both runs — indoor workouts, which have no route to begin with — while the outdoor half flipped between geometry and `ConsentRequired` depending only on foreground state. So the two conditions never have to be conflated: a rejected sync can say "recorded indoors, no route" or "route not readable right now, sync again in the foreground" as the different things they are, rather than one generic "couldn't sync" message.
- [ ] **Empirical Samsung Health check** — not doable on the Pixel used above; needs a Galaxy Watch paired to Samsung Health.
  - On a real Galaxy Watch paired to Samsung Health, confirm whether route geometry is genuinely unreachable via Health Connect, or whether there is any supported route we have missed (`docs/VISION.md` §4.1's validation gate). If routes turn out to be readable, Android's product improves materially and Samsung Galaxy Watch stops being unsupported.

## Phase 2: Client Shell, Session & Map

Set up the application scaffolding and map rendering. Auth comes first within this phase, not later: every tile route is wrapped in `requireAuth` (`services/server/internal/httpapi/server.go`), so no user-specific tile renders without a live session.

- [x] **Project setup & scaffolding** — `apps/android/fitmap`, a Kotlin/Gradle project with MapLibre Native 13.6.1 drawing the API's style document full-screen. Its own build rather than a module beside `poc-healthconnect`, which is throwaway; see `apps/android/fitmap/README.md` for how to build it and point it at an API. `./gradlew :app:assembleDebug` packages it against the host SDK, and `./gradlew installDebug` puts it on an attached device.
  - **`minSdk` is 34, `targetSdk` 37**, decided separately as this item asks. 34 (Android 14) is where Health Connect became part of the platform: below it, Health Connect is a Play-installed APK the app must detect, route the user into installing, and re-check — a second provider state machine, on a configuration Phase 1 never measured routes against. HoldMyTrack ingests GPS sessions from a watch, so the devices that cut off are not the ones it serves. 37 is the newest platform and matches `compileSdk`, comfortably above Play's current requirement of 36; that requirement rises annually and is re-checked per release rather than read off this document.
  - The shell renders before any account exists, which is why it comes first: the style endpoint is unauthenticated and the basemap archive is a plain `pmtiles://` URL, so the map is on screen before there is a session to attach. Every *user* layer is behind `requireAuth` and is attached only once a session exists. Flavor follows the system day/night setting — `light` or `dark` of the five the API serves — rather than inventing a theme preference the design pass has not decided.
  - Failures surface on screen, not only in logcat: a style or tile fetch that 404s otherwise leaves a plausible-looking blank map with nothing to say what went wrong. That reasoning is what the session-verification step below extends — an expired credential is the same failure wearing the same blank face.
- [x] **Authentication & session persistence** — `SignInActivity` over `net/FitMapApi.kt`, with the credential held process-wide in `net/Session.kt`.
  Sign in, create an account, or start a demo account: the four endpoints that mint a session (`POST /v1/auth/signup|login|demo`, plus `logout`) all return `session_token`, which is stored in the app's private `SharedPreferences` and sent back as `Authorization: Bearer`. Not an encrypted store — the file is already unreadable by other apps, and what actually bounds a leaked token is that signing out deletes the row server-side. The server's own error text is shown verbatim rather than reworded, so the client can never disagree with it about what is acceptable.
  **A restored token is not trusted until the server confirms it.** A session revoked or expired while the app was closed would otherwise surface as a wall of 401s on tile requests, which appear only in logcat — on screen it is indistinguishable from an ordinary blank map. So startup waits on `GET /v1/auth/me` before attaching any layer, and a 401 (only a 401 — a dead network says nothing about the credential) drops the token and falls back to the signed-out basemap.
  **MapLibre Native's own tile requests carry the token because the app hands the SDK its own `OkHttpClient`** — `HttpRequestUtil.setOkHttpClient` in `FitMapApplication`, one client for the app's API calls and the map's tile fetching, one interceptor in one place. This is the whole reason the prerequisite above chose a bearer token over a cookie jar, and the three user layers rendering at all is the proof it works: every one of them is behind `requireAuth`.
  **Verified live** on a Pixel 10a against a running `db`/`minio`/`api`/`worker` stack: signed in and watched the map fly to the account's activity extent with tracks drawn; confirmed a wrong password shows the server's own "invalid email or password"; confirmed the demo button yields a working session with no email; killed and relaunched the app and confirmed the session survives a cold start with no sign-in screen; signed out and confirmed the layers disappear, the stored token is gone, and the same token then returns 401 from both `GET /v1/auth/me` and the tracks tile endpoint — a revocation, not a local clear; deleted a live session row out from under the app and confirmed the next cold start detects it and drops to signed-out rather than showing a blank map.
- [x] **MapLibre Native's built-in PMTiles support is real, and HoldMyTrack needs nothing else** — confirmed on a device against HoldMyTrack's own archive.
  The style document (`docs/ARCHITECTURE.md` §2.1) carries a `pmtiles://` source URL, answered on web by the pmtiles **JavaScript** protocol plugin (`apps/web/src/map/style.ts`). Mobile needs no equivalent: MapLibre Native has **built-in, native `pmtiles://` support** (Android 11.8.0, iOS 6.10.0), refined across later releases (range requests and a forced XYZ tile scheme in Android 11.8.8, tile-compression handling in 13.0.2, an ambient cache in 13.3.0). So neither of the two options once thought necessary here — a native PMTiles reader to write, or a server-side `{z}/{x}/{y}` endpoint over the archive — is needed, and the served style document is consumed unmodified.
  **Verified live**, to the standard Phase 1's checks set rather than from documentation: the app draws the Ohio extract from the unmodified served document, and MapLibre's own HTTP layer is seen issuing range reads against `ohio.pmtiles`. **The caching question resolves too, and in the useful direction**: MapLibre's docs say "PMTiles sources do not support offline pack downloads or caching," which pre-dates the 13.3.0 ambient cache — reading the app's `files/mbgl-offline.db` after a session found 40 cached range responses totalling 2.8 MB, keyed `ohio.pmtiles?_mlnRange=<start>-<end>`, so the archive's header, directories and tile bytes all persist to disk across launches. What that sentence still describes correctly is the *offline pack* half: `regions` stays empty, and a pmtiles source cannot be packaged for deliberate offline download. HoldMyTrack asks for ambient caching and not for offline packs, so the limitation that survives is not one it runs into. The headless export renderer's identical question (`docs/IMPLEMENTATION.md` §5.5) is answered along with this, if that renderer ends up on MapLibre Native rather than a browser.
- [x] **Shared basemap style consumption** — `GET /v1/map/style/{flavor}` straight into `Style.Builder().fromUri(...)`, nothing reimplemented.
  The document is consumed as served, archive URL included, so `apps/web/src/map/style.ts` stays the single definition of the style across web, mobile and the export renderer. Flavor follows the system day/night setting (`light` or `dark` of the five the API serves) rather than inventing a theme preference the design pass has not decided. Attribution needed no code: `MapView` renders MapLibre's own attribution control, which picks up the ODbL credit the document's `protomaps` source already carries — the check `docs/IMPLEMENTATION.md` §5.6 asks for on each mobile client, now done for Android.
- [x] **Map modes: Normal, Fog of War, Heatmap** — `map/MapOverlays.kt`, one toggle over the three layers.
  Fog and heatmap are the server-rendered 512px PNG rasters (`GET /tiles/v1/fog|heatmap/{z}/{x}/{y}`); Normal is the basemap plus the live PostGIS→MVT tracks layer (`GET /tiles/v1/tracks/{z}/{x}/{y}`) with both rasters hidden. One toggle rather than three checkboxes, because Fog and Heatmap also hide the track lines (`docs/IMPLEMENTATION.md` §4.2.2 — the raster already encodes where, and lines over it read as noise). All three go in beneath the basemap's first symbol layer, so place labels stay legible over the veil, and the rasters go in before the tracks so a cleared route shows *through* the fog rather than under it — the same ordering `apps/web/src/map/layers.ts` fixes for the same reasons.
  All three are attached once the stored session is verified rather than at style load: every one is behind `requireAuth`, and an unverified token would surface as a wall of 401s on tile requests. The map itself is only ever created with a session (see "Gate the map behind login" below).
  Tile URLs are unfiltered for now. The endpoints accept `from`/`to`/`types`/`exclude` and the web client drives them from its date-range picker and hidden set, neither of which exists on Android yet — those controls fall inside the design pass, and an omitted filter already means "no restriction" server-side, so the unfiltered URL is the whole history rather than a placeholder for something missing.
  **Verified live** on the device, one screenshot per mode against an account with three synced activities: Normal draws the tracks as crisp lines under the place labels; Fog covers everything in the white veil with only those routes cleared and the lines correctly hidden; Heatmap replaces the veil with the intensity glow, also with the lines hidden. **One real bug found only by looking at a real screen**: at `targetSdk` 37 the system draws every app edge to edge and ignores the old opt-out, so the bottom bar sat *under* the gesture navigation pill with the mode buttons half covered — fixed by adding the system-bar insets to the bar's own padding (`MainActivity.insetSystemBars`).

## Gate the map behind login — supersedes Phase 2's original signed-out-basemap design

Phase 2 above shipped the map rendering unconditionally, signed in or not: `MainActivity` draws the unauthenticated style document and clears the loading indicator regardless of session state, attaching the three user layers only once a session exists (`apps/android/docs/IMPLEMENTATION.md` §1.2). The reasoning recorded at the time — "a signed-out map is the basemap alone, which is a complete map rather than a broken one" — has been revisited and reversed: a bare basemap with no Fog of War, no tracks, no Activities panel is not actually a compelling demonstration of what HoldMyTrack does. The app already has a much stronger one — `SignInActivity` offers a no-signup Demo account one tap away (`docs/SPEC.md` FR-1.1, FR-2), which shows the real product `VISION.md` §8.2 calls "the ad." Web already works this way: `AuthGate` is the only thing a signed-out visitor sees, and `MapView` never mounts without a session (`docs/IMPLEMENTATION.md` §4.9, §4.13). This item brings Android in line with that, rather than the other direction (giving web Android's current anonymous-basemap behavior) — considered and rejected, since it would mean shipping a weaker first impression on both clients instead of a stronger one on neither.

- [x] `MainActivity` does not mount the map at all for a signed-out visitor — it checks `Session.isSignedIn` before `setContentView` and hands off to `SignInActivity`, mirroring web's `AuthGate` rather than rendering the basemap and gating only the user layers.
- [x] `SignInActivity` (sign in / sign up / start a demo) is the first screen whenever no session exists: on a signed-out launch, after sign-out, and when a stored token is rejected with a `401`. It is the root of its own task (`SignInActivity.open` clears the back stack), so Back leaves the app rather than revealing a map.
- [x] Phase 2's record above and `apps/android/docs/IMPLEMENTATION.md` §1.2 describe the gated app.
- [x] Closes the cross-client inconsistency `docs/IMPLEMENTATION.md` §4.13 and `docs/BRAINSTORM.md` used to track: both clients now land an anonymous visitor on the login/sign-up/demo screen, with no unauthenticated map on either.

## Phase 3: Health Connect Ingestion (Path 2)

Implement permissions, local tracking, and sync logic.

- [x] **Permission management & onboarding flow** — `SyncActivity` over `health/HealthConnect.kt`, a five-state walk-through rather than one "grant permissions" button.
  The states are: Health Connect missing, Health Connect needing an update, sessions not readable, routes not readable, and history capped — each with the one action that resolves it. `READ_EXERCISE` is an ordinary dialog. `READ_EXERCISE_ROUTES` cannot be requested at all, so the screen names the taps: Health Connect → HoldMyTrack → *Additional access* → *Access exercise routes* → *Always allow*. This screen is also registered for `ACTION_SHOW_PERMISSIONS_RATIONALE`, so Health Connect opens it as the app's own explanation — it leads with what is read and what for, which has to be true in both places.
  **Health Connect's own permission screen only offers "Exercise"** — one data type, confirmed on the device. That is the whole Play Console declaration (see Phase 6), and it is why heart rate is not read: a third data type for a product whose scope is outdoor GPS routes would widen the declaration for something the map does not draw.
  **Two platform limits found by running it, not by reading about it.** First, the platform publishes `ACTION_MANAGE_HEALTH_PERMISSIONS`, which takes a package name and would land the user directly on HoldMyTrack's page — but the activity behind it is guarded by `GRANT_RUNTIME_PERMISSIONS`, a signature permission, so an ordinary app launching it gets a `SecurityException` that kills the process. Confirmed twice over: the crash, then the resolver itself. `HEALTH_HOME_SETTINGS` is what a third-party app can open, which is why the instructions above start from Health Connect's home. Second, and more consequential — see the history item below.
- [x] **Health Connect serves only the last 30 days unless `READ_HEALTH_DATA_HISTORY` is granted** — found on the first real sync, not anticipated.
  The first sync returned exactly 30 days of sessions, and Health Connect's own screen said so in as many words: *"HoldMyTrack can read data added after August 17, 2026."* An app whose entire premise is the accumulated shape of where someone has been cannot work inside a 30-day window — a new user would sync a month and see almost nothing. So `READ_HEALTH_DATA_HISTORY` is declared and requested. It is **not a fourth data type**: it is a time window over the one type already declared, so the Play declaration is unchanged. It is also programmatically requestable, unlike the routes permission, so the app asks for it directly instead of sending the user hunting. Declining it is a real answer, so that state still offers to sync the last 30 days rather than refusing to work.
- [x] **Foreground sync run** — `sync/SyncRunner.kt`, driven from `SyncActivity` and cancelled in its `onStop`.
  Not a service, and the name in this roadmap was the misleading part: nothing here schedules itself or survives the app being backgrounded, because Phase 1 measured that routes written by other apps come back `ConsentRequired` in the background whatever is granted. `onStop` is the real foreground boundary, so the run is tied to that rather than to `onPause`, which a permission dialog also triggers.
  Reads sessions ascending and paged, classifies each one, batches the ones with geometry (25 activities or 20,000 points, well inside the endpoint's own 100-per-request ceiling) and posts them. Cancelling mid-run is safe by construction rather than by cleanup — see the watermark below.
- [x] **Sync cursor / watermark** — `sync/SyncCursor.kt`, and the rule it enforces is the narrow one §4.0 asks for.
  Every record gets one of two verdicts. **Terminal**: the server took it, already had it, permanently refused it, or it has no route and never will — the watermark may pass. **Blocking**: a route exists and could not be read (`ConsentRequired`), or the request failed — the watermark stops and the run stops with it. The watermark only moves at a confirmed batch boundary, never on optimism, which is what makes a cancelled or failed run simply resumable.
  **A position is an instant plus a set of ids, not an instant alone.** Health Connect's `TimeRangeFilter.after` is inclusive, so the record the cursor stands on is read again next run, and two sessions can genuinely share a start instant — excluding the instant would lose a sibling. Naming the ids already handled at exactly that instant is what skips those and nothing else. Kept per account, so two people on one device never inherit each other's position.
  **A route-less session is terminal, not a failure.** Half of this store's sessions have none, for the ordinary reason that a gym session or a rowing machine has no trajectory. Retrying them forever would wedge the watermark on records that will never change.
- [x] **Sync rejection feedback** — the run's own outcome, reported on the sync screen.
  Three things are kept apart rather than collapsed into one "couldn't sync": how many were synced or already present, how many were skipped for having no route (*"Skipped 32 recorded indoors — no route to map"* — an explanation, not an error), and which the server actually refused, each with the server's own reason. Phase 1's finding that `NoData` and `ConsentRequired` are distinguishable is what makes that possible, and conflating them would throw it away.
  This is the run just watched, not a history. The persistent, browsable version belongs to Phase 4's sync status dashboard, as this roadmap already routed it.
- [x] **Payload preparation** — `SyncRunner.prepare`, and `health/ExerciseTypes.kt` for the one part that was not mechanical.
  `external_id` is Health Connect's own record id, which is exactly what the endpoint's idempotency on `(user_id, source, external_id)` is designed for — a re-sent record is recognised rather than minted anew, which is what makes a repeated run cost traffic and not rows. Elevation is sent when a location carries it and omitted when not, since an unknown altitude is not sea level. Heart rate is never sent (see the permission item above).
  **Activity types are normalized onto the vocabulary already in the database, and that is a correctness fix rather than tidiness.** Health Connect calls a bike ride `biking`; a `.FIT` upload of the same ride lands as `cycling`. Left alone the two would be different activity types, which splits the Activities panel's TYPE facets *and* breaks cross-source deduplication, whose `dedupe_key` includes the activity type (`docs/IMPLEMENTATION.md` §4.6) — the exact collision Phase 4 exists to resolve. The table is written against the library's public constants rather than its `EXERCISE_TYPE_INT_TO_STRING_MAP`, which is `@RestrictTo` internal API.
- **Phase 4's "Sync API client" largely landed with this**, because Phase 3 could not be verified without it: `FitMapApi.syncActivities` posts the batches and returns the per-activity verdicts the watermark reads. What is left in Phase 4 is genuinely separate — the dashboard, cross-source dedup, and any retry policy beyond "the next run resumes".

**Verified end to end on a Pixel 10a**, against a Health Connect store fed by Fitbit and a live `db`/`minio`/`api`/`worker` stack:
- Walked all four onboarding states on a device that had never granted anything, including granting the routes permission by hand in Health Connect.
- First sync: **24 synced, 24 skipped as indoor, out of 48 read** — closely matching Phase 1's independent 23/23 out of 46 on the same device.
- Checked the rows server-side: `source = 'healthconnect'`, `external_id` the Health Connect record UUID rather than a content hash, `raw_payload_key` scoped `raw/{userID}/healthconnect/{externalID}.json`, every activity with a bbox, and `biking` correctly landed as `cycling`.
- **Watermark**: an immediate second sync read **0 sessions** — not "read one and skipped it", which is what proves the ids-at-cursor filter works and not just the instant.
- **History permission**: granting it took the same store from 48 sessions to 59 and the earliest activity from 18 August back to 15 August.
- **Idempotency on a full re-walk**: cursor reset, sync again — **24 already in HoldMyTrack, 3 new, 0 duplicates** (27 rows, 27 distinct `external_id`s).
- **A failed run loses nothing**: with the API unreachable the run read 38 sessions, failed at the first batch, reported *"Stopped early. Failed to connect"*, and left the watermark at **never** — no partial advance. Restoring the connection and syncing again recovered **all 27**.
- One layout bug found only on a screen: at this target SDK the action bar overlays a scrolling layout, so the sync and sign-in screens needed `fitsSystemWindows`.

## Phase 4: API Integration & Sync Progress

Connect the native application to the HoldMyTrack backend.

**Verified end to end** against a live `db`/`minio`/`api`/`worker` stack, with deduplication exercised through the sync endpoint from two different sources: one ride synced as `healthconnect`, the same ride again as `healthkit` four seconds later, and a third copy three seconds earlier carrying heart rate and elevation. One stayed live throughout while the other two were marked superseded, the richest copy took the place over when it arrived, a genuinely different ride 10% longer was left alone, and the heatmap tile came back **byte-identical** across all three — the strongest available evidence that a superseded activity contributes nothing, since that raster is additive and any leak would brighten it. Deleting the winner then left one live copy and one still superseded, with the tile unchanged.

- [x] **Sync API client** — `FitMapApi.syncActivities`, landed with Phase 3 because that phase could not be verified without it.
  Batches of 25 activities or 20,000 points, whichever comes first, well inside the endpoint's own 100-per-request ceiling. Resumable retry is not a retry loop: the watermark only moves over activities the server has confirmed, so an interrupted run is repeated rather than resumed from a saved position, and a repeat costs traffic rather than rows because the endpoint keys idempotency on the platform's own record id. Verified by pointing a run at an unreachable API and syncing again.
- [x] **Cross-source deduplication** (`docs/IMPLEMENTATION.md` §4.6, root `ROADMAP.md` Phase 2) — `services/server/internal/ingest/dedupe.go`, server-side work triggered by this phase.
  Android sync being the second ingest source is the point at which this stopped being optional: one ride can now arrive from a watch and from a file with two genuinely different `external_id`s, which the unique index cannot catch. Identity is fuzzy — same type, start within half a minute either way, distance within ~1% — and it is matched as a **window** around the incoming activity rather than equality on a pre-rounded bucket. That difference is not academic: measured on a real pair three seconds apart that landed either side of a minute boundary and so was never compared at all. Collisions keep the richest copy (geometry over none, then more stream channels) and mark the rest `superseded_by` rather than deleting them.
  **Every user-facing read excludes superseded rows** — list, summary, histogram, day pages, trends, graph stats, tracks tiles, and both fog and heatmap composites. The reads that deliberately do not are the receive-time idempotency checks, where an already-superseded row is still "already processed", and the per-id lookups behind editing and deleting, which have to keep working for a duplicate the user can see.
  **Two bugs found only by running it.** The richness comparison never decided anything, because `activity_streams.elevation_m` and `heartrate` are arrays and ingest writes one element per point — a track carrying no elevation still has a non-null array full of nulls, so every activity scored two channels; a channel now counts only if some element actually holds a reading. And deleting the copy that won released every copy it had displaced at once (`ON DELETE SET NULL`), leaving the ride live twice and visibly double-counted in the additive heatmap, so the delete path now re-ranks what it frees.
- [x] **Sync status & error dashboard** — `SyncStatusActivity`, reached from the sync screen.
  Reads `GET /v1/uploads`, which lists **ingest jobs** rather than syncs: a Health Connect session and an uploaded file are the same kind of job, so they share one history instead of the app inventing a notion of "a sync" the server has no record of. Rows show when the activity happened and how far it went once there is an activity to describe, the server's own error text in red when there is not, and the job's submission time while it is still processing. It re-reads every two seconds while anything is in flight and not at all once everything has settled, since a finished job will not change again.
  A second section answers the other half of the same question. With two ingest paths an activity can be missing because it failed *or* because it was already here from somewhere else, and only the first is a fault — so duplicates are listed separately, naming both sources, rather than being left to look like an error or like nothing at all.
  **Verified live** on the device against the running stack: a history of five jobs with dates and distances, a failed job rendered in red with the server's own message, and a duplicate reading *"cycling from HealthKit — already here from Health Connect, so it is not drawn twice"*. The failed row was produced by marking a job failed in the database, since the display is what was new here; every other row came from real ingest.

## Phase 5: UI Design & Implementation

The Android counterpart to the root roadmap's Phase 3, and the pass that turns four working screens into a designed app. What exists today is functional scaffolding, stated precisely rather than by impression: `app/src/main/res` holds four layout files and one `strings.xml` and nothing else — no `colors.xml`, no `dimens.xml`, no `themes.xml`, no drawables — the two themes in use are stock `Theme.AppCompat.DayNight` and its `NoActionBar` variant, and the only colors anywhere are five literals in the layouts (a `#CC000000` scrim twice, `#FFFFFF`, `#C62828`) and two in Kotlin.

**This phase does not decide what HoldMyTrack looks like.** Root Phase 3 produces the palette, the type choice and the icon set for the product as a whole and ends in an explicit freeze; this is the pass that lands that on Android. So most of the work below is blocked on that freeze, and the two items that are not — the toolkit decision and designing the filter controls — are marked as such.

- [ ] **Decide the UI toolkit.** The open decision this phase has to settle before anything else, because it determines what "apply the design tokens" even means. Decide it explicitly and record the reasoning here, the way `minSdk`/`targetSdk` were in Phase 2.
  - **Material 3 on the existing Views** (`com.google.android.material`) — keeps all four layouts and the `MapView` exactly as they are, and brings a real token system (color roles, a type scale, shape, elevation) to style against instead of hand-rolling one.
  - **Compose + Material 3** — declarative, and where the platform is going, but it is a rewrite of every screen Phases 2–4 built, and MapLibre's `MapView` has to be hosted through `AndroidView` interop rather than used directly.
  - **Plain AppCompat with hand-rolled tokens** — no new dependency; `colors.xml`/`dimens.xml`/`themes.xml` and a custom type scale written out by hand. Most control, and reimplements what a component library already provides.
  - What should settle it: how cleanly the freeze's output maps onto Material's token vocabulary, and whether the map screen's chrome — which sits over a GL surface — is better served by Views or by Compose interop. **Not blocked on the freeze**, and worth deciding early since it changes the cost of everything else here.
- [ ] **Adopt the design freeze's tokens.** Color, type scale, spacing and shape, expressed once and referenced, rather than the literals listed above. One thing not to fold in: `MapOverlays.TRACK_COLOR` is `#b07e2e` because that is what `apps/web/src/map/tracks.ts` paints — it belongs to the shared map style, not to the app's theme, and pulling it into a token set would quietly let the two clients' tracks drift apart.
- [ ] **An icon set.** There are no drawables at all today. Same standard the root phase sets for itself: one coherent set, not ad-hoc per-screen artwork.
- [ ] **An app icon and launcher identity.** The manifest declares no `android:icon`, so the app ships with the platform default — and that default is what a user actually meets it as, since it is how HoldMyTrack appears in Health Connect's own app list while they are being walked through granting permissions.
- [ ] **The four screens.** Map chrome (the bottom bar, and the Normal / Fog / Heatmap toggle that currently marks its active mode with bold text and an alpha change), sign-in, Health Connect onboarding, and sync history — whose rows are `TextView`s built in code because there was no component vocabulary to build them from.
- [ ] **Decide whether there is a theme preference.** The map flavor follows the system day/night setting and picks `light` or `dark` of the five the API serves, deliberately not inventing a preference this pass had not decided. Decide it: system-only, or a real setting — and if a setting, whether it offers all five flavors or only those two.
- [ ] **Filter controls** — the one item here that is new function rather than restyling, and **not blocked on the freeze**. All three tile endpoints accept `from`/`to`/`types`/`exclude`, and the web drives them from a date-range picker plus its eye-icon hidden set; Android sends none of them, so the map is always the whole history. Fitting that onto a phone is a design problem before it is an implementation one, which is exactly why it was left here.
- [ ] **Empty, loading and error states.** The map reports failure through a single scrim-backed `TextView` at the top; the sync screens report through a bold status line; failed history rows are red text. Honest enough to build against, not a finished treatment.
- [ ] **Accessibility.** No content descriptions anywhere, touch targets never checked against the 48dp minimum, and nothing tried at a large system font size or under TalkBack. Far cheaper inside this pass than retrofitted after it.
- [ ] **Real-device design review.** The root phase refuses to assume its mobile CSS is correct and insists on real-device testing; the same applies here, and with reason — Phases 2 through 4 each turned up a layout bug that only a screen revealed (mode buttons under the gesture pill, an action bar drawn over a scrolling layout, two identical buttons stacked on each other).
- [ ] **Design freeze for Android.** The milestone this phase produces: this is how the app looks. Matches the root phase's own explicit freeze rather than trailing off into open-ended polish.

## Phase 7: In-App GPS Recording

A new capability, not an extension of Path 2: the app becomes able to originate an activity itself — a plain start/pause/stop GPS recording for a casual walk, hike, or drive someone would not otherwise bother tracking — rather than only reading history that already exists somewhere else. `docs/VISION.md` §1.1 and §4.1 state the product boundary this has to respect: GPS only, no heart rate/cadence/power, no training metrics, explicitly not a fitness-tracker replacement. [ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md) settles the one architectural fork this phase would otherwise have to litigate on its own: a finished recording is submitted directly to `POST /v1/sync/activities` under its own `source` value, with no Health Connect round-trip — so this phase does not re-fight Phase 3's foreground-only battle, because there is no other app's data being asked for here.

This phase is independent of Phases 5/6 above and can proceed in parallel with either — it touches new screens and a new permission set that the design freeze (Phase 5) and the Play Store compliance pass (Phase 6) will each eventually need to account for, but neither blocks starting this one.

### Platform questions to settle before building

- [x] **Foreground service or plain background location? Decided: a declared foreground service.** `recording/RecordingService.kt` runs with `FOREGROUND_SERVICE_TYPE_LOCATION` and a persistent notification for as long as a recording is active, independent of `RecordingActivity`'s own lifecycle — confirmed on-device: backgrounding the app mid-recording left the notification up and GPS fixes still arriving.
- [x] **Permission scope: foreground-only location, or background location too? Decided: foreground-only, no `ACCESS_BACKGROUND_LOCATION`.** Only `ACCESS_FINE_LOCATION` is requested — a foreground service with a location type keeps GPS running through the screen turning off without it; background location is for access with *no* running foreground component, which this app never has while recording. Avoids the separate Play Store "prominent disclosure" burden entirely, matching §7's own reasoning for not declaring more than the product demonstrably uses.
- [x] **Local buffering strategy while a recording is in progress. Decided: an in-memory list inside `RecordingService`, deliberately not solving crash recovery.** Points are appended only while `RecordingState.RECORDING`, never while paused. The **crash/kill recovery** item below is still open and unchecked — this decision explicitly doesn't answer it, per the "still doesn't lose data to a plain Activity recreation" bar being enough for this pass.
- [x] **What "pause" actually means for a GPS-only recording. Decided: plain, user-initiated pause/resume, no auto-pause**, matching §1.1's own boundary. Confirmed on-device: the elapsed-time readout freezes exactly at the pause instant and resumes counting from there, not from wall-clock time, and the first fix after Resume is treated as a fresh baseline rather than bridging the paused gap into the distance total.

### Client work

- [x] **Recording screen**: `recording/RecordingActivity.kt` over `activity_recording.xml` — Record/Pause/Resume/Stop, Name/Type/Description fields (editable until Stop), and a live Time/Distance/Altitude/Speed readout. The time readout ticks every second off a `Handler`, independent of GPS fix arrival (`RecordingService.MIN_UPDATE_MS` is 3s) — a stopwatch that only redrew on a fix would visibly stall between them. Name and Description start empty and Activity Type starts `"unknown"` — no defaults invented beyond what the server itself already falls back to.
- [x] **`RecordingService`** (not `RecordingRunner` — a bound+foreground `Service`, not a coroutine run tied to one screen's lifecycle, since surviving the screen going off is the whole point): accumulates `LocationManager` fixes; on Stop, `RecordingActivity` saves the finished recording to the local store below rather than submitting it — see "Deferred sync" below for why that moved.
- [x] **Activity type is free text, not a closed set, picked through a searchable Type picker** — `recording/ActivityTypePicker.kt`, the Android counterpart of the web edit dialog's `ActivityTypePicker.tsx`: the account's existing types (server-side plus this device's unsynced recordings), most-used first with counts, filtered as you type, and an **Add "…"** row that saves any new text exactly as typed (up to 50 characters). Walk/hike/run/ride/drive (`recording/RecordingTypes.PRESETS`, `health/ExerciseTypes.kt`'s own output vocabulary) are listed even on an account that hasn't used them, so recordings stay on the shared vocabulary by default.
- [x] **Route silhouette per Recorded Activities row** — `recording/TrackSilhouetteView.kt` draws the stored points as a small line in the map's track colour, no basemap, so recordings can be told apart at a glance.
- [x] **Download any recording as GPX** — Edit mode's **Download GPX**, on every saved row including a synced, locked one, through the system's save screen (no storage permission). GPX because other tools open it and HoldMyTrack's own upload parses it back.
- [x] **Deferred sync — the client-side redesign this phase's second pass made.** Originally Stop submitted directly (ADR-0007's server-side decision is unchanged; only *when* the client calls it moved). Now: Stop only persists to `recording/db/RecordedActivityStore.kt`, a plain `SQLiteOpenHelper` table (`recorded_activities`: id, name, description, activity_type, started/distance/duration, a JSON points blob, sync status, created-at) — **not Room**: this project's Kotlin toolchain (AGP's built-in Kotlin, 2.4.0 at the time) was newer than any published KSP release, confirmed by actually trying to add `androidx.room:room-compiler` and hitting a plugin-resolution failure before falling back, not assumed from documentation. `RecordedActivityRecord.toSyncJson()` builds the exact §4.0.3 wire shape from a stored row when it's time to actually submit.
- [x] **`RecordedActivitiesActivity`** (new menu item, "Recorded Activities") — every local recording, newest first, filterable by sync status (not synced / queued / synced) and by activity type (rebuilt from whatever distinct types are on file). Rows are built in code, matching `SyncStatusActivity`'s own convention (§Phase 5 below: no component vocabulary exists yet to build a reusable row from).
- [x] **Sync checkbox, one per row** — unchecked (not synced) / checked (queued) / checked-and-disabled (synced, per the "locked after sync" decision: a synced row's local fields no longer matter, so there's nothing left to toggle). Toggling persists immediately and re-filters the list in place.
- [x] **Edit reuses the recording screen**, not a second layout — `RecordingActivity` launched with `EXTRA_RECORDING_ID` hides Record/Pause/Stop and shows a Save button instead, pre-filled from the stored row, stats shown static rather than ticking. Locked (fields disabled, Save hidden, a "Already synced — no longer editable" notice) once the row has synced, matching the checkbox's own lock.
- [x] **"Sync Now" (the existing Health Connect button, `SyncActivity.kt`) now also drains the local queue** — `flushRecordedQueue()` runs after the Health Connect pass (or after it throws — a dead network says nothing about whether local rows can still go out) in the same tap, submitting every queued row and marking each synced on `"enqueued"`/`"already_processed"`. A rejected or failed row stays queued and is retried automatically next run — no new "failed" status, matching the decided retry posture. The combined result renders as one summary (Health Connect's own lines, then a "Recorded activities: N synced[, M failed — will retry next time]" line, omitted entirely when nothing was queued this run).
- [x] **Delete, always available regardless of sync status** — a confirmation dialog (mirroring `docs/SPEC.md` FR-5.11's own "nothing is deleted until the user confirms") removes the row from the local store only. Deliberately not a mirror of the server's own activity delete: a synced row's real `Activity` stays on the server (nothing here captures its server-assigned id to delete it by), and the dialog says so for a synced row rather than implying a full purge. Decided explicitly rather than defaulted: the alternative (delete-everywhere for a synced row) was considered and set aside as a bigger change — it would need the sync response to hand back the created activity's id, which nothing today captures.
- [x] **Local store scoped per account — found missing by testing, not by inspection.** The table had no account column at all through the first two rounds of testing above; switching from a demo session to a real account on the same device surfaced one account's recordings under another's. Fixed: an `account` column scoped to `Session.email` on every query, the same per-account key `sync/SyncCursor.kt` already established for its own watermark, including that class's own precedent for a demo account sharing one shared empty-string key (harmless here too, since a demo account can never sync regardless — see the demo-gating item below). Schema bumped to version 2; `onUpgrade` drops and recreates rather than a hand-written migration.
- [x] **Demo accounts gated client-side on both Sync screens, matching the web's own pattern** — found missing (neither screen checked demo status at all) while verifying the item above, not planned ahead of time. `Session.isDemo` now hides Sync Now/the secondary button/the Health Connect permission flow behind an explanatory message on the Sync screen (History stays visible — reading isn't a mutation), and disables every sync checkbox with a banner on Recorded Activities, mirroring `ImportPanel.tsx`'s `readOnly`-plus-explanation treatment on the web rather than leaving a demo session to discover the block only from the server's raw `demo_read_only` rejection.
- [ ] **Discard/save-on-stop confirmation**, mirroring the deliberate-confirmation pattern `docs/SPEC.md` FR-5.11 already uses for deleting an activity — still not built, but materially lower-stakes now than when this item was first written: Stop only ever saves locally, nothing is sent anywhere until the user separately queues and syncs it, and Delete (above) now offers a way back out.
- [ ] **Crash/kill recovery**: if the app or OS ends the process mid-recording (not after Stop — a stopped, saved-locally row is already durable in SQLite), the next launch should offer to resume or discard whatever was buffered in memory, rather than silently losing it. Still open — the in-memory buffering the recording service uses doesn't survive a process death, only an Activity recreation (rotation, `onStop`/`onStart`) while the bound `Service` keeps running.

**Verified live on a Pixel 10a**, three passes: the original submit-on-stop flow (granted location + notification permissions from one combined prompt, recorded a short walk — Record → real GPS fixes with altitude/speed arriving every ~3s → Pause froze the clock → Resume continued it → Stop — confirmed the activity reached the server with the entered name and a real `distance_meters`, and rendered on the map afterward); then the deferred-sync redesign against the same stack: recorded a walk with a custom, free-text activity type; confirmed the row landed in Recorded Activities as not-synced with **no network request made at Stop**; edited its name/description/type pre-sync and confirmed the edit persisted; checked its sync box (queued); tapped the Sync screen's "Sync Now" and confirmed it synced alongside a Health Connect run in one combined summary; confirmed the checkbox became checked-and-disabled and Edit became read-only afterward. A real failure case surfaced by accident (the session had signed into the demo account, whose writes the server correctly refuses) and confirmed the retry behavior live: the row stayed queued and the summary read "N synced, 1 failed — will retry next time" rather than dropping it; a subsequent "Sync Now" on a real account synced it. A third pass verified Delete, the account-scoping fix, and demo gating together: deleted a synced row and confirmed its server-side `Activity` was untouched in Postgres; signed into the demo account and confirmed Sync Now/Open Health Connect were hidden with the read-only message and the checkbox rendered `enabled="false"`; recorded under the demo session; signed out and into a real account and confirmed the demo-authored row did **not** appear in that account's Recorded Activities list.

### Server-side prerequisite

- [x] **Allowlist the new `source` value** in `POST /v1/sync/activities` — `internal/httpapi/sync_activities.go`'s `syncSources` now accepts `"recorded"` alongside `"healthconnect"`/`"healthkit"`, per ADR-0007. No new endpoint, no schema migration. `parse.JSONActivity` also gained optional `name`/`description`, threaded through `ingest.Process`'s insert — the one ingest path that can title an activity at creation instead of needing a later edit (`docs/IMPLEMENTATION.md` §4.0.4). Verified against a live `db`/`api`/`worker` stack directly (not just through the app): posted a batch with a name and description, confirmed both persisted, confirmed idempotency and the allowlist rejection both still hold.
- [x] **Validate `activity_type` length too**, added once the client's type field became free text — `syncOneActivity` now checks it against `maxActivityTypeLen` (50, the `VARCHAR(50)` column's own bound), the same way `name`/`description` already were. Without it, a long custom type would have failed as a raw, unhandled column-width error deep in the worker instead of a clean rejection at the endpoint.
