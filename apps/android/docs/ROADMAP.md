# HoldMyTrack for Android — Roadmap

This document outlines the engineering and product roadmap for the native Android application. The Android app's primary responsibility is to serve as an on-device ingest path (Path 2, `docs/adr/0001-three-independent-ingest-paths.md`), reading platform health data via **Health Connect** and displaying the shared map interface using **MapLibre Native**. Phase 7 adds a second, unrelated way an activity can originate on this app: casual, GPS-only recording done directly in HoldMyTrack, submitted straight to the server rather than through Health Connect ([ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md), `docs/VISION.md` §4.1).

As stated in `apps/android/README.md`, the Android development environment is not containerized and runs directly on the host machine.

`apps/android/` holds two Gradle builds: `holdmytrack/`, the app itself, and `poc-healthconnect/`, the throwaway Phase 1 diagnostic that is deleted once its findings are all recorded here. Every server-side prerequisite the app depends on is built.

## Where this sits in the wider plan

Read `docs/ROADMAP.md` (Phase 2 — Mobile) first; this document expands one item of it and does not override it.

- **The toolchain is on the host, not in a container** (`apps/android/README.md`), and it is installed: the Android SDK at `/opt/homebrew/share/android-commandlinetools` with platform 37, build-tools 37 and `adb` under `platform-tools/`, alongside JDK 21, which the Android Gradle Plugin supports. `ANDROID_HOME` is not exported by default, so export it (or write `sdk.dir` into `local.properties`) before invoking `./gradlew`. There is no Android Studio, but an AVD now exists (`holdmytrack`, a Pixel 7 image on Android 16/API 36, under `emulator/`) — used for Phase 7's own verification (`apps/android/docs/SPEC.md` §9); FR-1 through FR-4's own verification record still names a physical device specifically, and that distinction is worth preserving rather than blurring the two.
- **Android ships first of the two mobile apps**, so the Path 2 contract is designed against the more constrained platform. Android defines the payload shape and the sync-cursor semantics that `POST /v1/sync/activities` accepts, and iOS inherits them.
- **The design freeze is Phase 3 of the root roadmap, after Mobile** (`VISION.md` §5.4). Every screen here is therefore built to work, with Phase 5 below as the pass that finishes them — so the app has no *final* palette, type scale or icon set yet, and that is a schedule, not an oversight. What it has in the meantime is the web's current tokens — palette, Inter and Fraunces, and the spacing, radius and type scales — and its Lucide icons, carried into Material 3 (Phase 5, "Adopt the design tokens"), so the two clients already read as one product ahead of the freeze. The visual design comes *from* that root pass rather than being decided again here: two clients that each invented their own palette and type scale would not read as one product.
- **Cross-source deduplication is part of this phase, not a later one.** Root `ROADMAP.md` calls it "unavoidable once a second ingest source exists, which mobile sync is" — built, `docs/IMPLEMENTATION.md` §4.6.

## Technical Foundations & Platform Constraints

Before implementing any UI or sync routines, we must design around two hard platform constraints. Both are already verified against platform and vendor documentation in `docs/IMPLEMENTATION.md` §4.0 — this section does not re-derive them.

1. **Foreground-Only Route Sync**
   - **Constraint**: `READ_EXERCISE_ROUTES` cannot be requested programmatically; the user grants it manually in Health Connect settings. Routes written by other apps cannot be read in the background — `ExerciseRouteResult.ConsentRequired` is returned even with "Always allow" granted.
   - **Decision**: Android sync is strictly **foreground-only** (`docs/IMPLEMENTATION.md` §4.0). We will not build background route sync. The specific trap this avoids is named there: a background sync "advances the watermark past records whose routes were never read", producing a history that is complete in every respect except the map — worse than no sync at all.

2. **Samsung Health Route-Geometry Limitation**
   - **Constraint**: Samsung Health writes summary data but does not expose GPS route geometry (`EXERCISE_ROUTE`) to other apps via Health Connect, so Galaxy Watch sessions never carry a route (`docs/VISION.md` §4.1, `docs/IMPLEMENTATION.md` §4.0).
   - **Decision**: HoldMyTrack only ingests activities that have a route — this is a deliberate product boundary (`docs/VISION.md` §1.1), not just a platform limitation to work around. A session with no geometry is rejected at sync time with a clear reason (`POST /v1/sync/activities` already does this — see the server-side prerequisites below), not persisted and not silently dropped. In practice this means **Samsung Galaxy Watch sync is unsupported**: every Samsung-sourced session arrives with no geometry and is therefore always rejected.
   - **Route-less activities are ordinary, and indoor exercise is why.** A gym session, a swim or a rowing machine has no trajectory by its nature — `docs/IMPLEMENTATION.md` §4.0.2 already meets the same case from the Takeout side and skips it there too. Measured on a real store (Phase 1 below), half the sessions had no geometry on exactly these grounds, and all of Samsung's do, regardless of activity type. HoldMyTrack's scope is outdoor GPS tracking, so these are skipped by design rather than represented — a gap to close later would only make sense for a product that also wants to be a general fitness tracker, which this one deliberately isn't.

## Phase 1: Research & Verification

One throwaway app, one physical device, both platform questions answered together. Framed as due diligence rather than an open blocker: root `ROADMAP.md` notes that Samsung's own developer docs already state `EXERCISE_ROUTE` is unreachable, and this is "double-checking in case reality is better than documented". Both checks need the same device and the same permission plumbing, and the Samsung answer changes what Phase 3 has to build, so neither can wait until after the app exists.

- [x] **Health Connect route-access proof of concept** — `apps/android/poc-healthconnect`, measured on a Pixel 10a running Android 17 (API 37) against a Health Connect store fed by Fitbit.
  - **`READ_EXERCISE_ROUTES` is not programmatically requestable.** Requesting it alongside `READ_EXERCISE` and `READ_HEALTH_DATA_IN_BACKGROUND` grants the other two and silently omits it — it never even acquires a `USER_SET` flag. The user grants it at **Health Connect → the app → Additional access → Access exercise routes → Always allow**, a screen two levels below the app's main permission page and not linked from it. Phase 3's onboarding has to walk the user there explicitly; "grant permissions" is not a single flow.
  - **Foreground-only is real, and "Always allow" does not lift it.** With all three permissions granted, the same query over the same 46 sessions returned `23 route / 23 no-route / 0 consent-required` in the foreground and `0 / 23 / 23` in the background. Background access being granted changes nothing for routes.
  - **`NoData` and `ConsentRequired` are distinguishable, and both are stable.** 23 of the 46 sessions read as `NoData` in both runs — indoor workouts, which have no route to begin with — while the outdoor half flipped between geometry and `ConsentRequired` depending only on foreground state. So the two conditions never have to be conflated: a rejected sync can say "recorded indoors, no route" or "route not readable right now, sync again in the foreground" as the different things they are, rather than one generic "couldn't sync" message.
- [ ] **Empirical Samsung Health check** — not doable on the Pixel used above; needs a Galaxy Watch paired to Samsung Health.
  - On a real Galaxy Watch paired to Samsung Health, confirm whether route geometry is genuinely unreachable via Health Connect, or whether there is any supported route we have missed (`docs/VISION.md` §4.1's validation gate). If routes turn out to be readable, Android's product improves materially and Samsung Galaxy Watch stops being unsupported.

## Phase 5: UI Design & Implementation

The Android counterpart to the root roadmap's Phase 3, and the pass that turns eight working screens into a designed app. Where it stands today, stated precisely rather than by impression: Material 3 on Views (the toolkit decision below), themed once in `res/values/themes.xml` from the web's design tokens (`services/server/internal/web/static/tokens.css`, shared by the server-rendered pages and the map app) carried over value for value — the palette in `colors.xml`, the spacing, radius and type scales in `dimens.xml`, Inter and Fraunces in `res/font` — light only like the web, and provisional until the freeze replaces the values. Layouts reference theme attributes, dimension tokens and Material widgets (outlined text fields, filled/outlined/text buttons, `MaterialAlertDialogBuilder` dialogs) rather than literals; the literals left are the record button's own translucent black-and-white drawables, which sit over the map rather than on a themed surface, and `MapOverlays.TRACK_COLOR` (below). Every screen is designed after its web counterpart ("The screens", below); the freeze still sets the final values.

**This phase does not decide what HoldMyTrack looks like.** Root Phase 3 produces the palette, the type choice and the icon set for the product as a whole and ends in an explicit freeze; this is the pass that lands that on Android. So most of the work below is blocked on that freeze, and the two items that are not — the toolkit decision and designing the filter controls — are marked as such.

- [x] **Decide the UI toolkit: Material 3 on the existing Views** (`com.google.android.material`, `Theme.Material3.Light`). Settled before the freeze, because it determines what "apply the design tokens" even means.
  - **Why not Compose.** By the time this was decided the app had seven layouts and two custom Views (`RecordButton`, `TrackSilhouetteView`), not the four screens this item was first written against, so Compose meant rewriting all of them before any styling could start. The map screen is the product, and MapLibre's `MapView` is a View: under Compose it would be hosted through `AndroidView` with its lifecycle forwarded by hand, friction on exactly the screen that matters most. Compose's real advantage — Google's new component work lands there first — pays off for an app that keeps growing screens, and this one is deliberately small (an ingest path, a map, casual recording).
  - **Why not hand-rolled tokens on plain AppCompat.** Material already has the vocabulary the freeze will produce — color roles, a type scale, shape — plus components that meet the 48dp touch target and behave under TalkBack by default, which the Accessibility item below would otherwise have to rebuild. Measured on the emulator, that holds even where a style zeroes a button's insets: the map's mode buttons, which do, still come out 48dp tall.
  - **It doesn't close Compose off.** Views and Compose interoperate both ways (`ComposeView` in a layout, `AndroidView` in Compose), so a later move could go screen by screen, and Material 3's color and type roles map almost one-to-one onto Compose's `MaterialTheme`.
  - **Dynamic color is deliberately not applied.** Material You would replace the palette with one derived from the user's wallpaper; HoldMyTrack's look is a brand, not a system accent.
- [x] **Adopt the design tokens.** Color, type, spacing and shape, expressed once and referenced — adopted from the web's current `tokens.css` ahead of the freeze, so the freeze itself is a value swap in `res/values` (`apps/android/docs/IMPLEMENTATION.md` §1.3). Color in `colors.xml`, onto Material's color roles; the spacing, radius and type scales in `dimens.xml`, onto layouts' padding and margins, Material's corner sizes, and its type roles; Inter for text and Fraunces for screen titles, with Source Serif 4 for Russian titles as on the web, bundled in `res/font` trimmed to Latin and Cyrillic (about 630 KB). Elevation isn't carried: the web's shadows are CSS box-shadows, and the app's only raised surfaces are Material's own. One thing not to fold in: `MapOverlays.TRACK_COLOR` is `#b07e2e` because that is what `apps/web/src/map/tracks.ts` paints — it belongs to the shared map style, not to the app's theme, and pulling it into a token set would quietly let the two clients' tracks drift apart.
- [x] **An icon set.** Lucide, the web's set (root `docs/IMPLEMENTATION.md` §4.17), as vector drawables at the web's version, replacing glyphs each drawn for one use and a platform icon (`apps/android/docs/IMPLEMENTATION.md` §1.3): `ic_menu` (the burger, which had been a "☰" character), `ic_locate_fixed` (Find my location), `ic_chevron_down` (the Type field), `ic_pause`/`ic_play`/`ic_square` (the record button and its notification), and `ic_circle_dot` (the recording notification's status-bar icon, which was the platform's `ic_menu_mylocation`). The idle record button's solid red dot stays outside the set on purpose. Same standard the root phase sets for itself: one coherent set, not ad-hoc per-screen artwork.
- [x] **An app icon and launcher identity.** An adaptive icon (`res/mipmap-anydpi/ic_launcher.xml`): the HoldMyTrack logo as the foreground, sized to stay inside every mask's safe zone, on the web app's cream background, plus a monochrome layer (the logo's dark outline strokes) for Android 13+ themed icons. It matters beyond the launcher: it is how HoldMyTrack appears in Health Connect's own app list while a user is granting permissions.
- [x] **The screens.** Each designed after its web counterpart, one commit per screen and each checked on the emulator in English and Russian (`apps/android/docs/IMPLEMENTATION.md` §1.3 and each screen's own section): the map chrome as three panels of the web's `.map-mode-toggle` kind; sign-in and "check your email" as the web's auth card (`signin.html`, `verify-pending.html`), with Google's and Facebook's brand buttons; Health Connect onboarding and sync history after the web's Sync tab — status and results in notice boxes, history rows from a row layout instead of text built in code; Recorded Activities after the Activities panel, with drop-down filters and Lucide pencil and trash-2 row actions; the Edit/Save form after the web's edit window, with the web's confirm dialog for every dialog; and Profile after the web header's account menu. What's left belongs to other items: the map's own failure scrim (Empty, loading and error states) and the freeze's final values.
- [x] **Decide whether there is a theme preference.** Decided: no preference — the system's day/night setting is the only input, as now. The map takes `light` or `dark` of the five flavors the API serves from it, and the app's own chrome stays light, like the web's, so under the system dark setting a dark map sits under light controls; that is accepted rather than fixed with a dark palette invented here ahead of the freeze. A dark chrome theme, or a real setting (and whether it would offer all five flavors), comes back only if root Phase 3's freeze gives the product a dark palette — on the web as much as here.
- [ ] **Filter controls** — the one item here that is new function rather than restyling, and **not blocked on the freeze**. All three tile endpoints accept `from`/`to`/`types`/`exclude`, and the web drives them from a date-range picker plus its eye-icon hidden set; Android sends none of them, so the map is always the whole history. Fitting that onto a phone is a design problem before it is an implementation one, which is exactly why it was left here.
- [x] **Empty, loading and error states.** The map's black status strip — drawn under the chrome row, showing only a raw URL and MapLibre's error, with no way out — is replaced by one notice panel under the chrome, the map chrome's own panel after the web's on-map banner (`.version-banner`): a message, an optional small-print detail, and one action (`apps/android/docs/IMPLEMENTATION.md` §1.2). It carries four states, most important first: the map couldn't load (with the origin and error in small print, and Try again reloading the style); the server couldn't be reached while checking a restored session, which used to go only to logcat (Try again re-checks); "Checking your session…" when that check takes more than 600ms; and an empty map for an account with nothing on it yet, pointing at Sync and re-checked on every return until something arrives. Sync history reads "Loading…" until its first answer. The screens' own states were already designed in "The screens": notice and error boxes, the empty hints, the failed rows in red. Checked on the emulator, English and Russian.
- [ ] **Accessibility.** No content descriptions anywhere, touch targets never checked against the 48dp minimum (the map chrome's are 48dp, measured), and nothing tried at a large system font size or under TalkBack. Far cheaper inside this pass than retrofitted after it.
- [ ] **Real-device design review.** The root phase refuses to assume its mobile CSS is correct and insists on real-device testing; the same applies here, and with reason — Phases 2 through 4 each turned up a layout bug that only a screen revealed (mode buttons under the gesture pill, an action bar drawn over a scrolling layout, two identical buttons stacked on each other).
- [ ] **Design freeze for Android.** The milestone this phase produces: this is how the app looks. Matches the root phase's own explicit freeze rather than trailing off into open-ended polish.

Prepare the app for testing and store publication.

- [ ] **Physical device / Health Connect testing**
  - End-to-end testing on a physical device with the Health Connect toolbox on the host.
- [ ] **Play Store Health Connect data-type declarations**

These are not Android work, but shipping the app without them is not an option.

## Phase 7: In-App GPS Recording

A new capability, not an extension of Path 2: the app becomes able to originate an activity itself — a plain start/pause/stop GPS recording for a casual walk, hike, or drive someone would not otherwise bother tracking — rather than only reading history that already exists somewhere else. `docs/VISION.md` §1.1 and §4.1 state the product boundary this has to respect: GPS only, no heart rate/cadence/power, no training metrics, explicitly not a fitness-tracker replacement. [ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md) settles the one architectural fork this phase would otherwise have to litigate on its own: a finished recording is submitted directly to `POST /v1/sync/activities` under its own `source` value, with no Health Connect round-trip — so this phase does not re-fight Phase 3's foreground-only battle, because there is no other app's data being asked for here.

This phase is independent of Phases 5/6 above and can proceed in parallel with either — it touches new screens and a new permission set that the design freeze (Phase 5) and the Play Store compliance pass (Phase 6) will each eventually need to account for, but neither blocks starting this one.

### Client work

- [x] **One-tap recording from the map** — a translucent record button bottom-centre on `MainActivity`: tap starts, tap pauses/resumes, a two-second hold (with a countdown ring, `RecordButton`) stops. Nothing is asked while recording (no name, type or description); permissions are requested on the first tap. While recording, the map shows only the live track (`MapOverlays.setRecording`/`updateLiveTrack`) with the mode toggle hidden and the camera following the latest fix. A recording under one minute of moving time is discarded on Stop. Replaced a "GPS Logger" menu screen with its own Record/Pause/Stop and Name/Type/Description form, which took too many steps to start a recording on the way out the door.
- [x] **`RecordingService`** (not `RecordingRunner` — a bound+foreground `Service`, not a coroutine run tied to one screen's lifecycle, since surviving the screen going off is the whole point): driven by `ACTION_START`/`ACTION_TOGGLE`/`ACTION_STOP` intents from both the map button and its own notification, whose Pause/Resume and Stop actions and live stats (chronometer, distance, speed, altitude) make it controllable with no screen open. On Stop it saves the recording to the local store below itself, with the account's last-used type (`RecordingTypes.lastUsed`), rather than submitting it — see "Deferred sync" below.
- [x] **Activity type is free text, not a closed set, picked through a searchable Type picker** — `recording/ActivityTypePicker.kt`, the Android counterpart of the web edit dialog's `ActivityTypePicker.tsx`: the account's existing types (server-side plus this device's unsynced recordings), most-used first with counts, filtered as you type, and an **Add "…"** row that saves any new text exactly as typed (up to 50 characters). Walk/hike/run/ride/drive (`recording/RecordingTypes.PRESETS`, `health/ExerciseTypes.kt`'s own output vocabulary) are listed even on an account that hasn't used them, so recordings stay on the shared vocabulary by default.
- [x] **Route silhouette per Recorded Activities row** — `recording/TrackSilhouetteView.kt` draws the stored points as a small line in the map's track colour, no basemap, so recordings can be told apart at a glance.
- [x] **Download any recording as GPX** — the Edit screen's **Download GPX**, through the system's save screen (no storage permission). GPX because other tools open it and HoldMyTrack's own upload parses it back.
- [x] **Deferred sync — the client-side redesign this phase's second pass made.** Originally Stop submitted directly (ADR-0007's server-side decision is unchanged; only *when* the client calls it moved). Stop only persists to `recording/db/RecordedActivityStore.kt`, a plain `SQLiteOpenHelper` table (`recorded_activities`: id, name, description, activity_type, started/distance/duration, a JSON points blob, sync status, created-at) — **not Room**: this project's Kotlin toolchain (AGP's built-in Kotlin, 2.4.0 at the time) was newer than any published KSP release, confirmed by actually trying to add `androidx.room:room-compiler` and hitting a plugin-resolution failure before falling back, not assumed from documentation. `RecordedActivityRecord.toSyncJson()` builds the exact §4.0.3 wire shape from a stored row when it's time to actually submit.
- [x] **`RecordedActivitiesActivity`** (menu item "Recorded Activities") — every recording on the device not yet synced, newest first, filterable by sync status (not synced / queued) and by activity type (rebuilt from whatever distinct types are on file). Rows are inflated from `item_recorded_activity`, designed in Phase 5 after the web's Activities panel rows.
- [x] **Sync checkbox, one per row** — unchecked (not synced) / checked (queued); disabled while the session is a demo (an earlier `"unknown"`-type gate went when cross-source dedup moved to time overlap). Toggling persists immediately and re-filters the list in place.
- [x] **Edit** — `RecordingActivity` launched with `EXTRA_RECORDING_ID`: Name, Type (the picker above), Description, the recording's time and distance, Save and Download GPX. Saving a real type also makes it the type new recordings start with, so only an account's first recording needs an Edit before it can be queued.
- [x] **"Sync Now" (the existing Health Connect button, `SyncActivity.kt`) now also drains the local queue** — `flushRecordedQueue()` runs after the Health Connect pass (or after it throws — a dead network says nothing about whether local rows can still go out) in the same tap, submitting every queued row and deleting each from the device on `"enqueued"`/`"already_processed"` — from then on it lives on the server. A rejected or failed row stays queued and is retried automatically next run — no new "failed" status, matching the decided retry posture. The combined result renders as one summary (Health Connect's own lines, then a "Recorded activities: N synced[, M failed — will retry next time]" line, omitted entirely when nothing was queued this run).
- [x] **Delete** — a confirmation dialog (mirroring `docs/SPEC.md` FR-5.11's own "nothing is deleted until the user confirms") removes the row from the local store. Every row here is unsynced, so this discards the only copy, and the dialog says so.
- [x] **Local store scoped per account — found missing by testing, not by inspection.** The table had no account column at all through the first two rounds of testing above; switching from a demo session to a real account on the same device surfaced one account's recordings under another's. Fixed: an `account` column scoped to `Session.email` on every query, the same per-account key `sync/SyncCursor.kt` already established for its own watermark, including that class's own precedent for a demo account sharing one shared empty-string key (harmless here too, since a demo account can never sync regardless — see the demo-gating item below). Schema is at version 3: from version 1 `onUpgrade` drops and recreates rather than a hand-written migration; version 3 deletes rows left with the old `synced` status and keeps unsynced ones.
- [x] **Demo accounts gated client-side on both Sync screens, matching the web's own pattern** — found missing (neither screen checked demo status at all) while verifying the item above, not planned ahead of time. `Session.isDemo` now hides Sync Now/the secondary button/the Health Connect permission flow behind an explanatory message on the Sync screen (History stays visible — reading isn't a mutation), and disables every sync checkbox with a banner on Recorded Activities, mirroring `ImportPanel.tsx`'s `readOnly`-plus-explanation treatment on the web rather than leaving a demo session to discover the block only from the server's raw `demo_read_only` rejection.
- [x] **Save screen on stop** — stopping opens `RecordingActivity` as a "Save recording" screen (type pre-filled from the last used, Discard with confirmation in place of Download GPX); the row is already stored, so Back keeps it.
- [ ] **Crash/kill recovery**: if the app or OS ends the process mid-recording (not after Stop — a stopped, saved-locally row is already durable in SQLite), the next launch should offer to resume or discard whatever was buffered in memory, rather than silently losing it. Still open — the in-memory buffering the recording service uses doesn't survive a process death, only the UI going away (rotation, backgrounding, swiping the app out of recents) while the foreground `Service` keeps running. More pressing now that recording has no screen of its own to watch it by.

**Verified live on a Pixel 10a**, three passes: the original submit-on-stop flow (granted location + notification permissions from one combined prompt, recorded a short walk — Record → real GPS fixes with altitude/speed arriving every ~3s → Pause froze the clock → Resume continued it → Stop — confirmed the activity reached the server with the entered name and a real `distance_meters`, and rendered on the map afterward); then the deferred-sync redesign against the same stack: recorded a walk with a custom, free-text activity type; confirmed the row landed in Recorded Activities as not-synced with **no network request made at Stop**; edited its name/description/type pre-sync and confirmed the edit persisted; checked its sync box (queued); tapped the Sync screen's "Sync Now" and confirmed it synced alongside a Health Connect run in one combined summary; A real failure case surfaced by accident (the session had signed into the demo account, whose writes the server correctly refuses) and confirmed the retry behavior live: the row stayed queued and the summary read "N synced, 1 failed — will retry next time" rather than dropping it; a subsequent "Sync Now" on a real account synced it. A third pass verified the account-scoping fix and demo gating together: signed into the demo account and confirmed Sync Now/Open Health Connect were hidden with the read-only message and the checkbox rendered `enabled="false"`; recorded under the demo session; signed out and into a real account and confirmed the demo-authored row did **not** appear in that account's Recorded Activities list.

**Verified on an emulator** (the `fitmap` AVD, local stack, GPS fed with `adb emu geo fix`) for the one-tap flow: first tap raised both permission prompts then recorded; live track with the mode toggle hidden; pause from the button and Stop from the notification; a ~20 s recording dropped; recording survived swiping the app out of recents and the track redrew on reopen; set the first recording's type in Edit, queued and synced it — a `walking` activity appeared server-side and the local row was deleted; the next recording saved as `walking` with no Edit; a version-2 database with a `synced` and a `queued` row upgraded to only the queued row.

### Play Store / compliance implications (feeds Phase 6, not resolved here)

- [ ] A live-location feature is a distinct Play Console review surface from Health Connect's data-type declarations (Phase 6) — location permissions have their own policy requirements (a prominent in-app disclosure before the first request, a stated retention/use case) that Phase 6's existing Health Connect-focused checklist does not cover and will need extending for.
