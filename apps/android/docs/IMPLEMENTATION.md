# HoldMyTrack for Android: Implementation

> **Scope note.** This document covers each file's own implementation detail for the Android app — the app shell, auth, map overlays, Health Connect sync, in-app GPS recording, and the sync status screen. See `apps/android/docs/ARCHITECTURE.md` first for the app's shape and the stack this runs on, and `docs/IMPLEMENTATION.md` for the server-side schema and pipeline every call here eventually reaches. The app's local persistence is two `SharedPreferences` files, covered in place below, plus one SQLite database (§7) for recordings pending sync.

---

## 1. App Shell & Lifecycle

### 1.1 `HoldMyTrackApplication`

Process-level setup, in a fixed order that matters: `Session.init(this)` before anything reads a stored token; `MapLibre.getInstance(this)` to load the native library and install the module provider a `MapView`'s constructor asks for immediately; then `HttpRequestUtil.setOkHttpClient(HoldMyTrackApi.client)`, replacing MapLibre Native's own HTTP stack with the app's shared client. This last call is load-bearing and has to happen in `Application.onCreate`, not an Activity's — the map SDK may issue a request as soon as a `MapView` exists, and installing the client any later means some requests already went out through the SDK's default, tokenless client.

### 1.2 `MainActivity` and `MapFragment`

`MainActivity` is the main window and `MapFragment` is the map in it, with the state that governs what's drawn on it.

- **Never mounted without a session, or for an unconfirmed email.** `MainActivity.onCreate` checks `Session.isSignedIn` and then `Session.emailVerified` before `setContentView`, and hands a signed-out launch off to `SignInActivity.open` (an unconfirmed one to `VerifyEmailActivity.open`, §2.4) and finishes — no layout, no fragment, no `MapView`, no style request — mirroring web's `AuthGate` (`docs/IMPLEMENTATION.md` §4.13). Otherwise it adds `MapFragment` to `activity_main`'s one `FragmentContainerView` — only on a first create, since a recreation (rotation, theme, language) restores the fragment with its saved state — and hands every `onNewIntent` on to it ([ADR-0033](../../../docs/adr/0033-android-bottom-navigation-single-activity.md)).
- **`MapFragment` forwards MapLibre's lifecycle from its own.** Its layout is `fragment_map`; `onViewCreated` builds the map and its chrome, `onStart` through `onStop` and `onSaveInstanceState` forward to the `MapView` as an Activity would, and `onDestroyView` destroys it. Its permission launchers are registered as the fragment's own, the Edit window's Back callback is tied to its view's lifecycle, and the recording service is bound with the fragment's context.
- **The bottom bar is `MainActivity`'s** (`activity_main`: the tab's `FragmentContainerView` above a `BottomNavigationView` — `menu/bottom_nav`, styled `Widget.HoldMyTrack.BottomNav`, every label shown, the selected tab's icon on an `hmt_accent_container` pill). `showTab` hides the other tabs' fragments and shows its own, adding it the first time — `MapFragment` for Map and Stories, `SyncFragment`, `YouFragment` — with `commitNow`, so each tab keeps its state, the map's camera and layers included. Stories is the map with its panel on the Stories tab (`MapFragment.showStories`), and the panel reports its tab back (`onPanelTabChanged`), so the bar follows a tab chosen in the panel itself; Map from Stories puts the panel back on Activities (`showActivities`). The tab is saved across a recreation, and Back on any tab but Map goes to Map (`backToMap`). The bar pads itself clear of the gesture bar, and an insets listener on the container zeroes the navigation-bar inset the tabs see. The same listener pads the container by the left and right navigation-bar and display-cutout insets — a landscape phone's three-button bar, its camera — and zeroes those too, so no tab's chrome sits under them and none has to pad itself. Its middle item is an empty, disabled slot hidden from TalkBack; the record button sits over it, raised 14dp — the frame reaching up over the tab by as much, so the raised part takes touches — and `MapFragment` drives it (§7.1). Sync carries a Material `BadgeDrawable` (`setSyncWaiting`, `hmt_danger` behind the count, read out through the `sync_waiting` plural) with the recordings waiting: `refreshSyncBadge` counts them (`RecordedActivityStore.count`, `DatabaseUtils.queryNumEntries`, no points read) on every `onResume` — a Stop opens the Save screen over the app, so coming back from it is one — and `SyncFragment.updateSyncNow` sets it whenever its rows change; none for the demo account. `onNewIntent` shows Map for the notification's Stop and a View on map (`showMap`), the tab `openTab` names (Upload's "See Sync"), and hands every intent on to the map.
- **`syncSession()` is the single place session state and map state are reconciled**, called from `onResume` and once after the style finishes loading. It: routes to `SignInActivity` if the session is gone (a stored token the server just rejected with a `401`); calls `HoldMyTrackApi.verifySession` if a token is stored but not yet `Session.verified`; routes to `VerifyEmailActivity` if that check found the email unconfirmed; otherwise shows the mode toggle and attaches the user layers (`MapOverlays.attach`) once. The basemap style itself loads as soon as the map is ready, before verification finishes — it is unauthenticated (`docs/ARCHITECTURE.md` §2.1) — but the user layers wait for a verified token.
- **`verifying` is a re-entrancy guard**, not a cache — `onResume` fires on every return to this screen, including from the sign-in screen, so without it a slow verify request could be started twice.
- **The map says what's wrong in one notice under the chrome** (`map_notice`, inside `top_chrome` with the chrome row, so it sits below the row however tall that gets). `showNotice(kind, text, detail, failed, action)` fills it; `Notice` orders the four kinds by importance — `MAP_FAILED`, `UNREACHABLE`, `CHECKING`, `EMPTY` — and a less important one never replaces a more important one that is up, while `hideNotice(kind)` only takes down that kind. `MAP_FAILED` comes from MapLibre's `didFailLoadingMap` (origin and error in the detail line; Try again calls `loadStyle()`, which clears `overlaysAttached` since a new style has none of the app's layers). `UNREACHABLE` is a non-`401` failure of `verifyStoredSession` (Try again re-runs it). `CHECKING` is posted 600ms after a check starts (`CHECKING_DELAY_MS`) and removed when it answers, so a fast check never flashes. `EMPTY` is `frameActivities` getting a successful answer with no bounding box, for a non-demo account; `onResume` re-runs the framing while it's up, so returning from Sync with something new both takes it down and frames the camera. It steps aside while recording (`updateNoticeVisibility`). The compass is pushed below the notice while one is up. Replaced a black status strip that sat under the chrome row, showing the API origin and MapLibre's raw error with no way to retry, and a session failure that only reached logcat. Checked on the emulator, English and Russian: a new account's empty notice, then an upload and a return from Sync clearing it and framing the walk; a cold start with the port forward removed (`UNREACHABLE`); the same with MapLibre's cache (`files/mbgl-offline.db`) deleted as well (`MAP_FAILED`), and Try again recovering once the forward was back.
- **Only a `401` from `verifySession` clears the session.** Any other failure (`IOException`, a stopped dev stack) is logged, shown as the `UNREACHABLE` notice and otherwise left alone; the same restored token is tried again on the next resume or on Try again. This is the one piece of error-handling logic in the whole app that discriminates by HTTP status rather than treating "the request didn't succeed" as one bucket.
- **A group is framed along the shortest arc of longitude** (`map/BoxUnion`, the web's `unionBBox`, root `docs/IMPLEMENTATION.md` §4.7), east past 180 for one across the antimeridian, which `LatLngBounds.from` takes as it is. `BoxUnion.viewEdges` turns a view the map reports more than 180° wide, at Show in this area's zooms, into the short way round before `GET /v1/spots`.
- **`frameActivities()` runs once per process, guarded by `framed`**, which goes into the saved state: after a recreation the camera MapLibre restored stands, neither framed again nor replaced by the opening world view (`restoringCamera`). It reads `GET /v1/activities` (`HoldMyTrackApi.latestActivityBounds`), takes the most recently started drawn row's `bbox` — the web's opening view, `docs/SPEC.md` FR-4.5 — and `flyTo` animates the camera to fit it, capped at zoom 15. The cap exists because a single very short, or heavily clipped by a Private location (`docs/SPEC.md` FR-8.1), activity has a near-zero bounding box — fitting the camera to that literally would zoom in past the basemap's own z14 data onto an empty gray tile. `flyTo` keeps at least 96dp of map between its top and bottom padding (`MIN_FRAME_SPAN_DP`), taken from the top row's side first: on a landscape phone the row and the sheet left none, and the fit fell back to the whole world.
- **`insetSystemBars()` exists because of a bug found only on a real screen**, not from documentation: at `targetSdk` 35+ the system draws every app edge-to-edge and ignores the old opt-out, so a bottom bar laid out with ordinary padding sat *underneath* the gesture-navigation pill, with the mode-toggle buttons half covered. The fix adds the system-bar inset to each view's own existing padding (not replacing it) and returns the insets unconsumed, so nothing else downstream misses them.
- **MapLibre's `MapView` owns a native renderer and a GL surface**, so every one of `onStart`/`onResume`/`onPause`/`onStop`/`onSaveInstanceState`/`onLowMemory`/`onDestroy` forwards to the equivalent `mapView.on*` call. Missing any one of these is a leaked surface or a crash on rotation, not a subtle bug — this is why the full set is present even though several of them are otherwise empty boilerplate.
- **The top row is one full-width `top_bar`**: a weighted column at the start — the mode toggle's weighted scroll container, the recording's status card (§7.1) in its place while recording, and Show in this area under them — then `map_rail` at the end, a column of two round panels, Layers over Find my location, 8dp apart. The Edit window and the Private location editor open just under `top_bar`, over where the rail would be, so `renderRail` hides the rail while either is open (with `renderModeBar` hiding the toggle, the row is then empty), and dismisses the Layers menu (`PrivateLocationEditor`'s `onEditorClose` tells it when that editor goes). The row is not clickable, so a touch in the gaps still reaches the map. MapLibre's compass also lives top-end, so `applyCompassMargin` places it below the lower of `top_bar` and the notice (re-run on `top_chrome`'s layout changes).
- **The Layers menu is `map/LayersMenu`**, the web's `ui/OverlaysMenu.tsx`: `layers_button`, a `MapIcon.Toggle` button with `ic_layers`, in its `MapPanel` (`layers_panel`) at the top of the rail, which is `gone` until `renderModeBar` finds the session ready, and then stays through a recording, unlike `mode_bar`. `MapIcon.Toggle` is `MapIcon` made checkable with the mode buttons' `map_mode_bg`/`map_mode_text` tints, and `render` checks it while any path or place is picked and they're shown — also right after each tap, since a checkable `MaterialButton` flips itself on click. The count of paths and places picked is `layers_count`, an accent pill (`bg_layers_count`) over the panel's top-end corner, `gone` at zero and at 0.55 alpha while they're hidden; the button's content description carries it too. A tap on the button opens `popup_layers` under the panel, lined up with its end edge and 6dp below it, in a focusable `PopupWindow` at a fixed 224dp (the web panel's 14rem, so the Tracks explanation wraps rather than widening it), inflated afresh each time, so the explanation starts closed. Its first row is `layers_master`, a `MaterialSwitch` that shows or hides every pick at once: `map/MapLayersSwitch`, a SharedPreferences boolean (`map_layers`, default on); `render` sets it from the saved choice, so it's handled with a click listener rather than a checked-change one, and disables it, with `layers_master_empty` as its tooltip, while nothing is picked. `MapFragment.setLayersShown` saves it and re-applies the paths and places through `shownPaths`/`shownSpots`, which give `MapPaths.NONE` and no categories while it's off — every place the saved picks are applied goes through them — and `showSpots` closes an open spot popup whose badge is no longer drawn and tells `ShowInArea`; a capture in progress carries on. A box ticked in the menu while it's off calls `onShown(true)` first. A focusable popup closes itself on an outside touch, including one on the button, so a click landing within 300ms of that close doesn't reopen it. The menu reads and writes through `MapFragment`'s `setPaths`/`setSpots`/`setLayersShown`/`setSatellite`; `onDestroyView` dismisses it.
- **Paths are `map/MapPaths`**, the web's `map/paths.ts` (root `docs/IMPLEMENTATION.md` §4.24). The choice is three SharedPreferences booleans in `map_paths` (`trails`, `tracks`, `bike_paths`, default off); the single `show` key of the former one-toggle version is the default for all three until the first write removes it. `MapPaths.apply` sets `visibility` on each kind's two layers — the path and its bridge twin — by id (`TRAIL_LAYER_IDS`, `TRACK_LAYER_IDS`, `BIKE_PATH_LAYER_IDS`, which must match `style.ts`'s), in `loadStyle`'s loaded callback, since each style load brings them back hidden, and again on each change. A layer missing from an older served style is skipped.
- **Satellite is `map/MapSatellite`**, the web's `map/satellite.ts` (root `docs/IMPLEMENTATION.md` §4.26): `layers_satellite`, the Layers menu's second switch, checked while the imagery shows, and `gone` unless `loadStyle`'s callback found a `satellite` source in the served style (`MapSatellite.isAvailable`, kept as `satelliteAvailable`), which the server includes only when the deployment configures imagery. The choice is a SharedPreferences boolean (`map_satellite`, default off). `MapSatellite.apply` sets `visibility` on the `satellite` layer and, the other way, on every id in the style's `holdmytrack:satellite-hides` metadata (read from `Style.json`), and `lineOpacity` on the `holdmytrack:satellite-dims` roads — the metadata's `holdmytrack:satellite-road-opacity` when on, 1 when off — so the lists and the opacity are `style.ts`'s, not a second copy. `MapFragment.darkBase` — night mode, or satellite on — is what `MapOverlays.attach` gets for its veil, and a change calls `MapOverlays.setDarkVeil`, which re-adds the coverage layers with the other veil only when it changed.
- **Find my location is MapLibre's own `LocationComponent`, activated lazily.** `onLocateTap` asks for location on the first tap (fine and coarse together; either grant is enough), then `showMyLocation` activates the component with the default location engine, enables the position dot, and sets `CameraMode.TRACKING` with a minimum zoom of 14 (`LOCATE_ZOOM`) — which flies to the fix and follows it until the user pans, like the web's geolocate control. Nothing is located until that first tap. The button hides while recording, and a recording's first fix sets the camera mode back to `NONE`, so the recording's own follow (§7) is the only thing moving the camera then. `ACCESS_COARSE_LOCATION` is not declared in this app's manifest; MapLibre's merges it in.
- **The date range (`date_footer`, SPEC FR-2.6) is the head of the Activities sheet (§3.2).** Its row is `date_range_label` (the range, the serif title), `panel_summary` under it (`ActivitiesPanel`'s), and the range-shift buttons (`date_range_shift_earlier`/`_later`, `Button.SheetShift`: 44dp round tonal icon buttons); under it, `DayScrubberView`. Four pieces in `map/`: `ActivityDays` is `apps/web/src/ui/useActivityDays.ts` — pages of `GET /v1/activities/histogram?days=240&before=` (`HoldMyTrackApi.activityDayPage`), each day with its count and `distanceMeters`, an anchor-date window of `DateRangeSlider.WINDOW_DAYS` (12, about 30dp a day on a 412dp phone), prefetching once the window is within one window of the loaded edge, a pan past what's loaded carried until the page lands, and a generation counter so an answer to a superseded reload is dropped. `DateRangeSlider` is `DateRangeSlider.tsx`'s logic — handles on slot boundaries (`startOf`/`endOf`/`moveKnob`), the draft committed only on release, and the pull of a handle on the edge being paged toward, recorded as a pending `Pan` and landed in `setDays` once the window's first or last day actually changes. Paging has no button: `onTrackDrag` gets the boundary unclamped, and a handle dragged past the edge it's moving toward steps the window 5 days that way (`step`) every 500ms (`EDGE_REPEAT_MS`) until it's moved back in or let go, which commits once any pan has landed (`finish`). The shift buttons press-and-hold through `setUpRepeatButton` (400ms, then every 180ms, off an `OnTouchListener`; a click that isn't a touch, from TalkBack, steps once); their step is `ActivityDays.shift`: `RangeShift.kt`'s `shiftRange` (the web's `rangeShift.ts`, with the same cases in `RangeShiftTest`) gives the new range, the window moves just far enough to show it, and a `Load` answer fetches the next page and skips that press. `canShift` sets the buttons' enabled state. `ScrubberBars` holds the pure parts, tested in `ScrubberBarsTest`: `levels` (each day's distance as the square root of its share of the window's longest, floored at 0.15), `labels` (the day of the month, and the month where the window starts or a new one does) and `rangeLabel` ("24 Sep – 3 Oct 2026", the year said once, the months in `d MMM`). `DayScrubberView` draws — the selection as an `hmt_accent_container` band of the large radius over its slots, a bar per slot (accent inside the band, `hmt_border_strong` outside, at most 10dp wide), the labels under them, bold for a month, 5×28dp `hmt_accent_strong` handles, and a Lucide ‹ or › (`ic_chevron_left`/`_right`, `hmt_ink_muted`, a 16dp box) centred in the 12dp side padding for each of `ActivityDays.canPanEarlier`/`canPanLater`, which `DateRangeSlider.render` passes to `set` — and sorts each touch into one of three gestures, asking its parent not to intercept so the sheet doesn't drag with it: a press within 24dp of a drawn handle (`HANDLE_GRAB_DP`) is that handle's, reported as press, drag and release; any other press waits, and becomes a swipe once it moves past the touch slop — `onSwipe` with each whole slot the finger has moved, which `DateRangeSlider.onSwipe` hands to `ActivityDays.panBy` negated, so the days follow the finger, with no `Pan` recorded and so no handle pulled along — or, let go unmoved, a tap: a press at the nearest boundary and a release, so the nearer handle moves there and commits. `MapFragment` owns the state: `selectedRange`, and `userChangedRange`, which stops `onActivityDaysChanged` re-deriving the default (the last 5 of the reloaded window's days, through `LocalDate.now()` — the device's day, as the web uses the browser's). Days reload whenever `syncSession` passes with `daysStale` set, which `onResume` sets; `ActivityDays.reload` keeps the window's anchor, fetching back to it when it's older than the fresh page, so a range picked further back is still in view after Profile or Sync. `applyRange` redraws the tracks (`MapOverlays.setTrackRange`) and reads the range's list into the panel (`loadActivities`, §3.2); for a user's pick only, it first clears the panel's state and then flies to the union of the listed rows' `bbox`es — dropped if another range was picked meanwhile or a recording started. `renderDateFooter` shows the range for Normal, not recording, a verified session, the Activities tab and an account with history, and the sheet for Normal and not recording; `applyAttributionMargin` lifts MapLibre's logo and attribution (the ODbL credit, FR-2.4) above the *collapsed* sheet (`panel.peekHeight`), so opening it doesn't carry them up the screen. `flyTo` pads the fit by the top row's bottom edge and by the sheet from where it rests or is heading (`ActivitiesPanel.restingTop`), so a framed activity lands in the map left showing between them. The range goes into `onSaveInstanceState`, and so do the logo's and attribution's base margins: MapLibre restores its UI settings already lifted, and capturing them again lifted the logo twice its height above the sheet (found on the device after a language change).
- **Style flavor follows the app's night mode** (`Configuration.UI_MODE_NIGHT_MASK`, `MapFragment.isNight`), resolving to `light` or `dark` — two of the five flavors `GET /v1/map/style/{flavor}` serves. Night mode is the system's day/night setting unless the You tab's Theme overrides it (§1.3), and the app's own palette follows the same setting, so a dark map always sits under dark chrome. `MapOverlays.attach` takes the same flag, for Fog's veil (root `docs/IMPLEMENTATION.md` §4.2).

### 1.3 Theme (`res/values/themes.xml`)

Every Activity uses one of two themes, both built on `Theme.Material3.DayNight`: `Theme.HoldMyTrack` (with an action bar, for every screen with a title) and `Theme.HoldMyTrack.Map` (no action bar, for `MainActivity`'s edge-to-edge map). The palette lives in `res/values/colors.xml` as the web's `--fm-*` custom properties (`services/server/internal/web/static/tokens.css`) copied value for value, and `Base.Theme.HoldMyTrack` maps it onto Material's color roles once — accent `#B07E2E` as primary, ink `#202B25` as on-surface and secondary, cream `#F7F4EC` as background and surface, the web's danger red as error. The dark palette is `res/values-night/colors.xml`, the web's dark `--fm-*` values under the same names, so the theme's role mapping is written once and holds for both; `colorOnPrimary` is `hmt_on_accent` (white on the light accent, near-black on the dark palette's brighter one), and the status and navigation bar icons flip through `hmt_light_system_bars` (`res/values/bools.xml`, `values-night/bools.xml`). Which palette applies is AppCompat's night mode: `settings/AppTheme.kt` keeps the You tab's Theme choice (System, Light, Dark) in SharedPreferences, applies it with `AppCompatDelegate.setDefaultNightMode` in `HoldMyTrackApplication.onCreate` and again on a change — which recreates the open screens — and the map's flavor reads the same configuration (§1.2). Ink tints in drawables are colors too (`hmt_ink_tint_6`/`8`/`10`), so they flip to cream tints with the palette. Dynamic color is not applied, so the user's wallpaper never replaces the palette.

- **The rest of the tokens are in `res/values/dimens.xml`**, the web's spacing (`hmt_space_2`…`32`), radius (`hmt_radius_xs`…`lg`) and type (`hmt_text_3xs`…`2xl`) scales with CSS px read as dp, and sp for text: a phone browser draws one CSS px as one dp, so the mobile web and the app come out the same size. Every padding and margin in the layouts is a `hmt_space_*` reference, and so are the code-built rows' (`panel/ActivitiesPanel`, `panel/StoriesTab`, `map/LayersMenu`, `recording/ActivityTypePicker`, `settings/ChoicePicker`). Literal dimensions left are sizes, not spacing: the record button, icon boxes, hairlines, the 48dp route preview. The file turns off `UnusedResources`, since the whole scale is there, steps no screen uses yet included.
- **Shape is the web's radius scale, not Material's.** Inputs take `hmt_radius_sm` (`shapeAppearanceCornerExtraSmall`, which outlined text fields use), buttons and the map chrome `hmt_radius_md`, and menus, sheets and dialogs `hmt_radius_lg` (the medium, large and extra-large corners) — rather than Material 3's 4dp fields, pill buttons and 28dp dialogs.
- **Type is the web's two faces on Material's roles.** `res/font/hmt_sans.xml` is Inter and `hmt_serif.xml` Fraunces, each one variable `.ttf` listed once per weight (400–800) with its `wght` variation, so `textFontWeight` picks an instance; `res/font-ru/hmt_serif.xml` swaps in Source Serif 4, the web's own `:root:lang(ru)` choice, because Fraunces has no Cyrillic — a whole Russian title in one face. The files are Google Fonts' own (OFL; no Reserved Font Name, so modified copies keep their names, and the licences ship in `assets/licenses/`), cut down with fontTools: Latin, Latin Extended-A and Cyrillic only, weight kept as an axis over 400–800, and every other axis fixed — optical size at 14 for Inter (the web requests none, so it gets the default) and 20 for the serifs (the one size titles are drawn at), Fraunces' SOFT 0 and WONK 1 as Google serves it. About 630 KB in all, from 2.4 MB. The theme maps the scale onto the roles the app uses, each with zero letter spacing as on the web: `titleLarge`, the screen titles, is the serif at 20sp semibold, the web's `.auth-card__title` (the action bar names it directly, since Material's action-bar title style doesn't follow the role); `headlineSmall`, the recording's stats and dialog titles, 20sp bold; `titleMedium` 16sp and `titleSmall` 13sp semibold; `bodyLarge`, which text fields use, 14sp like the web's inputs; `bodyMedium` 13sp, the web's interface text; `bodySmall` 12sp; `labelLarge`, buttons, 14sp semibold like `.auth-card__submit`; `labelMedium` 12sp and `labelSmall` 11sp semibold. The display and larger headline roles aren't mapped: the web scale has no step above 20px and no screen uses them. Code that set a size of its own now uses a role, and `ActivityTypePicker` bolds the current type with `Typeface.create(typeface, 700, false)`, because `setTypeface(null, BOLD)` would drop to the system font.
- **Icons are Lucide**, the web's set (root `docs/IMPLEMENTATION.md` §4.17), converted from `lucide-static` 1.48.0 — the web's `lucide-react` version — to vector drawables named after the icon (`ic_map`, `ic_locate_fixed`, `ic_chevron_down`, `ic_pause`, `ic_play`, `ic_square`, `ic_circle_dot`), with the licence in `assets/licenses/lucide-LICENSE.txt`. The geometry is Lucide's own, a 24-unit grid with a 2-unit round stroke; its circles, lines and rounded rects are written out as paths, since a vector drawable has only paths. Every stroke is white and the colour comes from where the icon is used — `iconTint` on the map buttons, the text field's end-icon tint, the record button drawing white on its dark disc, the status bar masking the notification icon — the Android counterpart of the web's `currentColor`, so an icon file never names a colour. Icons stay at Material's 24dp rather than the web's 16px, the size Android's buttons, text fields and status bar are laid out around. One glyph is deliberately outside the set: the idle record button's solid red dot (`ic_record_start`), since a filled signal colour is what says "record", and Lucide's outlined circle would read as an empty radio button.
- **The default face reaches text through a TextView style, not the theme's `fontFamily`.** The theme sets `android:textViewStyle` (`Widget.HoldMyTrack.TextView`, BodyMedium) and points the platform's own text attributes — `PopupMenu` items, list and spinner rows — at BodyLarge. It first set `android:fontFamily` on the theme instead, which reaches every `TextView` as if set on it directly and so outranks its `textAppearance`: the serif TitleLarge came out in Inter, and every role's weight flattened to regular, which the sign-in card's title and buttons showed.
- **Shared pieces for the designed screens**, each after a web class: `Widget.HoldMyTrack.Card` (`.auth-card` — white, a 1dp border at ink 10%, `hmt_radius_lg`, 24dp padding, no elevation, since Material 3 tints an elevated surface toward the primary color); `Widget.HoldMyTrack.Hint` (`.auth-card__hint` — 13sp at ink 65%); `Widget.HoldMyTrack.Notice` and `.Notice.Error` (`.auth-card__notice`/`__error` — a tinted box, `bg_notice`/`bg_notice_error`); `include_or_divider` (`.auth-card__divider`). The web's `rgb(var(--fm-ink-rgb) / N%)` tints are `res/color/` selectors with `android:alpha` over a palette color, named by use (`hmt_card_border`, `hmt_ink_hint`, `hmt_notice_bg`, `hmt_error_bg`, …).
- **Checked on the emulator**, English and Russian: Inter in body text, fields and buttons, Fraunces titles, Source Serif 4 for the Russian title, and a 400 against 600 title rendering differently, which is the variable weights taking effect.
- **Button hierarchy comes from theme attributes**, so a plain `<Button>` in a layout inflates as a filled `MaterialButton`, and the secondary styles are named rather than hand-set: `Widget.HoldMyTrack.Button.Outlined` (also `materialButtonOutlinedStyle`) and `Widget.HoldMyTrack.Button.Text` (also `borderlessButtonStyle`).
- **The map chrome is panels of one kind**, after the web's `.map-mode-toggle` (and the design mockup's map page): `Widget.HoldMyTrack.MapPanel` — `bg_map_chrome` (the web's 92% white, `hmt_radius_md`), 4dp padding and a 2dp elevation for `--fm-shadow-sm` — holds the mode toggle, the recording's status, Layers and Find my location alike. Layers and Find my location sit in their panels as transparent icon buttons rather than carrying the color and shadow themselves: a translucent `MaterialButton` with elevation draws its shadow through its own fill, which showed as a lighter square around the icon. Their 48dp minimum height is set on the style (`MapIcon`) rather than taken from the row, since while recording the row holds nothing else and a `match_parent` button collapsed to nothing — so every panel is 56dp, measured. The toggle: Normal, Fog and Heatmap, each an 18dp Lucide icon (`ic_route`, `ic_cloud_fog`, `ic_flame`, tinted like the label) and its label. ## 2. Authentication & Session

### 2.1 `net/Session`

An `object` (process-wide singleton) rather than an instance, because two independent HTTP call sites need the same token without being wired to each other: the app's own `HoldMyTrackApi` calls, and MapLibre Native's tile fetching, which goes through the shared `OkHttpClient` but never through `HoldMyTrackApi` itself.

The token lives in two places at once, deliberately: a `@Volatile` field for fast, thread-safe reads (the bearer interceptor runs on whichever thread OkHttp is dispatching a tile request from — reading `SharedPreferences` on every one of those would be both slower and not obviously safe to do off the main thread), and `SharedPreferences` (`MODE_PRIVATE`) for persistence across process death. `init(context)` must run before either `token` or `isSignedIn` is read — `HoldMyTrackApplication.onCreate` guarantees this by calling it first.

`verified` is a separate boolean from "a token is present." A token can be present and *unverified* right after a cold start (restored from disk, not yet checked against the server) or present and *verified* right after a fresh sign-in (the server just minted it, so there is nothing to check). `markVerified()` and `clear()` are the only two ways `verified` changes; `MapFragment.verifyStoredSession()` and `VerifyEmailActivity.check()` are the only callers of either in response to a network result.

`emailVerified` is the account's own `email_verified`, persisted beside the token: `start()` takes it from the sign-in response, `markVerified(emailVerified)` from each `GET /v1/auth/me`. It is on disk rather than per-process so a cold start routes straight to the right screen without drawing a map first. A missing value reads as `true` — a session stored by a build that didn't record it — and the cold start's `GET /v1/auth/me` corrects it before any user layer attaches.

### 2.2 `net/HoldMyTrackApi`

The entire HTTP surface of the app in one object: one shared `OkHttpClient`, its interceptors, and the calls themselves — five session-minting calls behind a shared `authenticate` helper (sign-in, sign-up, demo, `signInWithGoogle`, `exchangeHandoff`), plus `providers`, `signOut`, `verifySession` (which answers with `email_verified`), `resendVerification`, `latestActivityBounds`, `activityBounds`, `activityDayPage`, `activityTypeCounts`, `syncHistory`, `duplicates`, and `syncActivities`; `facebookStartUri` builds a URL rather than making a call.

- **`client` is shared with MapLibre Native** (§1.1). Its `Dispatcher` is configured with `maxRequestsPerHost = 20`, matching what MapLibre's own default client would have used — inheriting OkHttp's plain default of 5 here would throttle the map's tile bursts relative to how the SDK behaves when it manages its own client, for no reason tied to this app's needs.
- **`BearerInterceptor` runs per request, not once at startup**, and checks the request's URL against `BuildConfig.API_BASE_URL` before attaching anything. Running per-request is what makes sign-in, sign-out, and token expiry take effect on the very next request — including the very next map tile — with nothing to re-register. The origin check exists because the style document's basemap assets (the pmtiles archive, glyphs, sprites) are unauthenticated and, in a production CDN deployment, live on a domain HoldMyTrack doesn't own; sending a live bearer token to that origin would only ever put a working credential in a third party's access logs.
- **`OriginInterceptor` sends the API's origin on every request that leaves it**, `Origin: https://holdmytrack.com` on the production build, unless the request already has one — what a browser sends on the web client's cross-origin fetches. The satellite imagery's key only accepts requests from the deployment's origin (root `docs/DEPLOY.md` §5), and without it MapTiler refused every imagery tile with a `403`. It gives nothing away: the key is already public in the web bundle and the style document, and the restriction is there to stop other websites spending the quota. Checked on an emulator against holdmytrack.com: with it, the imagery draws under the roads and labels.
- **Everything except `syncActivities` is callback-based** (`enqueue` + a `Result<T>` callback posted back to the main thread via a `Handler(Looper.getMainLooper())`). This is a deliberate rejection of a coroutines-everywhere style for this file specifically: five-to-eight call sites don't amortize the cost of a coroutines runtime and lifecycle-scope wiring layered on top of OkHttp's own async API, which already does the job.
- **`syncActivities` is the one `suspend` function**, and it wraps a *blocking* `execute()` call inside `withContext(Dispatchers.IO)` rather than using `enqueue`. This is intentional, not an oversight: its only caller (`SyncRunner`) must not send its next batch, or move the watermark, until this one is answered — the call site genuinely wants to block its own coroutine, and Health Connect's own read API already forces that caller onto coroutines regardless.
- **`activityTypeCounts` reads the same unpaginated `GET /v1/activities`** and counts rows per `activity_type` — what the recording Edit screen's Type picker (§7.6) lists, the same per-type counts the web client's Type facet is built from. There is no dedicated facets endpoint, and this list already carries every live row.
- **`latestActivityBounds` and `activityBounds` parse `GET /v1/activities` themselves** (through `forEachDrawn`, which skips rows with no `bbox` and Pending ones) rather than sharing a model type with anything else in the app, because nothing else in the app needs a full `Activity` model — the map only ever needs a bounding box: the most recent row's to open on, or the union of a date range's rows to fly to.
- **`ApiException` carries the server's own response text as its message**, unreworded. The server writes plain-text errors (`http.Error`), and this app treats that text as user-facing rather than a debugging detail — "invalid email or password" is exactly what a person needs to read, and rewriting it risks saying something the server didn't actually mean. The refusals a client branches on come as `{error, message}` instead (`demo_read_only`, `photo_needs_place`); `ApiException.from` reads those as their `message`, keeping the code in `errorCode`, so the user still sees the server's sentence rather than the JSON.
- **`image(path, maxSide)` fetches any API image with the bearer token** — an avatar, a photo, its thumbnail — and decodes it off the main thread, with `maxSide` sampling it down by powers of two so a 2048 px photo shown at a popup's width isn't held at full size. A browser tab or an image library would have no token to send, which is also why Full size opens in the app (§3.4).

### 2.3 `SignInActivity`

The app's first screen whenever no session is held, and the root of its own task: `SignInActivity.open` starts it with `FLAG_ACTIVITY_NEW_TASK | FLAG_ACTIVITY_CLEAR_TASK`, used by a signed-out cold start, by `MapFragment` when a stored token is rejected, and by the You tab's Sign out, so no screen that needs a session is ever left underneath it and Back leaves the app. A successful sign-in, sign-up or demo start replaces the task the same way with `MapFragment`.

**The web's two pages as two modes of one screen.** `signingUp` switches the title, the submit button (Sign in → `POST /v1/auth/login`, Create account → `POST /v1/auth/signup`), the link under it to the other mode, and the password's autofill hint (`password` or `newPassword`, so a password manager suggests a new password only on sign-up); the hint text, "Forgot password?" and the demo with its "or" show on sign-in only, as on the web. The email carries over a switch, the error box doesn't. It's one activity rather than two because the Facebook round trip returns here through `OAuthRedirectActivity` with the verifier this screen keeps, whichever mode started it. An `OnBackPressedCallback`, enabled only in sign-up mode, makes Back return to sign-in (Back from `/signup` on the web); `signingUp` survives recreation in the saved state, including a process death behind the Facebook tab. **"Forgot password?"** opens the web's own `/forgot` (`HoldMyTrackApi.forgotPasswordUri`, the API origin outside `/v1`) in a Custom Tab rather than a native form, since the emailed reset link opens the web's `/reset` page anyway.

The submit button, the demo, and Google and Facebook when the server has them, share one result handler (`onResult`). Client-side validation is limited to "both fields are non-empty" before a request is even sent — deliberately, so the server remains the single source of truth for what an acceptable email or password looks like, and its error text (via `ApiException.message`) is what the user sees on failure rather than a client-authored message that could drift from server behavior.

**Google and Facebook** (`docs/adr/0016-native-sign-in.md`; the server side is root `docs/IMPLEMENTATION.md` §4.15 and §4.22). Both buttons start hidden and appear only once `HoldMyTrackApi.providers()` reports each one configured; if that request fails they stay hidden, since a button that can only fail is worse than none.

- **Google** asks Credential Manager (`androidx.credentials` with `GetSignInWithGoogleOption`) for an ID token for `providers.googleClientId` — the server's *web* client ID, so the token's audience is the one the server checks — from `lifecycleScope`, and posts it to `POST /v1/auth/google/token` with the device's IANA zone. Closing the picker (`GetCredentialCancellationException`) shows nothing; any other failure is logged (in development it's almost always a missing Android OAuth client for the debug key's SHA-1, which the picker reports only as a generic error) and shows `google_failed`. `googleid` is pinned at 1.2.0: 1.2.1 is compiled with Kotlin 2.4 metadata, which this project's compiler can't read.
- **Facebook** doesn't use Meta's SDK. It makes a 32-byte verifier and its S256 challenge, saves the verifier in the `sign_in_handoff` SharedPreferences (the process can die while the tab is in front), and opens the server's `/v1/auth/facebook/start` in a Custom Tab (`androidx.browser`). The server's callback ends at `holdmytrack://oauth?code=…` or `?error=…`. **`OAuthRedirectActivity`** receives it: a `Theme.NoDisplay`, exported activity whose only job is forwarding the URI to `SignInActivity` with `CLEAR_TOP | SINGLE_TOP`, which closes the Custom Tab above it and keeps `SignInActivity` itself unexported. `handleRedirect` (from `onNewIntent`, or `onCreate` on a fresh instance) reads and removes the verifier, then either redeems the code at `POST /v1/auth/handoff` or maps the error code to the web's own wording (`facebook_no_email`, `facebook_email_in_use`, otherwise `facebook_failed`). `awaitingBrowser` re-enables the buttons in `onResume` when the tab was simply closed.
- Checked on an emulator against the local stack: the buttons follow `/v1/auth/providers`, closing the tab re-enables the screen, an `error=facebook_no_email` redirect shows its message and clears the verifier, and a real code for the stored verifier signs in and opens the map. The Facebook dialog itself and Google's picker weren't exercised there (no Facebook login on the emulator; no Google client configured locally).

**Designed as the web's sign-in and sign-up pages** (`templates/pages/signin.html`, `signup.html`, `.auth-card` in `static/pages.css`): the screen drops its action bar (`Theme.HoldMyTrack.NoActionBar`) and is one `Widget.HoldMyTrack.Card` on the cream page, 16dp from each edge, with the serif title inside it as on the web. Its children are spaced by the web's 16px gap — a `LinearLayout` with `showDividers="middle"` and the empty `gap_16` drawable, which skips `GONE` children the way flex gap does. The order is the web's: title, hint, Google and Facebook, an "or" divider (`include_or_divider`, the web's `.auth-card__divider`), the email, the password with "Forgot password?" under its right edge (the web's `.auth-card__forgot`), the error box, the submit button, the link to the other mode (`Widget.HoldMyTrack.Button.Link`, the web's `.auth-card__link`), another "or", and Try the demo as an outlined button, the web's `__secondary`. Google and Facebook are the web's brand buttons: white with the multicolor "G" (`Widget.HoldMyTrack.Button.Google`, the icon untinted), and white on Facebook's `#1877F2` with its "f" (`.Facebook`) — the two marks are the web's own SVG paths (`templates/auth.html`) as `ic_brand_google`/`ic_brand_facebook`, and like the web they sit outside the Lucide set. Checked on the emulator in English and Russian, with a wrong password showing the server's message in the error box; Google's button wasn't shown, since the local stack has no Google client.

A successful sign-in whose `email_verified` is false opens `VerifyEmailActivity` (§2.4) instead of `MainActivity`.

### 2.4 `VerifyEmailActivity`

The "check your email" screen (`apps/android/docs/SPEC.md` FR-1.4), the counterpart of the web's `/verify-pending`. Until it existed, an unconfirmed account — a signup when the server sends verification emails, or any new Sign in with Facebook account — opened the map with nothing on it: `requireVerified` answers every tile and sync request `403 email_not_verified`, which MapLibre reports only in logcat, and the sync screen failed with the raw JSON body.

- **Root of its own task**, like `SignInActivity`: `open` uses `NEW_TASK | CLEAR_TASK`, from `SignInActivity.onResult` and from `MapFragment.onCreate` and `MapFragment.syncSession`, so Back leaves the app instead of revealing the empty map.
- **The link is clicked in a browser the app never hears from**, so `check()` asks `GET /v1/auth/me` on every `onResume` — returning from the mail app is when the answer is most likely to have changed — and on Continue. Only Continue reports "not yet" or a network failure; the automatic check is silent. `checking` is the same re-entrancy guard as `MapFragment.verifying`. A confirmed answer replaces the task with `MapFragment`; a `401` clears the session and opens `SignInActivity`, as `MapFragment` does.
- **Resend** posts `POST /v1/auth/resend-verification` and shows the server's `message` (or its plain-text refusal, e.g. the per-account rate limit) verbatim, in the language `LanguageInterceptor` asked for.
- **Designed as the web's `/verify-pending` card** (`templates/pages/verify-pending.html`), on the sign-in screen's pieces (§2.3): no action bar, the serif title in the card, the hint with the address in bold (a `StyleSpan`, the web's `<strong>`), what Continue or Resend said in a notice (`verify_notice`) or, for a failure, the error box (`verify_error`), and Sign out as the web's small link-button (`Widget.HoldMyTrack.Button.Link`). Continue stays the filled button rather than Resend, the web's primary: the app's own step after clicking the link is to come back and continue, which the web does by reloading.
- **No change-email form**, unlike `/verify-pending`: `RecordedActivityStore`, `RecordingTypes` and `SyncCursor` key their data by `Session.email`, so changing it from here would need those migrated too. A mistyped address is corrected on the web.
- **`SyncFragment` checks `Session.emailVerified` too** (after its signed-out check, before its demo check), since Health Connect's rationale intent can open it (in `SyncActivity`) without passing through the map.
- Checked on an emulator (the `fitmap` AVD) against the local stack: an account signed up in the app and then set unverified in the database opened on this screen at the next launch; Continue said it wasn't confirmed yet; Resend showed "Verification email sent." and the API logged a fresh link; with the account set verified, returning to the app opened the map.

### 2.5 `settings/SettingsActivity`

The account's Settings (`apps/android/docs/SPEC.md` FR-1.5), after the web's page (`templates/pages/settings.html`): the avatar, then Name, Country, Timezone and Language saved together.

- **The lists are the server's** — `GET /v1/account/settings/options` (root `docs/IMPLEMENTATION.md` §4.12), the same functions that build the web page's selects, so every choice is one `saveSettings` accepts. Android's own ISO countries and zone ids would drift from the server's and fail a save with a `400`.
- **`net/Profile`** is the account as `authResponse` describes it — every sign-in, `GET /v1/auth/me` and every Settings or avatar change returns it — and `Session` keeps the two fields the app acts on, `country` and `locale`, on disk beside the token, refreshed by each of those answers (`Session.update`).
- **Country and Timezone** open `settings/ChoicePicker`, a searchable list in a dialog after `recording/ActivityTypePicker` — closed, only listed values; a timezone's region is shown and searched with it. **Language** is an exposed drop-down.
- **The avatar** goes through `ActivityResultContracts.PickVisualMedia` (the photo picker, no storage permission), is decoded at a reduced size, scaled to at most 512 px and sent as JPEG, off the main thread — a phone photo is often past the server's 5 MB limit, and an avatar is never shown large. `HoldMyTrackApi.avatar` fetches it back with the bearer token. The You tab shows it and the Name (§2.7).
- **Units** — `recording/RecordingFormat` is the one place distances, heights and speeds become text, now with an imperial branch for the web's three countries (`Imperial`, `services/server/internal/web/format.go`), read from `Session.country`; the Sync screen's recording rows and history go through `panel/PanelFormat`, which asks it which units, rather than each dividing by 1000.
- **Language** — `settings/AppLanguage` sets the per-app language through `LocaleManager`, only when it differs (setting it recreates every open screen). Automatic can't be told apart from "never chosen", so a sign-in (`SignInActivity`) or session check (`MapFragment.verifyStoredSession`) only applies an explicit language, and only a save — Settings', or the You tab's Language (§2.7) — clears a per-app language. The screen keeps its "Saved." notice as a string id across the recreation a language change causes, so it comes back translated.
- **First run** — `MapFragment.syncSession` sends a confirmed, non-demo account with an empty `Session.country` to `SettingsActivity.openOnboarding`: the root of a new task, the web's welcome title and intro, "Save and continue" on to the map. `Session.country` is only trusted once a session check has refreshed it, so an account that saved Settings on the web isn't sent there by a stale value. `HoldMyTrackApi.signUp` now sends the phone's zone as `timezone`, as the web's sign-up sends the browser's, so a new email account doesn't start on UTC.
- **Demo** — every field disabled and the web's note; the server refuses the save (`requireNotDemo`) regardless.
- **Delete account** is `settings/AccountDeletion`, from the You tab (§2.7) — `confirm` builds a `MaterialAlertDialogBuilder` with the destructive overlay, what goes (`settings_delete_hint`) as its message, and `layout/dialog_delete_account` (how to confirm, and an email field), and replaces the positive button's listener so a mismatch (`HoldMyTrackApi.deleteAccount`'s failure, the server's wording) lands on the field as its error without closing the dialog. `forget` then clears what the phone keys by the email — `RecordedActivityStore.deleteAll` and `SyncCursor.reset` — before `Session.clear`, so a new account made with the same address starts clean, and opens `SignInActivity.open(context, R.string.account_deleted)`, whose `notice` shows it. Gone for the demo account. Checked on the emulator against the dev stack: a wrong email kept the dialog with its error; the right one closed the account on the server and landed on the sign-in notice.
- Checked on the emulator against this branch's server (run on the host, port-forwarded): a new account opened on the welcome screen, picked the United States through the search, saved and went to the map, where an uploaded walk read 0.42 mi in sync history; Language saved as Русский switched the app, and back as English with "Saved." shown after the switch; an avatar picked through the photo picker uploaded, showed on Settings and Profile, and was removed; the demo account got the disabled screen and no gate.

### 2.6 `ProfileActivity` and `profile/`

Activity graph & trends, the web's `/profile` page (`apps/android/docs/SPEC.md` FR-1.6), from the You tab's numbers, after `templates/pages/profile.html` and `static/pages.css`.

- **Two reads, as the web page's queries.** `HoldMyTrackApi.activityDays` is the histogram's calendar-window mode from 1970-01-01 to December 31 of this year — the server returns only days with activity, so this is every active day and the account's `earliest`, in one call, the same `dailyTotals` the web page runs (root `docs/IMPLEMENTATION.md` §4.8). `HoldMyTrackApi.activityTrends` is `GET /v1/activities/trends` over its default trailing 12 months. No new endpoint: `graph-stats` isn't called, since every number comes from the days. Both are read on every `onResume`; a Trends answer that a later Week/Month switch has already replaced is dropped (`trendsRequest`).
- **`profile/ProfileStats` is `profile_page.go` ported**: `statsOf` (sums, the number of days, the longest run of consecutive dates), `daysInYear`, `distanceThresholds` (the 1/3 and 2/3 points of a year's non-zero distances), `shadeLevel`, `layout` (whole Sunday-to-Saturday weeks from the Sunday on or before January 1, padding cells as -1, each month's first-day column), `recentWeeks` (the You tab's glance: the last weeks through today, shaded by count, the days after today -1) and `trendHeights` (`ln(d + 1) / ln(peak + 1)`). Pure Kotlin over `java.time`, unit-tested in `ProfileStatsTest`. The account's zone (`Session.timezone`) decides this year and today.
- **`profile/YearGridView` draws a year on a canvas** at the web's sizes — 12dp cells 4dp apart, 2dp corners, 9sp labels at ink 45% — rather than 371 views. Its four shades are `color/profile_level_0`…`3`, which the legend's squares also take as tints. A tap maps to a column and row (a gap counts for the cell before it) and goes to `onDayTap`; the selected day gets a 1.5dp ink ring. The month and weekday labels are `profile_months` and `profile_weekdays`, the web's `month.standalone.*` and `weekday.short.*`, since Android's own short names differ from the web's (Russian "мая"/"май"). Each year is `item_profile_year` inflated into a `HorizontalScrollView`; this year's is scrolled so today's column is at the right edge.
- **`profile/TrendsChartView`** is `.trends__bars`: the bars share the width 2dp apart, 140dp tall at most, never under 2dp, top corners rounded, over a 1dp baseline at ink 12%; the tapped bar takes `hmt_accent_hover`, the web's `--fm-accent-hover`. Only periods with activity come back from the server, so the bars are as wide as their count allows — the web's chart does the same (root `docs/KNOWN_ISSUES.md`).
- **The switches are `MaterialButtonToggleGroup`s** (`Widget.HoldMyTrack.Button.ProfileToggle`): single selection, one always selected, white with an ink 20% border and accent-filled with white text when checked, the web's `.profile__toggle-btn`. They're saved in `onSaveInstanceState`.
- **Numbers** go through `panel/PanelFormat` (grouped counts, a total's one decimal under 10, a day's one decimal), plurals with the grouped count as a string, the short date from `DateFormat.getBestDateTimePattern("MMMd")` ("Sep 8", "8 сент." as the web's `ShortDate`), and elevation as whole metres or feet.
- Checked on the emulator against a local stack, in English and Russian: the cards, the 2026 grid opening on today, a tapped day's totals and the ring, Distance shading and its legend, a tapped bar's breakdown, Week and Month, and both switches kept across the recreation a language change causes.

### 2.7 `YouFragment`

The You tab (`apps/android/docs/SPEC.md` FR-2.9), `fragment_you`: the phone design's cards (`bg_section_card`, `Widget.HoldMyTrack.SectionCard` with its inset hairlines, `CardRow`s with an `IconTile` and a `RowChevron`), as on the Sync tab (§5.1).

## 3. Map Rendering

### 3.1 `map/MapOverlays`

Owns exactly three layers — `tracks` (a `VectorSource` MVT layer), `fog`, and `heatmap` (both `RasterSource` layers, 512px tiles matching the server's own raster tile size, not the MapLibre default of 256) — and the logic to add, remove, and toggle them.

- **`attach` is idempotent and re-runnable**, checked with `style.getSource(id) == null` / `getLayer(id) == null` before adding anything. This matters because a style *reload* (switching from `light` to `dark` when the app's night mode changes) discards any custom layers a previous `attach` call added — this is not a one-shot setup path.
- **Insertion point is computed, not hardcoded**: `labelInsertionPoint` finds the basemap's first `SymbolLayer` and every custom layer is added *below* it (`addLayerBelow`), so place labels always render on top. Within that, both rasters are added before the tracks vector layer, so tracks paint above whichever raster is currently visible — the same ordering rationale `docs/IMPLEMENTATION.md` §4.2's client-compositing section gives for the web client, reproduced here layer-by-layer rather than shared code, since there is no shared layer-ordering module between the two clients.
- **`setMode` only changes paint/layout properties**, never adds or removes anything — all three layers exist on the style simultaneously once attached; the toggle is a `visibility` flip (`Property.VISIBLE` / `Property.NONE`), plus Fog dimming every basemap `SymbolLayer` to `textOpacity`/`iconOpacity` 0.4 (`FOG_LABEL_OPACITY`, the web's own value — `docs/IMPLEMENTATION.md` §4.2) and every other mode, and `setRecording`, setting them back to 1, the default the served style never overrides. Heatmap quiets the basemap the same way, with the web's `heatmap-dim` (root `docs/IMPLEMENTATION.md` §4.2.2): a `BackgroundLayer` that `addCoverage` inserts before any heat layer, so all of them paint above it — cream `#f7f4ec` at 0.45 on the light map, black at 0.35 on the dark one and over satellite (the same `darkVeil` that picks Fog's veil, so `setDarkVeil` and `refreshCoverage` re-add it with the other color) — and `setMode` shows in Heatmap only. It's switched by its opacity (0 when off), not its visibility, unlike every other layer here: MapLibre Native doesn't draw a background layer again once it has been hidden, so the second switch to Heatmap had no wash. This keeps mode switching instantaneous and avoids re-adding sources on every toggle; since `attach` ends with `setMode`, a style reload re-applies the dimming too.
- **Only the tracks URL carries a filter, and only `from`/`to`.** `attach` takes the selected `DateRange` (null before the default is known, which is the whole history) and appends it to the tracks template; fog and heatmap stay bare, since neither mode is narrowed on the web either. `types`/`exclude` are never sent: TYPE/DISTANCE and the hidden set are applied on the device, as layer filters, as the web applies them (below). **`setTrackRange` replaces the tracks layer and source** rather than updating them, because MapLibre Native 13's `VectorSource` has no way to change its tile URL (no `setTiles`, checked against the AAR's classes) — removed and re-added below the first label layer, which keeps it above the rasters, with the old layer's visibility carried over so a mode or a recording in progress is respected.
- **The selected track is two more layers, not feature-state.** The web bolds the selected track with MapLibre GL's feature-state (`tracks.ts`'s `selected`, widening the line and showing a `tracks-casing` halo under it); MapLibre Native Android has no feature-state API, so `addTracks` adds three line layers on the one source, in paint order: `tracks-casing` (#202b25 at 0.95, 7.5dp — the web's `CASING_WIDTH`), `tracks-line`, and `tracks-selected` (4.5dp, the web's `EMPHASIS_WIDTH`), the first and last filtered to `in(id, selected)` — the selected track, or every checked one while selecting (`PanelState.highlighted`). `setTrackFilter(style, hidden, selected)` is the web's `setHiddenTracks` plus `setSelectedTracks`: `tracks-line` gets `!in(id, hidden)` (`literal(true)` when nothing is hidden), and the selected layers leave out any track that's itself hidden. The two values are kept on the object, since `setTrackRange` replaces all three layers and `addTracks` re-applies them; `setMode` and `setRecording` show and hide the three together (`TRACK_LAYER_IDS`). The tile's `id` property is the activity's UUID as text, the same string `GET /v1/activities` returns.
- **The selected track's bands are a GeoJSON layer**, `track-bands` — the web's `trackBands.ts` source and layer: one `LineString` feature per band run carrying its colour, painted with `line-color: get("color")` at 6dp over every track layer (`attach` adds it after the tracks; `setTrackRange` re-inserts the tracks under it). `setTrackBands(style, points, metric)` rebuilds the features from `map/TrackBands` — the web's band rules as a plain object (`scale`, `bandIndex`, `runs`), unit-tested — and `clearTrackBands` empties it. `setMode` and `setRecording` show and hide it with the tracks.
- **Refreshing tiles means a new URL.** Every tile URL carries the account's tile version as `cv` (`Session.tileVersion`), under which the server lets MapLibre keep the tile for good (root `docs/IMPLEMENTATION.md` §4.2.6), so a change shows up only at a new version, or for tracks, a new `v`. The version is kept on disk: a cold start attaches the overlays at the last one read, so MapLibre's cache draws at once, then `MapFragment.checkTileVersion` reads `GET /v1/coverage/status` once and refreshes everything only if it moved. `refreshTracks` also bumps `tracksVersion`, sent as `v` (which the server ignores), the web's `tracksVersion`: a change the app hasn't read a new version for yet (a type edit) would otherwise be answered from that cache. Fog and Heatmap have no counter of their own; `CoverageWatch` stores each status's version before it refetches. `refreshCoverage` removes and re-adds every Fog and Heatmap layer and source (`COVERAGE_LAYERS`), below `tracks-casing` so they stay under the tracks, with each layer's old visibility. `map/CoverageWatch` is `useCoverageRefresh.ts`: it polls `GET /v1/coverage/status` after a change and calls `refreshCoverage` once nothing is left rendering — and mid-job whenever the status `version` moves — restarting on every call. Reads go every 2 seconds for 90 reads, then every 10 (the web's `coveragePoll.ts`), a failed read included, until one finds nothing left. `checkTileVersion` — on attaching the overlays and now on every `onResume` too — starts a watch when its read finds the account still rendering, so an import made on the web or a sync still draining is followed to its end. Each read's `rendering` goes to `MapFragment.renderCoverageNotice`, which shows `coverage_notice` (the level notice's style, on a line above it) in Fog and Heatmap while it's true and the mode bar is up.
- **Fog and Heatmap say what they show** in `mode_chip` (`Widget.HoldMyTrack.ModeChip`), centred 32dp above the map's bottom, clear of MapLibre's logo and the raised record button: "Every activity, any date" or "The last 365 days", since neither takes the date range and the panel is gone. `renderModeChip` shows it once the session allows, not while recording, and runs from `setMode`, `renderModeBar` and `renderRecording`.
- **The level in view is named by `map/ZoomLevelNotice`**, the web's `ZoomLevelNotice.tsx` (root `docs/IMPLEMENTATION.md` §4.2.4): `MapOverlays.zoomTier(zoom)` maps a zoom to the same three bands the Country, Region and City layers switch on (`ZoomTier`, unit-tested against the boundaries), and the notice — a `TextView` in `top_chrome` under the second row, `Widget.HoldMyTrack.ZoomLevelNotice` after the web's pill — shows `map_level_<mode>_<tier>` whenever the mode or tier differs from what it last showed, fading out after 3 s (`SHOW_MS`, 400ms fades). `MapFragment` passes the zoom on camera idle, so a pinch through two levels names only where it lands, and the mode from `setMode` and `renderModeBar`, with `active` false before the session is verified and while recording, which also forgets what was shown, so the next entry names the level again. Not clickable, so the map takes touches through it.
- **`TRACK_COLOR = "#b07e2e"` is called out in its own comment as not a token to fold into a future design system** — it is the color `apps/web/src/map/tracks.ts` paints tracks with, and belongs to the shared map style's visual identity across clients, not to this app's own theming.

### 3.2 The Activities panel (`panel/`)

The web's phone Activities panel (`apps/web/src/ui/ActivitiesPanel.tsx` and index.css's `max-width: 768px` layer; `apps/android/docs/SPEC.md` FR-2.7), ported rule for rule and laid out after the web's own DOM, one XML block per web element (`include_activities_sheet.xml`, `item_activity_row.xml`, `popup_type_filter.xml`, `item_type_filter.xml`).

- **Three pieces, split where the web splits them.** `PanelState` is the state the web keeps in `MapView.tsx` — the list, the checked group, the one selected id, the session's hidden set, the excluded types, the distance band — with its rules as methods (`targetIds`, `mapHidden`, `checkAll`, `invertChecked`, `toggleTargetVisibility`, `resetForNewRange`). `ActivityFacets` is `activityFacets.ts`. The list's note (loading, none match, a failed read) is a second adapter after the rows (`ConcatAdapter`), as the web's is a last `<li>` — not drawn over the list, where a failed poll would write it across the first row. `MapFragment` owns the map and the fetch and plays `MapView.tsx`'s part: `loadActivities` (`GET /v1/activities?from=&to=` through `HoldMyTrackApi.activities`, plus duplicates), `applyTrackFilter` (the state's `mapHidden` and `focused` onto `MapOverlays.setTrackFilter`) as the panel's `onMapChanged`, and `flyToActivities` as its `onFly`.

A drag that comes to rest sets `expanded` itself. The content is never removed, only covered, so the list keeps its scroll position. `hold(down)` collapses it and turns its drag off without forgetting `expanded`, for an edit window over the map (the web's `.edit-track-lock`); `MapFragment.collapseSheetOnBack` collapses an open sheet on Back. `MainActivity.showTab` moves the panel between its tabs for the bottom bar (Stories, Map); a recreation brings the panel back on Activities, so the bar's Stories puts it back on its own.

### 3.3 Spots (`map/MapSpots`, `map/SpotPopup`, `map/ShowInArea`)

The web's `map/spots.ts`, `SpotPopup.tsx` and `ShowInArea.tsx` (root `docs/IMPLEMENTATION.md` §4.25), on the same tiles and `GET /v1/spots`.

- **`MapSpots` is the layers and the choice.** `Category` is the five in the menu's order, each with its wire name, icon and two labels (the menu's plural, the popup's singular). The choice is a string set in SharedPreferences (`map_spots`, empty by default). `attach` — called by `MapFragment` right after `MapOverlays.attach`, so on every style load — adds the badge images, the `spots` vector source (`/tiles/v1/spots`, z13–14, `cv` from `Session.tileVersion`), the `spots-in-area` GeoJSON source and five layers with the web's ids and order: the areas' fill (the accent at 0.15), their solid outline, the circles' dashed edge (two line layers, a dash pattern can't vary per feature), Show in this area's badges (z10–13) and the tiles' badges (z13 up). They're added with `addLayer`, on top of everything, and `add` puts a layer back under the first of those above it already on the map, which `refresh` relies on: `checkTileVersion` calls it when the version moves (an import bumps it), replacing the tile source and its four layers since a vector source's URL can't change. `apply` gives every layer an `in(category, literal(wanted))` filter — the lines also on `to-boolean(circle)` — and hides all five with nothing ticked or while a track is edited (`setEditing`, from `startEditTrack`/`onEditClosed`). `MapOverlays.setLabelOpacity` skips `BADGE_LAYER_IDS`, the only symbol layers not the basemap's.
- **The badges are bitmaps drawn once per style load**, since a style reload drops its images: a 30dp white circle ringed 2 units in the accent, the category's icon (`ic_seesaw`, `ic_dog`, `ic_landmark`, `ic_binoculars`, `ic_castle` — Lucide, and the web's own seesaw) tinted ink in the middle 16 of 30 units, added as `spot-{category}` at the display's density, and again as `spot-captured-{category}` — the accent circle ringed darker, the icon white. `iconAllowOverlap` and `iconIgnorePlacement` draw every one. `MapSpots.captured` holds the account's captures (id → time), which `MapFragment.loadSpotCaptures` reads from `GET /v1/spots/captures` when the overlays attach and on every `onResume`; `apply` sets both badge layers' `iconImage` to a `switch-case` on `in(to-number(id), literal(captured ids))` (`isCaptured`), and gives the four tile layers `any(!to-boolean(retired), isCaptured)` beside the category filter, so a retired place (ADR-0027) shows only to whoever captured it; Show in this area's layer needs no such clause, since the server already left the rest out. `setCaptured` re-runs `apply`, so a new capture updates both.
- **`spotAt`** queries the visible badge layers in a box 4dp around the tap and turns the feature into the API's `Spot`. `onMapTap` asks it first, before the Activities panel's own handling and in every mode, unless the Private location editor or the Edit window has the map: a hit opens the popup and stops there, anything else closes it.
- **`SpotPopup` is a view, not a MapLibre annotation**: `view_spot_popup`, 272dp, included right after the `MapView` so all the chrome stays over it. `place` puts it centred above the spot's screen point, 18dp off, clamped to 12dp gutters, or under the point when its top would pass `top_chrome`'s bottom; it runs on every camera move and whenever the popup's height changes (a layout listener, since new content is placed before it's measured). Description and inscription are `maxLines` 6 with `ScrollingMovementMethod`. Copy address goes through `ClipboardManager`, labelled Copy location for a place without an address; Wikipedia is an `ACTION_VIEW`. `renderCaptured` shows the captured line, the date in the phone's medium format, from `MapSpots.captured` — run on `show` and again when the captures arrive. The text rules — the address or `lat, lon` to six places, the Wikipedia URL encoded like `encodeURIComponent`, the memorial type as words — are `map/SpotText`, unit-tested (`SpotTextTest`).
- **`ShowInArea`** is the pill (`show_in_area`, a `TextView` centred in the top row's start column under the mode toggle, so it wraps rather than running under the rail). It keeps the web component's state — the categories and zoom, the last load (its categories, how many shown and in all), `moved`, `loading`, `failed` — and renders the button or the status line from it; `MapFragment` feeds it the camera's idle events and the ticked categories. A tap reads `visibleRegion.latLngBounds` and calls `HoldMyTrackApi.spotsInArea`; since those calls can't be cancelled, a request counter drops any answer but the latest. The places go to `MapSpots.setInArea`, which also keeps them for the next style load.
- **Capture mode is `map/CaptureMode`** (FR-2.8 item 6, ADR-0023), which `MapFragment` owns. `SpotPopup`'s Capture calls `onCaptureTap`, which asks for `ACCESS_FINE_LOCATION` (its own launcher, `capturePermissionLauncher`: a 25 m fix needs precise location) and calls `start`. `start` sets `FLAG_KEEP_SCREEN_ON`, enables an `OnBackPressedCallback`, shows the banner (`view_capture_banner`, the last child of `top_chrome`), calls `MapSpots.setCapturing` and fetches `HoldMyTrackApi.spotDetail` — the place's whole area, retried every 5 s on a failure — into a `SpotCapture`. While `MapFragment` is resumed (`resume`/`pause`, from its own) it listens on `LocationManager.GPS_PROVIDER` at 1 s, the provider `RecordingService` uses, and on `TYPE_ROTATION_VECTOR` for the heading (`getOrientation`'s azimuth plus the display's rotation, smoothed by a fifth each event the short way round); the arrow's rotation is the bearing to the place minus the heading, or minus the camera's bearing without the sensor. It turns on MapLibre's `LocationComponent` with `RenderMode.COMPASS` and `CameraMode.NONE`, and turns it back off on `stop` unless Find my location had it on. Each fix goes to `SpotCapture.onFix` with its `elapsedRealtimeNanos`; `Away` draws the guide line (`MapSpots.setGuide`) and, the first time, fits the user, the line's end and the anchor through `MapFragment.flyTo`, whose top inset includes the banner. `Captured` fires a `CONFIRM` haptic and `HoldMyTrackApi.captureSpot` with the last fix inside: success adds it to `MapSpots.captured` and re-renders the popup's captured line, then `stop` after 2.5 s; a `422` resets the count; anything else retries every 5 s. A place retired since the map loaded it — a `404` from `spotDetail` (the endpoint hides it from an account that hasn't captured it) or a `410` from `captureSpot` — goes to `gone`, which stops listening, clears `capture` so `resume` doesn't start again, shows `spots_capture_gone` and calls `stop` after 4 s (`GONE_MS`). `stop` undoes all of it; `startEditTrack`, `setSpots` (the place's category unticked) and `onDestroy` call it, and `onStyleAttached` puts the darker areas back after a style reload.
- **`SpotCapture` and `SpotGeometry` are plain Kotlin**, unit-tested on the JVM (`SpotCaptureTest`, `SpotGeometryTest`). `SpotGeometry` works on `GeoPoint`s and a `SpotArea` (polygons of closed rings, as `GET /v1/spots/{id}`'s GeoJSON has them): `contains` is even-odd ray casting over each polygon's outer ring minus its holes; `distanceM` and `nearestPoint` project every edge onto a plane centred on the position (equirectangular, x scaled by the cosine of latitude — well under a metre off across a place's few hundred metres) and clamp the position's projection to each segment; `bearing` is the great-circle initial bearing. `SpotCapture`'s states are `Locating`, `Away` (distance, bearing, and the line's two ends), `Holding` (ms held) and `Captured` (the fix). A fix with no accuracy or worse than 25 m is dropped; a fix inside adds the time since the previous one inside, at most 3 s, so a gap while the app was away counts for little; a fix outside zeroes the count.
- **`MapSpots.setCapturing`** records the target and re-applies: the areas' `fillOpacity` becomes a `switch-case` on `id` — 0.55 for the target, 0.35 for the rest, against 0.15 normally — and both edge layers' `lineWidth` stops double for the target. The guide is its own GeoJSON source and dashed line layer, `spots-capture-guide`, added under the badges and outside `LAYER_IDS`, since it isn't filtered by category and `refresh` has no reason to touch it; it shows only while there's a target and the spots are shown.
- **The Layers menu's group** is five checkboxes in `popup_layers`, now inside a `ScrollView` for a landscape screen. `LayersMenu` counts the ticked categories with the paths, and `MapFragment.setSpots` saves the choice, re-filters the layers, closes an open popup whose category is no longer drawn, and tells `ShowInArea`.

Capture mode was checked on the emulator against the dev stack with the extract, positions set with `adb emu geo fix`: from 200 m out the banner's distance and arrow, the darker areas, the guide line and the camera fitting both ends under the banner; inside, the count to 30 s, the capture reaching the server, the badge filled after a restart and the popup's Captured line with no Capture button; Stop clearing the banner, the dot and the darker areas, with the GPS registration and the screen-on flag gone. The earlier check: the badges at zoom 14, a playground's popup (titled by its category, Copy address copying coordinates) and a monument's, Show in this area at zoom 12.96 loading 68 places, and in Fog the badges over the veil at full strength and still tappable.

### 3.4 Photos (`photos/`, `map/PhotoMarkers`, `map/PhotoPopup`, `panel/PhotosTab`)

The web's photos (root `docs/IMPLEMENTATION.md` §4.27, ADR-0024), against the same `/v1/photos` endpoints, with no Android-only server work.

- **Five pure pieces in `photos/`, ported line for line.** `PhotoExifFields` is `photoPrep.ts`'s `readExif` less the byte parsing: the time and zone rules over the tag values `android.media.ExifInterface` reads — OffsetTimeOriginal for the zone, else the camera clock minus the GPS clock rounded to 15 minutes, else a zoneless `taken_local`; zero positions and all-zero dates read as absent. `PhotoTrack` is `photoTrack.ts` (`pointAt`, `fractionAt`, `startFraction` with its `PlaceAnchor`s), `PhotoDraft` is `photoDraft.ts` as an immutable data class whose `with…` methods hold the web tab's change rules (a change back to what's saved is no change), and `PhotoClusters` is `photoClusters.ts`. None has an Android type, so `app/src/test` covers them.
- **`PhotoPrep` prepares a picked photo** off the main thread: the EXIF through `ExifInterface` (JPEG, HEIC and WebP alike, where the web reads JPEG only), then `ImageDecoder` decoding it upright by its orientation, scaled to 2048 px on its long side while decoding, so a large photo is never held at full size, a 320 px thumbnail scaled from that, and both re-encoded as WebP at 85 — re-encoding drops every EXIF field. A file `ImageDecoder` can't read is `UnreadablePhotoException`. `PhotoImages` keeps fetched thumbnails in an 8 MB `LruCache`, coalescing requests for one path, since markers are rebuilt on every regrouping and the tab's rows show the same images.
- **`MapFragment` owns the photos**, as the web's `MapView` does: `refreshPhotos` works out the scope — Normal mode only; the Edit window's one activity while it's open (none for a group), else the selected activity, else the open Story — and reads `GET /v1/photos` when it moves, or with `force` when the photos may have changed under it: a save from the Photos tab, the selected activity's reprocess landing (`updateTrackMetrics(refetch)`, the web's `trackMetricsVersion`), a Private location change, a Story's members changing, a delete. A generation counter drops a superseded answer, and a new scope starts empty. `renderPhotoMarkers` merges the Photos tab's `PhotoMarkerOverlay` over the saved photos and hands them to `PhotoMarkers` — none on the Track tab (`EditActivityWindow.showingTrack`), for a hidden route, or while recording, when every history layer steps aside.
- **`PhotoMarkers` are views, not a symbol layer**, as the web's are HTML markers: `photo_markers`, a pass-through `FrameLayout` over the map and under the popups and chrome, holds one `PhotoMarkerView` per group, keyed by its ids. The view draws the thumbnail with a `BitmapShader` cropped into a 36dp circle (52dp when active) in a 2dp ring, two cards' edges behind a group and the count badge on its corner, inside a square padded 12dp all round so its touch target is past 48dp and its shadow is the circle's (an oval outline). `regroup` runs `PhotoClusters` over the projected points on every camera idle, with the photo in hand left out of every group; `place` only moves the views, on every camera move. A marker's tap is the view's, so the map's own tap handling never sees it and the selection stays.
- **A group's tap is `openPhotoMarker`**: more than 15 m across (`PHOTO_GROUP_SPREAD_M`), `flyTo` fits it with a zoom cap of 19 instead of the usual 15; otherwise `PhotoPopup` opens on it. The popup is `SpotPopup`'s pattern — `view_photo_popup` placed above the group's first photo, or under it without room, and placed again on every camera move and once its picture has its size — with the thumbnail standing in until the stored copy arrives through `image(url, maxSide)`. Full size and a tap on the picture open `PhotoViewer`, an `AppCompatDialog` in its own edge-to-edge theme (`Theme.HoldMyTrack.PhotoViewer`, dark in both themes) whose bars are padded by the system-bar insets; the web's Full size opens a browser tab, which here would have no session. The viewer starts from the copy the popup already holds (or the cached thumbnail) and swaps in the stored copy, decoded unsampled, when it arrives; `onIndex` steps the popup with it, and `retain` hands it the refreshed group. Its picture is `ZoomImageView`, which draws the bitmap through a `Matrix` built from `photos/PhotoZoom`, the web's `photoZoom.ts` ported line for line: a view `{scale, x, y}` over the fitted size (contain, never upscaled), with `zoomAt`, `panBy` and `clamp` bounding the scale to 1–8 and the offset to the overhang past the screen. A `ScaleGestureDetector` zooms about the pinch's focus, a `GestureDetector`'s scroll pans and its double tap zooms, and the buttons' steps and the double tap animate over 180 ms. The fit is worked from the photo's own `width`/`height`, not the bitmap's, so the swap from the smaller copy keeps the zoom. The icon buttons' tint has no disabled state, so a disabled one is dimmed to 35%, as the popup's ‹ › are. `retain` keeps the popup on the photos still in view after a refresh and closes it when none is.
- **The Photos tab (`include_photos_tab`) edits `PhotosTab.draft`**, and `EditActivityWindow` writes it between the fields and the track edit; `photosSaved` survives a failure, so a Cancel after a partial save still has the map refetch. ## 4. Health Connect Integration

### 4.1 `health/HealthConnect`

Two things live here: the three permission constants, and the `Readiness` state machine (`docs/SPEC.md` FR-3.1 specifies the six states from the user's perspective).

- **`READ_EXERCISE_ROUTES` is a raw string constant**, not a library-provided one — `androidx.health.connect` ships a write-side constant for this permission but no read-side one, consistent with a permission the platform won't let an app request programmatically in the first place (verified directly: requesting it alongside the other two silently omits it from what's granted, without ever raising an error).
- **`READ_HISTORY` uses the library's own constant** (`HealthPermission.PERMISSION_READ_HEALTH_DATA_HISTORY`) because, unlike routes, it *is* programmatically requestable — it rides in the same permission-request call as `READ_EXERCISE`.
- **`readiness(context)` is computed fresh on every call, never cached** — the routes permission specifically can only be granted by leaving this app (into Health Connect's settings) and coming back, so caching it across that trip would show a stale state at the exact moment the user needs to see it update.
- **`settingsIntent()` targets Health Connect's home screen (`HEALTH_HOME_SETTINGS`), not its per-app permission page.** The obvious API for the latter, `ACTION_MANAGE_HEALTH_PERMISSIONS`, is guarded by the signature-level `GRANT_RUNTIME_PERMISSIONS` permission — an ordinary app calling it gets a `SecurityException` that kills the process. This was found by hitting the crash on a device, then confirmed a second way by querying the intent resolver directly, and is why `SyncActivity`'s onboarding screen has to spell out the four-tap path by hand instead of deep-linking to it.

### 4.2 `health/ExerciseTypes`

A hand-written `Map<Int, String>` from Health Connect's `EXERCISE_TYPE_*` constants to HoldMyTrack's `activity_type` vocabulary.

- **Written against public constants, not the library's own `EXERCISE_TYPE_INT_TO_STRING_MAP`**, which exists and would save writing this table out, but is annotated `@RestrictTo` (library-group internal, removable without a semver bump) — a dependency this code doesn't want to take. Every entry is a named constant on the left-hand side rather than a bare integer literal specifically so a transcription mistake is a compile error, not a silently mislabeled activity type at runtime.
- **A handful of entries deliberately rename Health Connect's own term**: `EXERCISE_TYPE_BIKING`/`BIKING_STATIONARY` → `"cycling"`, `RUNNING_TREADMILL` → `"running"`, both `SWIMMING_OPEN_WATER`/`SWIMMING_POOL` → `"swimming"`. These renames exist because HoldMyTrack's other ingest paths already speak the FIT-file vocabulary, and a mismatch here would split one real activity type into two in the Activities panel's TYPE filter, which is the reason that remains now that cross-source deduplication (`docs/IMPLEMENTATION.md` §4.6) matches on time overlap rather than type.
- **`name()` falls back to `"unknown"`** for any exercise type this table doesn't cover — the same fallback value the server itself uses for an activity that arrives with no type at all, so an unmapped Health Connect constant degrades to a value already meaningful elsewhere in the system rather than to something new.
- **Indoor types are included for completeness, not because they're ever sent**: a session with no route never reaches `prepare()` in `SyncRunner` at all (§5.2), so in practice only outdoor types are ever looked up here.

### 4.3 AndroidManifest permission declarations

Exactly three Health Connect permission declarations, matching `health.HealthConnect`'s three constants one-to-one, and no more — deliberately, since declaring an unused data type is a documented Play Store rejection cause (`docs/VISION.md` §7). `READ_HEALTH_DATA_IN_BACKGROUND` is conspicuously absent: measured on a device, granting it changes nothing for route reads (the same 46-session test returned 23 routes in the foreground and zero in the background whether or not this was granted), so declaring it would only be asking for an alarming-sounding permission that buys the app nothing.

`SyncActivity` carries two manifest-level registrations beyond being a normal exported activity: an intent filter for `androidx.health.ACTION_SHOW_PERMISSIONS_RATIONALE` (Health Connect launches this screen itself to show its own rationale for the request, and without a registered handler the permission dialog can refuse to appear at all — found on a device), and an `activity-alias` named `ViewPermissionUsageActivity`, guarded by `START_VIEW_PERMISSION_USAGE` and targeting `SyncActivity`, which is where Health Connect's own "see how this app used your data" link lands. Arriving by either (`RATIONALE_ACTIONS`), `SyncFragment.onViewCreated` opens the rationale dialog (`showRationale`) straight away — only on a fresh start, not after a rotation, so a dismissed dialog stays dismissed; on the Sync tab it waits behind the info button (`sync_health_connect_info`, Lucide `info`) beside the Health Connect heading. The dialog's neutral button opens `/privacy` in a Custom Tab (`HoldMyTrackApi.webPageUri`), the policy Health Connect requires this screen to lead to.

## 5. Sync Engine

### 5.1 `SyncFragment`

The Sync screen (`docs/SPEC.md` FR-3.5, FR-4) — `MainActivity`'s Sync tab, and the whole of `SyncActivity` (`activity_sync`), which hosts the same fragment alone for Health Connect's entry points (above), signed out included. Its run is cancelled in `onStop` and in `onHiddenChanged` when another tab hides it, and a hidden one reads nothing on a resume, waiting until it shows again: Health Connect's onboarding, the recorded-activity rows, the history under them (§6), and the run's lifecycle owner. `render()` handles the account gates (signed out, unconfirmed, demo) and hands the rest to `renderHealthConnect()`, the six-state switch `docs/SPEC.md` FR-3.1 specifies from the outside; the implementation details worth calling out beyond that spec:

- **Two sources, one button, nothing to choose.** Sync now sends everything there is: Health Connect whenever `includesHealthConnect()` (Ready, or needs-history, which syncs 30 days), and every row of `recording/RecordedActivityRows` (§7.1.1). Those two decide `updateSyncNow()`, which every row change and run start/end calls. `startSync()` only asks for a Health Connect client when `includesHealthConnect()`, and `show()` takes a nullable `SyncReport` for a recordings-only run. Each setup state has one action, the section's `sync_primary` button; there is no separate "Open Health Connect" beside it.
- **`refresh()` is a no-op while `syncJob` is non-null.** Readiness is re-derived on every `onResume`, and a running sync's own coroutine doesn't want its buttons and status text stomped by a concurrent readiness re-render.
- **`onStop` cancels `syncJob` unconditionally.** This is not cleanup after the fact — it *is* the foreground boundary the whole sync design depends on (`docs/ARCHITECTURE.md` §1.1). Because `SyncCursor` only ever advances over confirmed-terminal segments (§5.3), cancellation here is safe by construction: there is no in-flight, half-applied watermark state for `onStop` to worry about tearing down.
- **An unconfirmed email hides everything**, as a signed-out session does — see §2.4.
- **Cards on cream**: `fragment_sync` is the phone design's screen — a serif title (`TextAppearance.HoldMyTrack.ScreenTitle`), then cards (`bg_section_card`, the surface at `hmt_radius_card`) under `Widget.HoldMyTrack.SectionHeading`s, 20dp apart (`gap_20`). The account gate is its own notice (`sync_account_notice`). The Sync now card (`sync_hero`) is drawn by `updateSyncNow`, which every row change and run start and end calls: the heading (`sync_headline`) says what's waiting (the `sync_waiting` plural) or "Syncing…", the line under it (`sync_detail`, `showDetail`) what a run would also read — Health Connect, with `lastSyncedLabel` — or, mid-run, its progress (`showProgress`), with an indeterminate `LinearProgressIndicator` (`sync_progress`) while `syncJob` is set; Sync now is `Widget.HoldMyTrack.Button.Hero`, an ink pill (`hero_button_bg`/`_text`). What the run did goes under the button (`sync_results`, `showResults`), and what it couldn't do — rejections, an early stop, or the whole run throwing — in the error box (`sync_problems`, `showProblems`), both selectable; it stays there rather than in the heading, which the `refresh()` in `startSync`'s `finally` puts back. Health Connect's card is a `bg_status_dot` tinted by state, `sync_status_title`, and `sync_status`, which `showStatus` writes — in the danger color for a failure — with the step (`sync_instructions`, `sync_primary`) under them. Bring in files (`sync_files_section`) is two `Widget.HoldMyTrack.Tile`s that start `UploadActivity` and a bare `TimelineImportActivity`; it, the Sync now card and the Health Connect card are gone for the demo account. Checked on the emulator in dark mode, signed in with Health Connect not yet permitted and as the demo account.
- **`openSettings()` catches broadly (`Exception`, not just `ActivityNotFoundException`)** because the actual failure encountered in development was a `SecurityException` from an earlier attempt at `ACTION_MANAGE_HEALTH_PERMISSIONS` (§4.1) — a button that can't open a screen reports that in the status text rather than crashing the app around it.

### 5.2 `sync/SyncRunner`

One foreground run: page through Health Connect ascending from the watermark, classify each record, batch and post the ones with usable geometry, and advance the watermark only over what's confirmed.

- **The classification into terminal vs. blocking happens inline in the paging loop**, not as a separate pass — `ExerciseRouteResult.Data` is prepared and added to the pending batch; `NoData` is counted and added straight to the current *segment* (eligible for the watermark) without ever entering a batch; anything else (`ConsentRequired`) sets `stoppedBecause` and breaks out of the paging loop entirely, mid-page if necessary.
- **`segment` and `batch` are different lists with different lifetimes.** `segment` accumulates every record dealt with since the watermark last moved (both route and no-route ones) and is what `advanceOverSegment()` reads to compute the new watermark position; `batch`/`batchRecords`/`batchPoints` accumulate only records with geometry, pending a `POST` to the sync endpoint, and are cleared on every `flush()` regardless of outcome. A record is only removed from active tracking once it's in `segment` — meaning a record that fails preparation (too many/too few points) still lands in `segment`, because that rejection is itself terminal (§5.3).
- **`flush()` is called both when a batch limit is hit mid-page and once, unconditionally, after the paging loop ends** — the second call is what sends whatever was still buffered when the loop stopped, including when it stopped because of a blocking record: everything gathered *before* that record is still legitimately finished with and must not be abandoned just because something later in the page couldn't be read.
- **A failed request inside `flush()` clears the batch without moving the watermark**, and returns the exception's message as the stop reason. Nothing in an unanswered batch is terminal — the request might succeed on retry, so guessing either way (assume success and advance, or assume failure and skip) is exactly the mistake `SyncCursor`'s design exists to prevent.
- **`prepare()` builds each activity's JSON off the main thread** (`Dispatchers.Default`), because a long ride's point array is real serialization work — tens of thousands of points is the documented ceiling this file itself checks against (`MAX_POINTS_PER_ACTIVITY = 50_000`, matching the server's own limit in `docs/IMPLEMENTATION.md` §4.0.3, checked client-side so a record that could never be accepted is reported as a rejection instead of being sent only to be refused).
- **Elevation is included per-point only when the platform location object actually carries it**; there is no default-to-zero, because zero is a real, wrong value for "unknown altitude" (a hazard the file's own comment calls out explicitly).
- **Batch limits (25 activities / 20,000 points) are stricter than the server's own ceiling (100 activities per request)**, deliberately: a smaller batch keeps a single mobile-data request modest, and makes the watermark advance more often during a long first backfill — a larger batch would mean more work re-attempted if any single request failed.

### 5.3 `sync/SyncCursor`

The watermark itself: an `Instant` plus a `Set<String>` of record ids already handled at that exact instant, persisted per account in its own `SharedPreferences` file (`holdmytrack.sync`).

- **A bare instant is not sufficient as a position, and this is the one subtlety in the whole sync engine worth re-reading before touching it.** Health Connect's `TimeRangeFilter.after(instant)` is *inclusive* of that instant, so the record the cursor is parked on is read again on the very next run. Simply excluding that instant from the next read would be wrong in the other direction, because two distinct sessions can genuinely share an identical start time — excluding the instant outright would silently drop whichever sibling didn't happen to set the watermark. `handledAtCursor` is the set of ids already dealt with at exactly that instant, and it's what lets the next run skip only those specific records while still picking up any newly-appearing sibling at the same instant.
- **`advanceTo` merges rather than replaces `handledAtCursor` when the new instant equals the current one.** Two sessions sharing a start time can land in different batches within the same run (if a batch-size limit falls between them), and each `flush()`/`advanceOverSegment()` call advances the watermark independently — so the ids recorded for a given instant have to accumulate across calls within a run, not just across runs.
- **`advanceTo` refuses to move backwards.** Defensive against a run that, for whatever reason, reads a narrower window than a previous run already covered — moving the watermark earlier would re-open a range of history already confirmed closed.
- **Keyed by account (email string, empty for a demo account) rather than globally**, in its own preference keys (`at.$account`, `ids.$account`) inside one shared file — this is what prevents two people using the same physical device from inheriting each other's sync position, and what lets the same account resume correctly across a sign-out/sign-in cycle.
- **`reset()` exists but has no UI entry point today** — it's the mechanism a full re-walk would use, relying on the server's idempotency (keyed on the platform's own record id, not a content hash — `docs/IMPLEMENTATION.md` §4.0.3) to make that safe, but nothing in the app currently calls it.


### 5.4 `UploadActivity` and `imports/FileImports` — uploading files

The Upload screen (`apps/android/docs/SPEC.md` FR-3.6), from Sync's Upload files tile, is the web's Upload menu (`services/server/internal/web/static/upload.js`) ported, against the same `POST /v1/activities/upload` (root `docs/IMPLEMENTATION.md` §4.0.1), with no Android-only server work.

- **A process-wide object, not the screen's.** `FileImports` holds the queue, the transfers and the notes and runs on its own `CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`, so an upload outlives a rotation or a trip to another app, unlike a Health Connect run, which `onStop` cancels on purpose (§5.1). `UploadActivity` registers a listener in `onStart`, removes it in `onStop`, and redraws from `transfers` and `notes` on each change (`render`). `sentCount` moves each time a file has gone, and once it's above zero the screen shows Follow them in Sync, which opens the Sync tab (`MainActivity.openTab`); its history reads the jobs on start and polls while they process (§6).
- **`enqueue` is `upload.js`'s `enqueue`**: a `.json` goes to the Timeline screen instead (§5.5) and nothing else picked with it is queued; more than `MAX_PLAIN_FILES` (20) non-zip files are refused, keeping any `.zip`. Two checks the web doesn't make: a name that isn't `.gpx`/`.fit`/`.tcx`/`.zip` gets a note rather than being dropped silently, and a file over the server's limit (64 MiB, 512 MiB for a `.zip`, `services/server/internal/httpapi/server.go`) is refused before it's sent. Names and sizes come from `OpenableColumns`; a size the provider doesn't give is -1, sent without a length and shown in MB.
- **The picker asks for `*/*`.** Providers label these files inconsistently — the emulator's Downloads called a `.gpx` a "BIN file", `application/octet-stream` — so filtering by MIME type would hide the very files asked for, and `enqueue` decides by name instead.
- **One file at a time**, as on the web. `HoldMyTrackApi.uploadActivityFile` streams the file into the multipart body (`UriRequestBody`, read 64 KiB at a time from `ContentResolver.openInputStream`, and opened afresh on each `writeTo`, so OkHttp's retry resends all of it) rather than reading it into memory, since a `.zip` can be 512 MiB. Progress comes back on OkHttp's thread and is posted to the main thread once per percent. The call goes through `uploadClient`, the app's client with a 2-minute write and 10-minute read timeout: the server answers once it has stored the file, which for a large archive is longer than the default ten seconds.
- **`UploadOutcome`** is what the response says: `already_processed` for a file, noted as the web notes it, and for an archive `zip_accepted` with its `batch`. The server unpacks an archive in the background (root `docs/IMPLEMENTATION.md` §4.0.1), so what the history won't show about its files comes later: `FileImports` keeps each archive it sent in `unpacking`, by batch, and while any is there polls `GET /v1/uploads/active` every 2 seconds (`pollUnpacking`, `HoldMyTrackApi.unpackedArchives`). An `UnpackedArchive` with a batch of its own becomes the web's notes — already imported, skipped, truncated, or "{file}: {reason}" for one that couldn't be unpacked — and leaves `unpacking`. `unpacking` is process-wide, like the queue, so a note still arrives after the Upload screen is left; one for an archive sent before the process was killed is lost. A non-2xx answer is an `ApiException` with the server's own text, noted as "{file}: {reason}".
- **Opened or shared files.** `UploadActivity` has `VIEW` and `SEND`/`SEND_MULTIPLE` filters for `application/gpx+xml`, `application/vnd.garmin.tcx+xml`, `application/zip` and `application/x-zip-compressed`; `importShared` (from `onCreate` and `onNewIntent`) hands their URIs to `enqueue` when `canUpload()`. A `.fit` has no MIME type apps agree on, and most hand a `.gpx` over as `application/octet-stream`, which the app doesn't claim, since it would then offer itself for every binary file; those are picked in the screen. The system Files app opens a `.zip` itself on a tap, so sharing it is the way in from there.
- **The two guides** — `/help/google-health-export` and `/help/timeline-export` (root `docs/SPEC.md` FR-10.5) — open in a Custom Tab from link buttons, through `HoldMyTrackApi.webPageUri`, like the menu's web pages.

### 5.5 `timeline/` — the Google Maps Timeline import

The web's Timeline import (root `docs/IMPLEMENTATION.md` §4.0.5, `apps/web/src/timeline/reader.ts`, `TimelineImportWindow.tsx`) as `TimelineImportActivity` (`apps/android/docs/SPEC.md` FR-3.7), sending through `HoldMyTrackApi.syncActivities` with `SOURCE_TIMELINE` like the web does.

- **`TimelineReader` is `reader.ts` rule for rule**, so the same export makes the same activities in both clients and importing it on both is `already_processed` the second time: an activity's route is its start, the `timelinePath` points strictly inside its span (two binary searches over the sorted path), and its end, times strictly increasing, the start or end left out when it's more than `ANCHOR_MAX_M` and faster than `ANCHOR_MAX_MPS` from the path point beside it; fewer than two distinct places is skipped; `external_id` is `seg-<start>-<end>` in epoch seconds; `day` is the first ten characters of the export's own `startTime`, its local date; `activityType`, `MODES_OFF_BY_DEFAULT` (Flying), `select`, `summarize` and `batches` (100) match. Times are parsed with `OffsetDateTime.parse`, the offset kept in the text sent. It takes raw entries (`RawPathPoint`, `RawActivity`) rather than JSON, so `TimelineReaderTest` runs on the JVM with `reader.ts`'s own test cases.
- **`TimelineFile` streams the JSON** with `android.util.JsonReader`, where the web parses the whole file (`JSON.parse`): three months is about 40 MB and years can be hundreds, too much for an app's heap as a tree of objects. It keeps only each activity's times, `start`/`end` `latLng` and `topCandidate.type` and each path point, and reads past visits, `rawSignals` and `userLocationProfile`. A top-level array is checked for the iPhone's shape and an object with `timelineObjects` or `locations` but no `semanticSegments` is the older Takeout file, each a `TimelineFormatException` naming it; malformed JSON is an `IOException`, shown as "couldn't be read as JSON".
- **`TimelineImport` holds the state process-wide**, like `FileImports`, for the same reasons: a large file isn't re-read on rotation and a send isn't cut short by leaving. The reading runs on `Dispatchers.IO`, the sending one batch after another under one `batch` UUID with the file's name as `batch_title`, so the history counts the import as one. `TimelineImportActivity` draws it from a listener and calls `reset()` when it finishes, which leaves alone a read or send still going.
- **The screen** rebuilds its mode checkboxes on each change (`renderModes`, the type through `RecordingTypes.format`, the distance through `PanelFormat.totalDistance`). From and To are `MaterialDatePicker`s bounded by the file's first and last day and the other end of the range, a day as midnight UTC both ways. There's no map preview: the screen isn't the map, and the counts per mode stand in for the dashed lines.
- **Opened or shared.** The manifest gives `TimelineImportActivity` `VIEW` and `SEND` filters for `application/json`, so a `.json` tapped in the Files app comes straight here. `incomingUri` reads the intent's data or `EXTRA_STREAM`; Upload opens it with the picked URI and `FLAG_GRANT_READ_URI_PERMISSION`, and Sync's Maps Timeline tile with none, to choose one.

## 6. Sync History

### `sync/ImportHistory`

The sync history (`apps/android/docs/SPEC.md` FR-4): the web's `/sync` page (`services/server/internal/httpapi/sync_page.go`, `templates/pages/sync.html`) — every import — over `include_sync_history`, in two sizes. On the Sync tab it's the `preview`: `PREVIEW_ROWS` (3) rows, See all (`sync_see_all`, shown once there's any) to `SyncHistoryActivity`, and no pager; `SyncFragment` starts it from `render()` once the account may see it (every resume, and after a run) and stops it in `onStop` and when another tab hides it. `SyncHistoryActivity` is the whole of it, started in `onStart` and stopped in `onStop`, its View on map finishing it.

## 7. In-App GPS Recording

`recording/` (`RecordingService`, `RecordingActivity`, `RecordedActivityRows`, `recording/db`) plus the record button and live-track layer on the map (`MapFragment`, `map/MapOverlays`) own this feature end to end. The wire contract it submits to — `POST /v1/sync/activities` under `source = "recorded"` — is specified server-side in `docs/IMPLEMENTATION.md` §4.0.4, along with [ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md)'s decision not to add a new endpoint for it. What follows is the client half that decision left to this app to design.

### 7.1 Recording and submitting are two separate steps, not one

**Recording is one tap, and nothing is asked.** The record button is `MainActivity`'s, raised over the bottom bar's middle slot (`record_button` in `activity_main`: a surface disc ringed in the border colour, red while recording and amber while paused, its pause and play icons tinted to match), and `MapFragment` drives it — a start from Sync or You first shows Map (`MainActivity.showMap`). It is 56dp idle and 60dp while a recording is active (`sizeRecordButton`, a bigger target for the hold with less of it under the finger): tap to start, tap to pause/resume, hold for two seconds to stop. The button is `recording/RecordButton.kt`, an `AppCompatImageButton` that replaces the platform long-press with its own: while `holdEnabled` (set by `renderRecording` whenever a recording is active) an `ACTION_DOWN` starts a 2 s `ValueAnimator` that draws a 5dp white arc on a translucent black track 5dp outside the button's edge, where a fingertip on the button doesn't cover it; it gives a `SEGMENT_TICK` haptic at each quarter, reports its progress through `onHoldProgress`, and on completion gives a `CONFIRM` haptic and calls `onHoldComplete` (`MapFragment.stopRecording`). Releasing early cancels; the click that release would produce is suppressed unless it came within `ViewConfiguration.getLongPressTimeout()`, so an abandoned hold never pauses. TalkBack gets the stop as the node's `ACTION_LONG_CLICK`. While `pulsing` (recording, not paused) an infinite 1.6 s animator draws a red halo widening 8dp out from the button and fading, stopped when paused, idle or detached. Every tap is felt: `startRecording` gives `CONFIRM` and a 1.15× scale pop, `onRecordTap` gives `TOGGLE_OFF` on pause and `TOGGLE_ON` on resume — on the button, so the system's touch-feedback setting applies. A tap that pauses also shows a short "Hold to stop recording" toast (`onRecordTap`), since a tap is the obvious guess at stopping and it only pauses; resuming shows nothing. The first tap asks for `ACCESS_FINE_LOCATION` and `POST_NOTIFICATIONS` together; only location is required to start. The button only sends intents — `RecordingService.ACTION_START` (via `startForegroundService`), `ACTION_TOGGLE`, `ACTION_STOP` — and the service's own notification carries Pause/Resume and Stop actions — Pause/Resume sends `ACTION_TOGGLE` straight to the service; Stop opens `MainActivity` with `ACTION_STOP` as its intent action, which it hands to `MapFragment` (`handleStopIntent`, ignored on a relaunch from recents), because the Save screen that follows needs an app window in the foreground to open over, and because it's confirmed there first: `confirmStop` shows "Stop recording?" with the time and distance so far (`currentStats`), in the destructive dialog style, and only its Stop calls `stopRecording`. One tap in the shade is an easy mistake where the map's hold is its own confirmation, so the map's stop never asks. A Stop that arrives before the bind answers sets `pendingStopConfirm`, and `onServiceConnected` asks then; nothing is asked if the recording is already idle, a second Stop while the dialog is up is ignored, and `renderRecording` dismisses the dialog if the recording ends under it.

**The status card in the mode toggle's place** (`recording_status`, a `MapPanel` the width of the top row's start column) is the on-map "is it recording?" answer, so a start is never in doubt without opening the shade. `renderRecordingStatus`, run from `renderRecording` on every state change and fix, shows it only while a recording is active: a 10dp dot (`hmt_record` red, `hmt_record_paused` amber), a `Chronometer` in the serif title size whose base is the service's `currentStats().elapsedMs` back from now — ticking on its own while recording, stopped while paused — and a detail line: the distance, "Waiting for GPS…" until `points()` has a fix, or "Paused · distance". The Chronometer's text comes from a tick listener in `RecordingFormat.duration`'s h:mm:ss, the notification's format; stopped, nothing ticks after `setBase`'s own redraw, so the paused time is set directly. During a hold, `renderHoldProgress` replaces the detail line with "Keep holding to stop…" and shows a red `LinearProgressIndicator` filling with the ring. Its **Stop** (`recording_status_stop`) asks first, as the notification's Stop does (`confirmStop`), since a tap on a button in reach is easy to make by mistake where the record button's hold is its own confirmation. `MapFragment` binds to the service from `onStart` to `onStop` purely to watch it (`onChange`, `points()`), which is also how reopening the app mid-recording (even after swiping it out of recents — the foreground service keeps running) redraws the whole track so far.

**While recording, the map shows that recording and nothing else.** `MapOverlays.setRecording` hides every user layer (history tracks, fog, heatmap at every tier) and `MapFragment` hides the mode toggle; ending the recording restores whichever mode was selected. The live track is a `GeoJsonSource` line plus a dot at the latest fix (`MapOverlays.attachLiveTrack`/`updateLiveTrack`), added at style load on top of every other layer and redrawn from the service's point list on each fix. The camera flies to the first fix at zoom 16 (or the current zoom, if closer) and eases to each later one, so a zoom the user picks sticks. A recording's own points never reach the history layers: those are server tiles, and nothing unsynced is on the server.

**The notification is the "am I recording?" indicator and the stats readout.** One ongoing notification for as long as a recording is in progress: title "Recording" with the system chronometer counting elapsed time (so the service doesn't re-post every second), or "Paused · h:mm:ss" with the time frozen; text is distance · current speed · current altitude, re-posted on each fix and state change. Its channel is `IMPORTANCE_DEFAULT` with sound and vibration off, not `IMPORTANCE_LOW`: a low-importance notification is filed under the shade's collapsed "Silent" section, which hides its action buttons behind an extra tap — found on an emulator. Channel importance can't be raised once created, so the channel id is `recording_status` and the service deletes the earlier `recording` channel.

**Stop saves in the service, not in a screen**, because Stop can come from the notification with no screen open. `RecordingService.stop` drops the recording, with a "Too short — not saved." toast, if its moving time (pauses excluded) is under `MIN_DURATION_MS` (60 s) or it has fewer than 2 points; otherwise it inserts a row with a blank name and description and `RecordingTypes.lastUsed` as its type (§7.5), in the same transaction that clears the recording's journal (§7.9), on an application-lifetime coroutine scope, since the service itself may be destroyed as soon as it leaves the foreground. Once the insert lands it starts `RecordingActivity.saveIntent` (`FLAG_ACTIVITY_NEW_TASK`, allowed because a stop always comes from `MapFragment` in the foreground): the same edit form with `EXTRA_JUST_STOPPED`, titled "Save recording", Download GPX swapped for Discard (confirm, then `store.delete`). Saving first and asking second means Back, or the activity never getting to open, still leaves the recording stored with the last-used type — the screen only refines a row that already exists. Name, type and description are otherwise set from a Sync screen row's Edit (the same `RecordingActivity`).

Stopping a recording only persists it to `recording/db/RecordedActivityStore.kt`; nothing reaches the network until the user taps Sync now on the Sync screen (§7.1.1). That screen's `flushRecordedQueue` (`SyncFragment.kt`) walks every row after the Health Connect pass when Health Connect can be read, or on its own when it can't (§5.1), submitting each as its own call to `POST /v1/sync/activities` and deleting it from the device on `"enqueued"`/`"already_processed"` — from then on the activity lives on the server (the map, the activity list), and the Sync screen only ever lists recordings that haven't synced. A rejected or failed row is left where it is, so the next Sync now retries it with no action needed from the user — the same resumable-retry posture `SyncCursor` (§5.3) already has for Health Connect sync. A recording that shouldn't reach the map is deleted rather than held back: there is no per-row choice of what goes.

`activity_type` is free text here, not the fixed vocabulary `health/ExerciseTypes.kt` (§4.2) normalizes Health Connect sessions onto — there's no platform exercise-type field to normalize from on this path. `external_id` is a UUID the app mints when a recording starts (`java.util.UUID.randomUUID()`, which also keys its journal, §7.9), not a platform record id — unlike Health Connect/HealthKit, there is no platform health store handing this activity an identity, so the client originates one itself.

### 7.1.1 The Sync screen's recording rows, designed after the web's Activities panel

`recording/RecordedActivityRows` fills the Sync screen's Recorded on this phone card (`sync_recorded_rows`, a `Widget.HoldMyTrack.SectionCard`) with every unsynced row, newest first. The class is a plain helper over an `AppCompatActivity`, not a view: `reload()` re-reads the store (on every resume, and after a run deleted what it sent), and `onChanged` tells `SyncFragment` to re-evaluate Sync now, which is enabled while `count` is above zero. Each row is `item_recorded_activity`, inflated: the silhouette on a 48×40dp `bg_type_tile`, the name (or its start date and time) over its metadata line (`CardRowTitle`, `CardRowSub`) — the Activities panel's row line, "[date · ] distance · duration · type" through `PanelFormat` and `RecordingTypes.format`, so a recording reads as its activity will once synced — then Edit and Delete as Lucide `pencil` and `trash-2` icon buttons (`Widget.HoldMyTrack.Button.RowIcon`, 48dp), Delete in the danger color — the web's own icons for those actions. Rows are at least 68dp, with the card's inset hairlines between them. `TrackSilhouetteView` has the `(Context, AttributeSet)` constructor that inflation needs. Checked on the emulator: a 1-minute recording saved through the Save screen listed as "2.3 mi · 1m · Unknown", and Sync now sent it, left the list empty, and put it at the top of the history as "GPS Logger".

The Edit and Save form (`RecordingActivity`, `activity_recording.xml`) follows the web's edit window (`EditActivityWindow.tsx`): the web's 10dp gap between fields, Time and Distance as labelled figures — the label in the list-heading style (`Overline`), the value 20sp bold with tabular figures (`fontFeatureSettings="tnum"`) so the clock doesn't jitter — and the Save screen's Discard as an outlined button with a danger label (`Widget.HoldMyTrack.Button.Danger`). Checked on the emulator in English and Russian, on both the Edit and the Save screen with their Delete and Discard dialogs.

### 7.2 `recording/db/RecordedActivityStore`

Plain `SQLiteOpenHelper`, not Room: this project's Kotlin toolchain — AGP's built-in Kotlin at the time this was built — was newer than any published KSP release, confirmed by trying it (a `com.google.devtools.ksp` version matching Kotlin 2.4.0 does not exist on Maven Central) rather than assumed from documentation.

**The table is scoped per account.** Without it, a recording made under one account (or the shared demo session) would show up in another's list of recordings on the same device. An `account` column scopes every query (`all`, `get`, `update`, `delete`) to `Session.email` — the same per-account key `sync/SyncCursor.kt` (§5.3) uses for the same reason, including that class's own precedent for a demo account sharing one empty-string key across every demo session. That sharing is harmless here for the same reason it's harmless there: a demo account can never sync regardless (§7.4), so nothing recorded under it ever reaches the server no matter which demo session later sees it locally. `RecordingDbHelper` is at schema version 5. From version 1, `onUpgrade` drops and recreates rather than a hand-written `ALTER TABLE`, the same "no migration tooling needed pre-launch" call the server side already makes. Version 3 changes no columns: it deletes rows with a `synced` status (§7.1 — a synced row is deleted, not kept) and keeps every unsynced row, since those exist nowhere else. Version 4 adds the journal's two tables (§7.9) and touches nothing else; the database is in WAL mode, since the journal commits on every fix while other screens read. Version 5 drops `sync_status` (`ALTER TABLE … DROP COLUMN`, which the platform's SQLite has from Android 14, the app's `minSdk`): Sync now sends every row, so there is no queued mark left to keep. Checked on the emulator by upgrading a version-4 database in place, then saving and syncing a recording.

### 7.3 Delete is local-only

Every recording row on the Sync screen is unsynced (§7.1), so Delete, after a confirmation that says so, discards the only copy of that recording. It never reaches the server; once a recording has synced, deleting it is the server-side delete (`docs/IMPLEMENTATION.md` §4.7.4) from the web app, since the phone no longer holds it.

### 7.4 Demo accounts are blocked from sync client-side too

Matching the web's own pattern (its Upload control disabled with a tooltip saying why), not just the server's `requireNotDemo`, so a demo session never meets the block as a raw `demo_read_only` error through a generic failure path. `Session.isDemo` (§2.1, `isSignedIn && email.isEmpty()` — the emptiness the class uses to mean "demo") is checked: the Sync screen hides Sync now and the whole Health Connect section behind an explanatory notice, and keeps the demo account's recordings and its history listed — reading is not a mutation.

### 7.5 A recording's starting type

A recording's `activity_type` is only ever set through Edit, and until the account has set one it is `RecordingTypes.DEFAULT` (`"unknown"`). An untyped row syncs like any other: cross-source dedup (`docs/IMPLEMENTATION.md` §4.6) matches on time overlap, not type, so an `"unknown"` recording still collapses into the same walk arriving as `"walking"` through Health Connect. (An earlier matcher required an exact type match, and this screen disabled the sync checkbox for an untyped row to compensate; both went when the matcher changed.)

Since recording asks nothing, most recordings would otherwise stay `"unknown"` until edited. `RecordingTypes.lastUsed` avoids that: every Edit save with a real type records it in a per-account preference (`holdmytrack.recording`, key `last_type:{Session.email}` — the same account key as the store), and each new recording starts on that type. So only an account's first recording starts untyped; after that, a recording usually carries the right type as-is and is edited only when it was a different kind of activity. A preference rather than "the newest row's type" because synced rows are deleted and the store is often empty. Clearing a row back to `"unknown"` is never remembered.

### 7.6 Type picker (`recording/ActivityTypePicker`)

The Type field on the Edit screen is the Android counterpart of the web edit dialog's `ActivityTypePicker.tsx` (`docs/IMPLEMENTATION.md` §4.7.4): a tap-to-open trigger showing the formatted type, which opens a dialog with a search field over the account's existing types, most-used first with each one's count, filtered as you type with `SearchPicker.tsx`'s own ranking (exact whole-label match, then word-start, then substring) and accent/case folding. While the search text doesn't exactly match an existing type, a last **Add "…"** row saves it exactly as typed, up to the server's 50-character `maxActivityTypeLen`; the keyboard's Done picks the top row.

The list is `RecordingTypes.known`: the server's per-type counts (`HoldMyTrackApi.activityTypeCounts`, read once when the screen opens), plus this device's recordings (all unsynced — a synced one is deleted locally and counted in the server's number instead), then any of the walk/hike/run/ride/drive `RecordingTypes.PRESETS` the account hasn't used, uncounted — so a new account still starts on the shared vocabulary `health/ExerciseTypes.kt` uses. `"unknown"` is left out as a choice, and a current value missing from the list is shown at the top so the current choice is always visible. Labels use `RecordingTypes.format`, the same `snake_case`-to-title-case display as the web's `formatActivityType`; the stored value is always the raw string. A dialog rather than a dropdown under the field, because the soft keyboard takes half the screen and a dialog keeps both the search field and the list above it.

### 7.7 Route silhouette (`recording/TrackSilhouetteView`)

Each recording row on the Sync screen shows a 48dp preview of its route, drawn from the row's own stored points as a bare line in the map's track colour (`MapOverlays.TRACK_COLOR`), with no basemap and no tile request. Longitude is scaled by cos(latitude) at the track's middle — an equirectangular projection local to the track, indistinguishable from Web Mercator at a few kilometres across — and the shape is fitted to the square keeping its aspect ratio, centred along the shorter side.

### 7.8 GPX download

Edit mode's **Download GPX** writes the recording as a GPX 1.1 file (`RecordedActivityRecord.toGpx`: one `<trk>` carrying `<name>`, `<desc>` and `<type>`, one `<trkseg>` of `<trkpt>`s with `<ele>` where known and `<time>`). The file goes through the system's own save screen (`ActivityResultContracts.CreateDocument`), so the user picks the destination and the app needs no storage permission. GPX because every other mapping tool opens it, and HoldMyTrack's own upload parses it (`internal/parse/gpx.go` reads `<trk><type>`), so a downloaded track can come back in unchanged.

### 7.9 Crash and kill recovery (`recording/db/LiveRecordingJournal`)

`RecordingService` keeps the recording in memory — the point list, distance, moving time — and a foreground service survives the screen going away, not the process: a low-memory kill, a crash or Force stop takes all of it, and the notification with it. So every fix is also written to disk as it arrives, to a journal in the same database: `live_recording` (one row: id, account, moving time, distance) and `live_points` (one row per fix, keyed by recording id and sequence number). A row per fix rather than rewriting `points_json` keeps each write constant-size over a multi-hour recording; at one fix per ≥3 s that is about 1,200 small commits an hour. Writes are queued in order on one single-threaded dispatcher on an application-lifetime scope, and a failed write is logged rather than thrown, so a full disk doesn't end the recording.

What is written when: Start inserts the `live_recording` row, with the recording's id (the `external_id` it will sync under, minted here rather than at Stop) and the account signed in at that moment; each fix appends its point and updates moving time and distance in one transaction; a pause updates moving time, since the time moved since the last fix would otherwise be lost. Moving time is stored as a number rather than as `elapsedRealtime` marks, which reset on reboot. Stop (or a too-short drop) moves the recording into `recorded_activities` — or nowhere — and deletes the journal in one transaction (`finish`), so there is no moment when a stopped recording is in neither place. A journal row with no recording running in this process is therefore always a leftover from one that died.

**Recovery is offered, not automatic.** The service stays `START_NOT_STICKY`: a sticky restart counts as a start from the background, which gets no while-in-use location access, so a location foreground service restarted that way could fail or record nothing, and it would resume without the user knowing. Instead, whenever `MapFragment` binds and the service is idle, `findLeftover` looks for a journal row — queued behind pending writes, so a Stop that has only just happened is never mistaken for one — and, if there is one under the signed-in account, the map shows a non-cancellable "Unfinished recording" dialog with its moving time and distance: **Resume** loads the points and totals back into the service as **paused**, with `lastFix` cleared, so the time the process was dead adds neither moving time nor distance, and starts it as a foreground service again (allowed, the map being in the foreground); it fails with the location-needed toast if location access has been revoked since. **Save** goes the way Stop does — the minimum-length check, the row, the Save screen. **Discard** confirms first ("Discard this recording?"), since the journal holds the only copy; Cancel brings the prompt back. Another account's leftover isn't offered, since its Save screen would find nothing under the signed-in account; it waits for that account. A Start that finds a leftover the prompt never got to (another account's, or a tap before the prompt came up) saves it as it stands, under its own account and that account's last-used type, rather than overwriting it — the journal holds one recording at a time.

### 7.10 Verified on device

The map-button flow, on an emulator (the `fitmap` AVD, against a local `db`/`api`/`worker` stack, GPS fed with `adb emu geo fix`): the first tap raised the location and notification prompts and started recording; the mode toggle disappeared and the live line grew with the camera following; tapping paused (the notification read "Paused · 0:01:44" and a far-off fix sent while paused added no point) and Stop from the notification saved a 26-point row; a ~20 s recording stopped by long-press was dropped (no database created, notification gone); swiping the app out of recents mid-recording and reopening it redrew the full track and recording continued; the first recording saved as `"unknown"`, was set to walking in Edit and queued, and "Sync Now" created a `walking` activity server-side and removed the row from the device; the next recording then saved as `walking` with no Edit.

Earlier, on a Pixel 10a: recorded a short walk with a custom, free-text activity type; confirmed the row landed in Recorded Activities as not-synced with no network request having been made; edited its name/description/type pre-sync and confirmed the edit persisted; checked its sync box (queued); tapped "Sync Now" and confirmed the row synced alongside a Health Connect run in the same combined summary text. ## 8. Build Configuration

`BuildConfig.API_BASE_URL` is the one build-time value that comes from outside the build, set per build type from a Gradle property: debug from `holdmytrack.apiBaseUrl` (`gradle.properties` defaults it to `http://10.0.2.2:8080`, the emulator's alias for the host loopback), release from `holdmytrack.releaseApiBaseUrl` (`https://holdmytrack.com`), so the Play build can't pick up a dev stack's address. The release build is signed by the `release` signing config, which reads the upload keystore's path, alias and passwords from `holdmytrack.upload*` properties kept outside the repository (`apps/android/holdmytrack/README.md`, Release build). Pointing a physical device at a host dev stack over USB requires `adb reverse` for both the API port and the web dev server port the style document's asset URLs resolve against (`BASEMAP_ORIGIN`, `docs/ARCHITECTURE.md` §2.1) — documented with exact commands in `apps/android/holdmytrack/README.md`. The other, `BuildConfig.DONATE_LINK`, is set per build type: `true` in debug, the APK the website offers (`docs/DEPLOY.md`), and `false` in release, the Play build, whose payments policy doesn't allow a link to payment outside Play's billing (`apps/android/docs/ROADMAP.md` Phase 6). `MapFragment.showMenu` leaves Donate out when it's false.

**The version comes from git.** `app/build.gradle.kts` sets `versionCode` to the commit count (`git rev-list --count HEAD`), so it rises with every commit and never needs bumping — Play refuses an upload whose code isn't higher than the last — and bakes the short SHA in as `BuildConfig.GIT_SHA`, the same one the server's `/healthz` reports. `versionName` is the release number, `0.10`, changed by hand when a release means something. Outside a git checkout the code is 1 and the SHA `dev`. `HoldMyTrackApi.appVersion` joins the two — "0.10 (62da50b)" — for the You tab's last line (`apps/android/docs/SPEC.md` FR-2.9) and the `User-Agent` the app sends on its own API requests (`HoldMyTrack-Android/0.10 (62da50b)`, `UserAgentInterceptor`); other origins keep MapLibre's own. Nothing on the server records the User-Agent yet: neither the API nor Caddy writes access logs.

**Cleartext `http://` traffic is permitted in debug builds only** (`app/src/debug/AndroidManifest.xml`), so a release build cannot be pointed at a plaintext dev endpoint by accident — the network security configuration itself is what enforces this, not a code-review convention.

`libs.versions.toml` pins every dependency version with an inline rationale for why that version specifically (MapLibre's pmtiles-support floor, the Health Connect version the device measurements were taken against, OkHttp pinned to what MapLibre's own POM resolves to rather than left implicit) — the versions themselves are covered in `apps/android/docs/ARCHITECTURE.md` §2; this file is where the *reasoning* for each pin lives, so an upgrade is a decision made against that reasoning rather than a blind bump.

**Languages: English and Russian** (root `docs/IMPLEMENTATION.md` §4.21, `docs/adr/0014-localization.md`). All the app's text is in `res/values/strings.xml`, with Russian in `res/values-ru/strings.xml`. Strings that are the same in every language (`app_name`, the placeholder dash, the Health Connect/HealthKit product names) are `translatable="false"`, so lint's `MissingTranslation` checks everything else in both files. The Russian avoids plural forms by phrasing counts as "label: N" ("Прочитано тренировок: 5"), so the English strings' `%d` stay plain `<string>`s. `res/xml/locales_config.xml`, referenced as the manifest's `android:localeConfig`, puts HoldMyTrack in Android's per-app language list (minSdk 34, so it's the platform's own setting, with no AppCompat per-app-locale API needed). `build.gradle.kts`'s `androidResources.localeFilters` keeps only `en` and `ru` resources in the APK, so a phone set to a language the app doesn't have gets the English app, not English mixed with a library's own translations. Two pieces of code followed the strings: `recording/RecordingFormat` takes `Resources` and formats its units through `unit_km`/`unit_m`/`unit_kmh` in the device's locale, and `sync/SyncRunner` takes `Resources` for the refusal and stop reasons it reports (`sync_consent_required`, `sync_refusal_*`). `HoldMyTrackApi`'s `LanguageInterceptor` sends `LocaleList.getDefault()` as `Accept-Language` on the API origin's requests, read per request, so the server's messages come back in the app's language. The account's Language setting is applied as the app's per-app language (§2.5).

## 9. Verification Methodology & Known Gaps

**Automated tests are few**: JUnit unit tests over the pure logic (`app/src/test`, §3.2), which CI runs on every push and pull request, uploading their JaCoCo coverage to Codecov (root `docs/DEVELOPMENT.md`, "CI"), and no instrumentation tests. Every behavior described in `apps/android/docs/SPEC.md` has instead been verified manually against a live `db`/`minio`/`api`/`worker` stack, with the specific steps and observed results recorded narratively in `apps/android/docs/ROADMAP.md` under each phase while it was open (a finished phase is removed from that file; `git log -p` on it still has the record) — for example, the sync engine's watermark correctness was verified by forcing a mid-run API outage and confirming a subsequent run recovered every record with zero duplicates, and the layer-ordering/visibility logic in `map/MapOverlays` was verified by screenshotting all three map modes against a real account. FR-1 through FR-4 (`apps/android/docs/SPEC.md`) were verified this way on a physical device (a Pixel 10a running Android 17/API 37); FR-5's in-app recording (`apps/android/docs/SPEC.md` §7), and FR-3.6's file uploads and FR-3.7's Timeline import, were instead verified on an emulator (a Pixel 7 AVD, Android 16) against the same kind of live stack — noted there specifically, since it's the one exception to this file's otherwise-consistent "physical device" claim.

This is a real gap relative to the server codebase, which the app inherits no test infrastructure from, and is worth naming rather than leaving implicit:

- **Regressions are only caught by re-running the manual verification steps**, which do not run automatically and are not gated in CI. A change to `SyncCursor` or `SyncRunner` in particular should be re-verified against the specific scenarios verified when sync was built (mid-run failure, a `ConsentRequired` route, two sessions sharing a start instant), since those are exactly the edge cases a quick manual smoke test tends to skip.
- **Verification has only ever run against one physical device and one Health Connect data provider (Fitbit).** The empirical Samsung Health check (`apps/android/docs/ROADMAP.md` Phase 1) remains unresolved for lack of a Galaxy Watch to test against — the current "Samsung is unsupported" conclusion rests on Samsung's own published documentation plus this app's design stance, not on a device-level measurement the way every other finding in this document is.
- **No test double exists for Health Connect.** `SyncRunner` and `SyncCursor` are exercised only against a real `HealthConnectClient` on a real device; there is no fake or mock implementation of the client to run these classes against in isolation.
