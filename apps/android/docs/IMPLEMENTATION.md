# HoldMyTrack for Android: Implementation

> **Scope note.** This document covers each file's own implementation detail for the Android app — the app shell, auth, map overlays, Health Connect sync, in-app GPS recording, and the web's own pages shown in the app. See `apps/android/docs/ARCHITECTURE.md` first for the app's shape and the stack this runs on, and `docs/IMPLEMENTATION.md` for the server-side schema and pipeline every call here eventually reaches. The app's local persistence is two `SharedPreferences` files, covered in place below, plus one SQLite database (§7) for recordings pending sync.

---

## 1. App Shell & Lifecycle

### 1.1 `HoldMyTrackApplication`

Process-level setup, in a fixed order that matters: `Session.init` before anything reads a stored token; `MapLibre.getInstance` to load the native library a `MapView`'s constructor needs; then `HttpRequestUtil.setOkHttpClient(HoldMyTrackApi.client)`, replacing MapLibre Native's own HTTP stack with the app's shared client. **This last call has to happen in `Application.onCreate`, not an Activity's** — the map SDK may issue a request as soon as a `MapView` exists, and installing the client any later means some requests already went out through the SDK's default, tokenless client.

### 1.2 `MainActivity` and `MapFragment`

`MainActivity` is the main window, with the bottom bar; `MapFragment` is the map in it, with the state that governs what's drawn (`apps/android/docs/ARCHITECTURE.md` §1.1).

- **Never mounted without a session, or for an unconfirmed email.** `MainActivity.onCreate` checks the session before `setContentView` and hands a signed-out launch to `SignInActivity` (an unconfirmed one to `VerifyEmailActivity`, §2.4) — no layout, no `MapView`, no style request. It adds `MapFragment` only on a first create, since a recreation (rotation, theme, language) restores the fragment with its saved state.
- **Tabs are shown and hidden, never replaced** (`showTab`, with `commitNow`), so each tab keeps its state, the map's camera and layers included. Stories is the map with its panel on the Stories tab, and the panel reports its tab back, so the bar follows a tab chosen in the panel itself.
- **Insets are handled once, on the tabs' container**: it pads itself by the side navigation-bar and display-cutout insets and zeroes them for the tabs, so no tab's chrome sits under a landscape phone's three-button bar or camera, and none has to pad itself.
- **The record button's frame reaches up over the bar by as much as the button is raised**, since a view never gets a touch outside its parent: without it the raised part took no touches.
- **`syncSession()` is the single place session state and map state are reconciled**, called from `onResume` and once after the style loads. It routes to sign-in if the token was just rejected, verifies a restored token once, and only then attaches the user layers. The basemap style loads before verification finishes — it is unauthenticated (root `docs/ARCHITECTURE.md` §2.1) — but the user layers wait for a verified token. `verifying` is a re-entrancy guard, not a cache: `onResume` fires on every return, including from the sign-in screen, so a slow verify could otherwise start twice.
- **Only a `401` from verifying clears the session.** Any other failure is shown as a notice with Try again, and the same token is tried on the next resume. This is the one place the app discriminates by HTTP status rather than treating "the request didn't succeed" as one bucket.
- **The map says what's wrong in one notice, by importance** (`Notice`): a less important kind never replaces a more important one that is up, and a kind can only take itself down. "Checking" is posted after a delay and removed when the check answers, so a fast check never flashes.
- **`frameActivities()` runs once per process, and the flag goes into the saved state**, so after a recreation the camera MapLibre restored stands. The fit is capped at zoom 15, because a very short or heavily clipped activity has a near-zero box, and fitting it literally would zoom past the basemap's data onto an empty tile. It keeps a minimum span of map between its top and bottom padding: on a landscape phone the top row and the sheet left none, and the fit fell back to the whole world. A group is framed along the shortest arc of longitude (`map/BoxUnion`, the web's `unionBBox`, root `docs/IMPLEMENTATION.md` §4.7).
- **`insetSystemBars()` exists because of a bug found only on a real screen**: at `targetSdk` 35+ the system draws every app edge-to-edge and ignores the old opt-out, so a bar laid out with ordinary padding sat *underneath* the gesture pill. The fix adds the inset to each view's own padding and returns the insets unconsumed, so nothing downstream misses them.
- **MapLibre's `MapView` owns a native renderer and a GL surface**, so every lifecycle call forwards to it. Missing any one is a leaked surface or a crash on rotation, not a subtle bug.
- **The top row is not clickable**, so a touch in its gaps still reaches the map. The Edit window and the Private location editor open over where the Layers/locate rail would be, so the rail hides while either is open. MapLibre's compass is moved below the row and the notice whenever their layout changes.
- **The Layers menu** (`map/LayersMenu`, the web's `OverlaysMenu.tsx`) is a focusable popup inflated afresh each time. A focusable popup closes itself on an outside touch, including one on its own button, so a click landing just after that close doesn't reopen it. Its master switch is set from the saved choice, so it's handled with a click listener rather than a checked-change one. Every place the saved picks are applied goes through `shownPaths`/`shownSpots`, which give nothing while the switch is off. A checkable `MaterialButton` flips itself on click, so the button's state is re-rendered after each tap.
- **Paths** (`map/MapPaths`, `map/MapBikePaths`; root `docs/IMPLEMENTATION.md` §4.24) are laid out as on the web: coverage, then the trail and track layers lifted out of the basemap's roads — MapLibre Native has no `moveLayer`, so each is removed and added back below the labels — then the bike paths, then the tracks. A coverage refresh puts its layers back under whatever sat right over them, so the paths stay above the veil. **When the tile version moved while the app was away, the bike-path and spot sources are replaced at the new version**; without it, the app kept drawing tiles cached before an import. The legend's colors and dashes must match the web's `style.ts`.
- **Satellite** (`map/MapSatellite`, root `docs/IMPLEMENTATION.md` §4.26) is offered only when the served style has a `satellite` source, and applies the style metadata's hide and dim lists rather than a second copy of them. Night mode or satellite is a dark base, which picks Fog's veil; the coverage layers are re-added only when the veil actually changed.
- **Find my location is MapLibre's own `LocationComponent`, activated lazily** on the first tap, tracking until the user pans like the web's geolocate control. A recording's first fix sets the camera mode back to none, so the recording's own follow (§7) is the only thing moving the camera then. `ACCESS_COARSE_LOCATION` is merged in from MapLibre's manifest.
- **The date range** (Android SPEC FR-2.6) ports the web's logic as pure classes, tested against the web's cases: `ActivityDays` (`useActivityDays.ts`), `DateRangeSlider` (`DateRangeSlider.tsx`), `RangeShift` (`rangeShift.ts`, `RangeShiftTest`), and `ScrubberBars` (bar heights and labels, `ScrubberBarsTest`). `DayScrubberView` only draws and sorts each touch into a handle drag, a swipe or a tap, asking its parent not to intercept so the sheet doesn't drag with it. The default range uses the device's day, as the web uses the browser's. Days reload on every resume, keeping the window's anchor, so a range picked further back is still in view after Profile or Sync. **The logo's and attribution's base margins go into the saved state**: MapLibre restores its UI settings already lifted, and capturing them again lifted the logo twice its height above the sheet.
- **Style flavor follows the app's night mode**, so a dark map always sits under dark chrome, and the style URL carries the app's language for the labels (root `docs/IMPLEMENTATION.md` §4.21). A language change recreates the activity, so the map loads the new URL.

### 1.3 Theme (`res/values/themes.xml`)

**The palette, scales, fonts and icons are the web's** (root `docs/IMPLEMENTATION.md` §4.17, §4.18): `res/values/colors.xml` and `res/values-night/colors.xml` are the web's light and dark tokens value for value, under the same names, and `res/values/dimens.xml` its spacing, radius and type scales with CSS px read as dp — a phone browser draws one CSS px as one dp, so the mobile web and the app come out the same size. **A change to the web's tokens needs the matching change here.** The base theme maps the palette onto Material's color roles once, so the mapping holds for both palettes. Dynamic color is not applied, so the user's wallpaper never replaces the palette.

- **Which palette applies is AppCompat's night mode**: the You tab's Theme choice is applied in `HoldMyTrackApplication.onCreate` and again on a change, which recreates the open screens, and the map's flavor reads the same configuration (§1.2).
- **Shape is the web's radius scale, not Material's** pill buttons and 28dp dialogs.
- **Fonts are the web's Inter and Fraunces as variable fonts**, cut down with fontTools to the scripts and weights the app uses (about a quarter of the original size); `res/font-ru/` swaps in Source Serif 4 for the serif, the web's own Russian choice, because Fraunces has no Cyrillic. The licences ship in `assets/licenses/`. Code bolds with `Typeface.create(typeface, 700, false)`, because `setTypeface(null, BOLD)` would drop to the system font.
- **The default face reaches text through a TextView style, not the theme's `fontFamily`.** Setting `android:fontFamily` on the theme reaches every `TextView` as if set on it directly and so outranks its `textAppearance`: titles came out in Inter, and every role's weight flattened to regular.
- **Icons are Lucide at the web's version**, converted to vector drawables, every stroke white so the color comes from where the icon is used — the Android counterpart of the web's `currentColor`. Three glyphs are outside the set: the idle record button's solid red dot, since a filled signal color is what says "record", and two activity types Lucide has no icon for, drawn on its grid and stroke.
- **Map chrome panels carry the color and shadow, not the buttons in them**: a translucent `MaterialButton` with elevation draws its shadow through its own fill, which showed as a lighter square around the icon. Their 48dp minimum height is set on the style, since while recording the row holds nothing else and a `match_parent` button collapsed to nothing.
- **The mode buttons name themselves radio buttons to TalkBack**, since `MaterialButton` calls itself a toggle outside a `MaterialButtonToggleGroup` and sets that after any delegate. Selection is set by `MapFragment.setMode` on all three, and the mode is kept in the saved state: the buttons restore their own checked state after a recreation, so without it the toggle showed Heatmap over a map drawn in Normal.
- **Dialogs use `MaterialAlertDialogBuilder`**, not the platform `AlertDialog`, which would ignore the app theme. A dialog whose confirm destroys something opts into the destructive overlay, so no other dialog's confirm turns red.
- **Accessibility traps found by auditing every screen's view tree** at font scales 1.0 and 2.0 and in landscape (TalkBack itself was walked on a physical device, since it couldn't be driven on the emulator):
  - `MaterialButton` ignores `android:minWidth` from a style, so the mode buttons' minimum width is set in code.
  - `isSingleLine` set after `minHeight` undoes it.
  - MapLibre's attribution button is too small and has no id; it is found by its content description and padded only toward the empty map, so the icon stays put. Padding it evenly and moving it back through the attribution margins broke after a recreation, which restores those margins.
  - At large font scales the mode toggle keeps only the active mode's label, and rows that can't fit stack into a column (`ui/LargeText`).
  - A target drawn smaller than 48dp keeps a 48dp touch area — the sheet's handle reaches under the head's first row with a negative margin, the filter chips use an inset ripple.

## 2. Authentication & Session

### 2.1 `net/Session`

**An `object` (process-wide singleton) rather than an instance**, because two independent HTTP call sites need the same token without being wired to each other: the app's own calls, and MapLibre Native's tile fetching, which goes through the shared `OkHttpClient` but never through `HoldMyTrackApi`.

**The token lives in two places at once, deliberately**: a `@Volatile` field for fast, thread-safe reads (the bearer interceptor runs on whichever thread OkHttp dispatches a tile request from, where reading `SharedPreferences` each time would be slower and not obviously safe), and `SharedPreferences` for persistence across process death. `init` must run before either is read, which `HoldMyTrackApplication.onCreate` guarantees.

**`verified` is separate from "a token is present"**: a token restored from disk after a cold start hasn't been checked against the server yet, while one just minted by a sign-in needs no check.

**`emailVerified` is on disk rather than per-process**, so a cold start routes straight to the right screen without drawing a map first. A missing value reads as `true` — a session stored by a build that didn't record it — and the cold start's session check corrects it before any user layer attaches.

### 2.2 `net/HoldMyTrackApi`

The app's whole HTTP surface in one object: one shared `OkHttpClient`, its interceptors, and the calls.

- **`client` is shared with MapLibre Native** (§1.1), with `maxRequestsPerHost` raised to what MapLibre's own default client uses — OkHttp's plain default would throttle the map's tile bursts.
- **`BearerInterceptor` runs per request, not once at startup**, and attaches the token only to the API's own origin. Per request is what makes sign-in, sign-out and token expiry take effect on the very next request, the next map tile included. The origin check exists because the basemap's assets are unauthenticated and live on a domain HoldMyTrack doesn't own; sending a live token there would only put a working credential in a third party's access logs.
- **`OriginInterceptor` sends the API's origin on every request that leaves it**, as a browser does on the web client's cross-origin fetches. The satellite imagery's key only accepts requests from the deployment's origin, and the basemap's edge rule refuses a request with no `Origin` (root `docs/IMPLEMENTATION.md` §5.4), so without it the map would draw nothing at all. It gives nothing away: the key is already public in the web bundle and the style.
- **Everything except `syncActivities` is callback-based**, posted back to the main thread — a deliberate rejection of coroutines-everywhere for this file: a handful of call sites don't amortize a coroutines layer over OkHttp's own async API.
- **`syncActivities` is the one `suspend` function, wrapping a blocking call on `Dispatchers.IO`**: its caller must not send its next batch until this one is answered, and Health Connect's own API already puts that caller on coroutines.
- **The Type picker's counts come from the same unpaginated activity list** the web's Type facet is built from; there is no dedicated facets endpoint.
- **`ApiException` carries the server's own response text as its message, unreworded**: the server's plain-text errors are written for people, and rewriting them risks saying something the server didn't mean. Refusals a client branches on come as `{error, message}`; those show their `message` and keep the code.
- **`image()` fetches any API image with the bearer token** and samples it down off the main thread. A browser tab or an image library would have no token to send, which is also why Full size opens in the app (§3.4).

### 2.3 `SignInActivity`

**The root of its own task** (`NEW_TASK | CLEAR_TASK`), from a signed-out cold start, a rejected token or Sign out, so no screen that needs a session is ever left underneath it and Back leaves the app. A successful sign-in replaces the task the same way with the map, or with `VerifyEmailActivity` (§2.4) for an unconfirmed email.

**The web's two pages as two modes of one screen**, rather than two activities, because the Facebook round trip returns here with the verifier this screen keeps, whichever mode started it. The password's autofill hint follows the mode, so a password manager suggests a new password only on sign-up. The mode survives recreation, including a process death behind the Facebook tab. **"Forgot password?"** opens the web's own `/forgot` in a Custom Tab rather than a native form, since the emailed reset link opens the web's `/reset` anyway.

**Client-side validation is only "both fields are non-empty"**, deliberately, so the server remains the single source of truth for what an acceptable email or password looks like, and its error text is what the user sees.

**Google and Facebook** (the server side is root `docs/IMPLEMENTATION.md` §4.15 and §4.22) show only once the server reports each configured; if that request fails they stay hidden, since a button that can only fail is worse than none.
- **Google** asks Credential Manager for an ID token for the server's *web* client id, so the token's audience is the one the server checks. Any failure other than closing the picker is logged: in development it's almost always a missing Android OAuth client for the debug key's SHA-1, which the picker reports only as a generic error. `googleid` is pinned at 1.2.0: 1.2.1 is compiled with Kotlin 2.4 metadata, which this project's compiler can't read.
- **Facebook** doesn't use Meta's SDK (root `docs/IMPLEMENTATION.md` §4.22). The verifier is saved to `SharedPreferences` before the Custom Tab opens, since the process can die while the tab is in front. **`OAuthRedirectActivity`** receives the `holdmytrack://oauth` redirect: an exported, no-display activity whose only job is forwarding the URI to `SignInActivity` with `CLEAR_TOP | SINGLE_TOP`, which closes the tab above it and keeps `SignInActivity` itself unexported. The buttons re-enable on resume when the tab was simply closed.

### 2.4 `VerifyEmailActivity`

The "check your email" screen (`apps/android/docs/SPEC.md` FR-1.4). Without it, an unconfirmed account opened the map with nothing on it: the server answers every tile and sync request `403`, which MapLibre reports only in logcat.

- **Root of its own task**, like `SignInActivity`, so Back leaves the app instead of revealing the empty map.
- **The link is clicked in a browser the app never hears from**, so the screen asks the server on every `onResume` — returning from the mail app is when the answer is most likely to have changed — and on Continue. Only Continue reports "not yet" or a failure; the automatic check is silent.
- **No change-email form**, unlike the web's: the recordings, the type list and the hidden candidates are keyed by the session's email on the phone, so changing it from here would need those migrated too.
- **`SyncActivity` checks the email too**, since Health Connect's rationale intent can open it without passing through the map.

### 2.5 `web/WebPageActivity` — the web's own pages in the app

Settings, Activity graph & trends, Sync history and About are the web's own pages in a `WebView`, not native copies (ADR-0042), so a change to one reaches both clients with a server deploy and there is no second implementation to keep in step. How the server renders a page for the app is root `docs/IMPLEMENTATION.md` §4.19.

- **Signed in by cookie, not by the bearer token.** A WebView's requests never pass through the app's `OkHttpClient` (`apps/android/docs/ARCHITECTURE.md` §1.1), so the session is written into the WebView's own cookie store before every load, beside the in-app marker and the language. A request header would reach only the first request; a cookie rides on every link, form POST and redirect after it. The store is the app's own, and signing out empties it.
- **The language cookie decides only for Automatic**, where the app can run in a per-app language other than the phone's, which is all the WebView's `Accept-Language` would say.
- **The app's Theme, with no code for it.** A WebView in an app targeting API 33+ answers `prefers-color-scheme` from the activity theme, which follows the app's night mode, so a page follows the app's Theme rather than the phone's.
- **Where a navigation goes is `route`**, a decision over the URL: the page's own path stays in the WebView, `/` opens the native map, the sign-in pages just finish and leave the map's own session check to act, and anything else opens in a Custom Tab. Trap: `shouldOverrideUrlLoading` is never offered a POST and can't be relied on for the redirect after one, so `route` runs again in `onPageStarted`, which stops the load; that's how Settings' first-run save reaches the map.
- **The avatar**: the page's file input opens the photo picker, and the picked image is shrunk to a small JPEG before the page's form uploads it — a phone photo is often past the server's limit, or HEIC, which it refuses. The file input's callback must be answered exactly once: with the file, or with null for a cancel or an unreadable image.
- **Read again on return**, except Settings, so a half-filled form survives the photo picker.
- **What a Settings save changes in the app arrives with the next session check**, since the page saves through the server, not the app.
- **First run**: a confirmed account with no country is sent to Settings as the root of a new task. Its save redirects to `/`, and `route` reads the session before opening the map: the map gates on the country, which so far only the server has heard about, and without the read it sent the account straight back. A stored country is only trusted once a session check has refreshed it, so an account that saved Settings on the web isn't sent there by a stale value.
- **Against a dev stack, a page's form POST is refused** unless the app's API base is the stack's `APP_BASE_URL` origin (root `docs/IMPLEMENTATION.md` §4.19, `docs/DEVELOPMENT.md`). Production's are both `https://holdmytrack.com`.

### 2.7 `YouFragment`

The You tab (`apps/android/docs/SPEC.md` FR-2.9).

- **Read on every showing**, and an answer after the view is gone is dropped. The totals come from the same per-day histogram the web's Profile page reads, summed by `ProfileStats`, a port of the page's own sums.
- **The country is named by `Locale.getDisplayCountry`** in the app's language rather than from the server's list, which would cost a request for one label.
- **The Language save resends the profile just read**, since the settings endpoint replaces Name, Country and Timezone along with Language.
- **Units** — `recording/RecordingFormat` is the one place distances, heights and speeds become text, with the web's imperial countries (`services/server/internal/web/format.go`) read from the session's country.
- **`settings/AppLanguage`** sets the per-app language only when it differs, since setting it recreates every open screen. Automatic can't be told apart from "never chosen", so a sign-in or session check only applies an explicit language, and only the You tab's Language save clears one.
- **Delete account** (`settings/AccountDeletion`) replaces the dialog's positive-button listener, so a mismatched email lands on the field as its error without closing the dialog. After the server closes the account it **clears what the phone keys by the email** — recordings, hidden candidates, sync sources — before clearing the session, so a new account made with the same address starts clean.

### 2.8 `privacy/PrivacyActivity`

The Privacy screen (`apps/android/docs/SPEC.md` FR-1.7).

- **A row and Add a location open the map's editor and finish this screen**, so Back from the editor doesn't land on a list it may have changed.
- **Download your data** (`privacy/DataExportActivity`) polls while an archive is being prepared, only while the screen is resumed. Each part is handed to Android's `DownloadManager` with the session's `Authorization` header: the download outlives the screen, resumes on its own, and needs no storage permission at minSdk 34.

## 3. Map Rendering

### 3.1 `map/MapOverlays`

Owns the history layers — tracks, Fog and Heatmap — and the logic to add, remove and toggle them; the web's counterpart is root `docs/IMPLEMENTATION.md` §4.2–§4.3.

- **`attach` is idempotent and re-runnable**, checking each source and layer before adding it: a style *reload* (the app's night mode changing) discards every custom layer, so this is not a one-shot setup path.
- **The insertion point is computed, not hardcoded**: every custom layer goes below the basemap's first symbol layer, so labels stay on top, with the rasters under the tracks — the web's ordering, reproduced layer by layer, since there is no shared layer-ordering module between the clients.
- **`setMode` only changes properties**, never adds or removes layers, so switching is instant and a style reload re-applies it. Fog dims the basemap's labels to the web's value and other modes reset them to the default the served style never overrides. **Heatmap's basemap wash is switched by its opacity, not its visibility**: MapLibre Native doesn't draw a background layer again once it has been hidden, so the second switch to Heatmap had no wash.
- **Only the tracks URL carries a filter, and only the date range** (or the open Story). Type, Distance and the hidden set are applied on the device as layer filters, as on the web. **Changing the range replaces the tracks layer and source**, because MapLibre Native's `VectorSource` has no way to change its tile URL; the old layer's visibility is carried over, so a mode or a recording in progress is respected.
- **The selected track is two more layers, not feature-state.** The web bolds it with feature-state, which MapLibre Native Android doesn't have, so a casing and a wider line on the same source are filtered to the selected (or checked) ids. The filters are kept on the object, since replacing the source re-adds every layer.
- **Refreshing tiles means a new URL** (root `docs/IMPLEMENTATION.md` §4.2.6). The tile version is kept on disk, so a cold start attaches at the last one read and MapLibre's cache draws at once, then the status is read and everything refreshed only if it moved — on attach and on every resume. Tracks also carry the app's own `v`, since a change the app hasn't read a new version for yet (a type edit) would otherwise be answered from cache. `map/CoverageWatch` is the web's `useCoverageRefresh.ts`, the same rules, and a resume that finds the account still rendering starts one, so an import made on the web is followed to its end.
- **The zoom tiers' constants must match the web's `zoomTiers.ts`** (`ZoomTier`, unit-tested against the boundaries), and so must the level notice, which names the tier on camera idle, so a pinch through two levels names only where it lands.
- **The track color is the shared map style's, not this app's theme**, so it is not folded into the palette tokens.

### 3.2 The Activities panel (`panel/`)

The web's phone Activities panel (`apps/web/src/ui/ActivitiesPanel.tsx`; `apps/android/docs/SPEC.md` FR-2.7), ported rule for rule.

- **Three pieces, split where the web splits them.** `PanelState` is the state the web keeps in `MapView.tsx` — the list, the checked group, the selected id, the hidden set, the filters — with its rules as methods; `ActivityFacets` is `activityFacets.ts`. Both are plain Kotlin, covered by `PanelStateTest`. `ActivitiesPanel` binds the views and redraws everything from the state in one `render()`. `MapFragment` owns the map and the fetch, as `MapView.tsx` does.
- **The rows are a diffing `ListAdapter`, so a render rebinds only rows that changed**: rebinding every row cancelled a tap that landed mid-rebind, when a list reload came in between two ticks. The list's note is a second adapter after the rows, as the web's is a last `<li>`, not drawn over the list, where a failed poll would write it across the first row.
- **The sheet is a `BottomSheetBehavior`**, peeking at its head's bottom edge, recomputed after layout whenever that edge moves, at any font scale. The expanded offset is computed from the head's *natural* height, not the one a too-short sheet squeezed it to, which on a landscape phone cut the scrubber's labels off. The content is only ever covered, never removed, so the list keeps its scroll position. While an edit window is over the map the sheet is held collapsed without forgetting its state.
- **A track tap queries a box around the finger**, the web's touch tolerance, and scrolls the row into view on the list alone, never the sheet — the same reason the web scrolls the list rather than calling `scrollIntoView`.
- **Selecting is just "the checked group is non-empty"**, so nothing can leave the list selecting with nothing checked. The selection bar and the selected activity's card are bound to one action set described from the same target, so the two never disagree. Back ends selecting before it collapses the sheet.
- **The master checkbox's state is set from the rows on every render**, and its click only decides between "uncheck all" and "check all", so the widget's own toggle never disagrees with the state.
- **The Distance slider holds `Float`s, which can't carry every distance exactly**, so a knob within a meter of either end is snapped onto that end's activity; otherwise dragging only the low knob dropped the range's longest activity.
- **Times are shown in the zone the activity was recorded in** (root `docs/IMPLEMENTATION.md` §4.30), skipping a zone the phone's tz data doesn't know. One Story reads "Story" from a plain string rather than the plural's `one`, which in Russian also covers 21, 31 and so on.
- **The selected activity's pace bands** are read whenever the selection moves to another activity and again when its reprocess lands, an answer for an activity no longer selected dropped; `map/TrackBands` is the web's `trackBands.ts`, unit-tested.
- **The Track tab** (`panel/TrackEditor`) ports the web's editor; its rules are `panel/EditTrackOps`, a port of `editTrackOps.ts`, unit-tested. The knobs are the times of the points they sit on, so a deleted point never moves them. Cut's and Split's previews show while the button is held, where the web shows them on hover. A refused split that would hide a part (`split_hides_part`) asks before resending with `allow_hidden`.
- **The editor's point drags and the Private location handle are taken in a touch listener on the `MapView` itself**, which runs before MapLibre's gestures: a press on a point or handle takes the whole gesture, so the map doesn't pan (the web's `dragPan.disable()`); every other touch still reaches the map. A press let go unmoved, a cancel or a second finger commits nothing.
- **Private locations** (`panel/PrivateLocationEditor`, the web's `PrivateLocationsPanel.tsx`) are edited on the map from the Privacy screen. A request waits until both the list and the style are in. The circle is scrolled into the map left above the editor rather than centred, since at phone width centring put the handle under the card. **A change reprocesses whole activities**, so the coverage watch takes a callback and the tracks, list, days and metrics are re-read once the server has drained — a batch done before the first read never shows a row Pending at all.
- **Edit is a card, not a dialog**, so its Track tab can edit on the map, as the web's does; while it's open the sheet, the bottom bar and the rail step aside. Save checks the server's length limits before any request. A group resends each activity's own name and description (a full replace), and a group of mixed types writes no type until one is picked — the web's rule, for the same retyping bug. Saves that already went are skipped on a retry.
- **Delete runs one request at a time** (parallel deletes race each other's coverage re-render) inside a dialog that stays up and resumes from where a failure stopped.
- **Pending** is the web's two Pending effects: a row entering or leaving Pending refetches the tracks and starts the coverage watch, and while any is Pending the list is polled. A failed read reschedules the poll, so a dropped poll doesn't strand a Pending badge. An edit saved from the Track tab also counts as finished the first time a list shows it not Pending, since the job is often done before the reload after the save answers.
- **The Stories tab** (`panel/StoriesTab`) is the web's `StoriesTab.tsx`. A delete drops the Story from the list in hand rather than refetching, for the web's reason: a refetch would bring it back to the open-the-newest rule. The open Story belongs to `MapFragment`, as it's `MapView.tsx`'s on the web, and leaves the range alone; every re-read asks for the open Story, else the range, and an answer for another is dropped. The open Story isn't saved across a recreation.
- **Copies of Stories** (root `docs/IMPLEMENTATION.md` §4.23) are polled only while one is arriving, and an arrival gets the same refresh as a delete.
- **Add to story and New story** keep their dialog up through the request and keep a refusal under the fields, taking over the dialog's confirm button as Delete does.

### 3.3 Spots (`map/MapSpots`, `map/SpotPopup`, `map/ShowInArea`)

The web's `spots.ts`, `SpotPopup.tsx` and `ShowInArea.tsx` (root `docs/IMPLEMENTATION.md` §4.25), on the same tiles and endpoints.

- **`MapSpots` is the layers and the choice**, re-added on every style load. Its layers go on top of everything; `add` puts a layer back under the first of those above it already on the map, which `refresh` relies on when the tile version moves, since a vector source's URL can't change. They're hidden while a track is edited, and left out of Fog's label dimming.
- **The badges are bitmaps drawn once per style load**, since a style reload drops its images. The captured and retired rules are style expressions over the account's capture list, as on the web: the captures are read in full when the overlays attach and only `since` the newest on every resume (`map/CapturesSince.kt`).
- **`spotAt` is asked first on every map tap**, in every mode, unless an editor has the map, so a spot's tap never selects or clears a track underneath.
- **`SpotPopup` is a view, not a MapLibre annotation**, placed above the spot's screen point on every camera move and whenever its height changes, flipping under it when it would pass the top chrome. Its text rules are `map/SpotText`, unit-tested.
- **`ShowInArea` keeps the web component's state.** Its requests can't be cancelled, so a counter drops any answer but the latest; the loaded places are kept for the next style load.
- **Capture mode** (`map/CaptureMode`, FR-2.8 item 6) asks for precise location, since the capture needs a fix within 25 m, and listens on the GPS provider and the rotation sensor only while the map is resumed. **Its rules are plain Kotlin** — `SpotCapture` (the states, dropping inaccurate fixes, and counting at most a few seconds across a gap, so time away counts for little) and `SpotGeometry` (inside-test, nearest point and bearing on a local plane, well under a metre off across a place's few hundred metres) — unit-tested on the JVM. A place retired since the map loaded it ends the mode with its own message. Stopping undoes everything, leaving MapLibre's location component on only if Find my location had it on.

### 3.4 Photos (`photos/`, `map/PhotoMarkers`, `map/PhotoPopup`, `panel/PhotosTab`)

The web's photos (root `docs/IMPLEMENTATION.md` §4.27, ADR-0024), against the same endpoints.

- **Five pure pieces in `photos/`, ported line for line**, with no Android type, so `app/src/test` covers them: the EXIF time rules (`PhotoExifFields`), the slider's walk (`PhotoTrack`), the draft (`PhotoDraft`), the grouping (`PhotoClusters`) and the viewer's zoom math (`PhotoZoom`).
- **`PhotoPrep` decodes a picked photo upright and already scaled** with `ImageDecoder`, so a large photo is never held at full size, and re-encodes it, which drops every EXIF field. `ExifInterface` reads JPEG, HEIC and WebP alike, where the web reads JPEG only. Thumbnails are cached with requests for one path coalesced, since markers are rebuilt on every regrouping.
- **`MapFragment` owns the photos**, as the web's `MapView` does, with the web's scope rule, re-reading when the photos may have changed under it; a generation counter drops a superseded answer.
- **Markers are views, not a symbol layer**, as the web's are HTML markers, in a pass-through layer over the map. A marker's tap is the view's, so the map's own tap handling never sees it and the selection stays.
- **The full-size viewer is in the app**, since a browser tab would have no session. Its fit is worked from the photo's own size, not the bitmap's, so the swap from the smaller copy to the stored one keeps the zoom.
- **The Photos tab's rows are kept for as long as their photo is listed and moved rather than re-inflated**, so an open row's slider and caption survive the renders a drag causes. The slider isn't set from the draft while a finger has it, since the place rounds to a second and would pull the knob back a step. Add photos is registered in `MapFragment`, since only an activity or fragment can register for a result.

## 4. Health Connect Integration

### 4.1 `health/HealthConnect`

The three permission constants, and the readiness state machine (Android SPEC specifies its states).

- **`READ_EXERCISE_ROUTES` is a raw string constant**: the library ships a write-side constant but no read-side one, consistent with a permission the platform won't let an app request programmatically (requesting it silently omits it from what's granted).
- **Readiness is computed fresh on every call, never cached**: the routes permission can only be granted by leaving the app for Health Connect's settings and coming back, so a cached value would be stale at the exact moment the user needs to see it update.
- **The settings intent targets Health Connect's home screen, not its per-app permission page.** The obvious API for the latter is guarded by a signature-level permission, so an ordinary app calling it gets a `SecurityException` that kills the process — found on a device — which is why the onboarding spells out the path by hand.

### 4.2 `health/ExerciseTypes`

A hand-written map from Health Connect's exercise types to HoldMyTrack's `activity_type` vocabulary.

- **Written against public constants, not the library's own int-to-string map**, which is `@RestrictTo` (removable without a semver bump). Every key is a named constant, so a transcription mistake is a compile error, not a mislabeled type.
- **A few entries rename Health Connect's term to the FIT vocabulary** the other ingest paths already speak (biking → cycling, treadmill → running, both swims → swimming), or one real type would split in two in the Type filter.
- **An unmapped type falls back to `"unknown"`**, the value the server already uses for an activity with no type.

### 4.3 AndroidManifest permission declarations

**Exactly three Health Connect permissions, and no more**, since declaring an unused data type is a documented Play Store rejection cause (`docs/VISION.md` §7). `READ_HEALTH_DATA_IN_BACKGROUND` is deliberately absent: measured on a device, granting it changes nothing for route reads (root `docs/IMPLEMENTATION.md` §4.0), so it would only ask for an alarming-sounding permission that buys nothing.

**`SyncActivity` handles Health Connect's rationale intent**, and without a registered handler the permission dialog can refuse to appear at all — found on a device. An `activity-alias` is where Health Connect's own "see how this app used your data" link lands. Arriving by either opens the rationale dialog, only on a fresh start, so a dismissed dialog stays dismissed after a rotation; it leads to `/privacy`, which Health Connect requires.

## 5. Sync Engine

### 5.1 `panel/SyncTab` — the Sync sheet

The Sync tab (`apps/android/docs/SPEC.md` FR-3.2–FR-3.5) is the map's own sheet on a third tab, as Stories is (§3.2): `PanelTab.SYNC`, whose content is `include_sync_content` in the sheet's `FrameLayout` beside the Activities and Stories contents. `MainActivity.showTab(Tab.SYNC)` shows the map fragment and calls `MapFragment.showSync()`, which switches to Normal and calls `ActivitiesPanel.showSync()` (the sheet half-expanded); `onPanelTabChanged` marks the bar's Sync while the panel shows it. A Sync tab restored after a recreation, or opened before the panel exists (`openTab` from `SyncActivity`'s Choose what to sync on a fresh window), is put back once the map's view is up (`pendingSync`, `nav.post`). `ActivitiesPanel.showTab` calls `syncTab.start()` and `stop()` as it does `storiesTab`'s, and `renderTabs` titles the head "Sync" with `sync_subtext` under it.

- **`MapFragment` builds the tab and hands it to the panel**, since it reads the phone and draws on the map: `SyncTab(content, activity, scope, onCandidates, onFrame, onSynced)`. `scope` is the map's view's `lifecycleScope`; `onCandidates` is `drawSyncCandidates` (§5.6); `onFrame` flies to the `BoxUnion` of the candidates' bboxes; `onSynced` reloads the range's list and days and checks the tile version, as a return to the map does.
- **Foreground-only is enforced by cancelling, not by design elsewhere.** `MapFragment.onStop` and `onHiddenChanged(true)` (the You tab over the map) call `pause()`, which cancels a read (`loadJob`) and a run (`runJob`) in flight; `onResume` and `onHiddenChanged(false)` call `resume()`, which lists what's kept again while the tab shows (`restore`). Cancelling is safe by construction: a read replaces what's kept only once it has finished, in one transaction (§5.7), so there's no half-written state to tear down.
- **Opening the tab reads nothing from Health Connect.** `start` and `resume` call `restore`: the recordings from `RecordedActivityStore`, and — while Health Connect is switched on (`SyncSources`) — the sessions `WaitingStore` kept from the last Load, a session still in memory from this one kept in place of its copy since it carries its route; recordings' keys pruned from the hidden set; then `askOverlaps` (`POST /v1/activities/overlaps`) for every listed row. If `SyncSources.firstLoadPending` and Health Connect is readable, it goes on to `loadUpdates`. **Load** is `sync_load` over `sync_checked` (`sync_last_load` with `PanelFormat.phoneDateTime` — the app's language with `Session.country` as its region, in the phone's zone — or not loaded yet, or reading; with no source set up the button is disabled over `sync_no_source`, Health Connect off, or `sync_source_not_set_up`, on and not readable) in `sync_load_column`, beside Sync (`sync_now` over `sync_ticked`) in the bar's `sync_buttons`, stacked by `LargeText.stack` at a large font size: `loadUpdates` runs `WaitingLoader.load` (§5.7) in `loadJob` and takes its sessions, `checkedAt` and refused count, or shows its failure in `sourceProblem`, leaving the list as it was. What a run lands leaves `WaitingStore` (`landed`); a session whose ingest then fails goes back into it (`keepAgain`, written before the next `restore` reads it). The bar is gone only for the demo account, showing with nothing listed; the empty note is `sync_list_not_loaded` until the first load.
- **The list is one `RecyclerView`** (`sync_list`) behind a `ConcatAdapter`: the head (`include_sync_head` — the account notice, the run's results and problems, the Health Connect note — with **Open Sync settings** (`sync_source_settings`) while Health Connect is off or not readable — the type `ChipGroup` — `renderTypes` inflates each chip from `item_sync_type_chip`, `Widget.HoldMyTrack.SyncTypeChip`, on the Profile toggle's `profile_toggle_*` colours, accent-filled while ticked, since Material's own checked tint can't be told from unticked in dark mode — and Select all), the rows (`RowAdapter`, `item_sync_candidate`), and the foot (`include_sync_foot` — the empty note, Show hidden, `sync_tiles` — Upload files to `UploadActivity` and Sync history to `WebPageActivity` (§6), two `Widget.HoldMyTrack.Tile`s by weight, stacked by `LargeText.stack` at a large font size — and **Sync settings** (`sync_sources`) to `SyncActivity`). The head and foot are single fixed views wrapped in `ViewAdapter`; they're inflated against the list, so its `LinearLayoutManager` is set where the list is declared, before them. The bar (`sync_bar` — Load and Sync each over its line, the progress under them) sits above the list rather than under it, so the half-open sheet shows it.
- **Rows are `item_sync_candidate`**, after `item_activity_row`: the type tile (`typeIcon`) is the tick box — ticked, `ic_check` on `hmt_accent`, as an Activities row's check is — the text the row's tap (`pick`: highlight and fly) and long press (tick), a Hidden badge, and a recording's Edit and Delete. `Row` is the diffed model, not `Candidate`, whose line is an array.
- **Similar tracks** (`candidate_similar`, an `ic_info` `RowIcon` in `hmt_accent_strong`, opening `sync/SimilarTracksDialog` over `dialog_similar_tracks`) has two halves. The account's: each time the list is shown and after each Load, `askOverlaps` sends every candidate's key with its `startedAt` and `endedAt` — a session's Health Connect start and end, a recording's start and last point — to `HoldMyTrackApi.activityOverlaps` (`POST /v1/activities/overlaps`, root `docs/IMPLEMENTATION.md` §4.6) and keeps the answer by key: the activity each overlaps the most, with its `id`. The phone's: on every `render`, `sync/Similar.waiting` compares the rows still to be sent — not hidden, not on their way — with each other, by the server's rule ported to Kotlin (`Similar.overlaps`, `MIN_SHARE` for `overlapMinShare`; `SimilarTest` runs the server's `TestOverlapMatches` cases both ways round, so the two can't drift apart). A row with either has the ⓘ, its `contentDescription` the `sync_row_similar` count. In the dialog a waiting row's tap is `pick` — its line framed, its row scrolled to — and the activity's is `MainActivity.viewOnMap` on its day in its own timezone, the path Sync history's View on map takes (§6), titled with its name or `PanelFormat.startedAt` when it has none. The bar's line becomes `sync_ticked_similar` while any ticked row has a ticked twin. A failed request leaves out only the account's half: it's advice, and the list doesn't depend on it. The demo account doesn't ask.
- **Hide is `ItemTouchHelper`** (`SwipeToHide`, either direction, rows only, not during a run) calling `swiped`, which hides or unhides in `HiddenCandidates` (§5.3), unticks, and shows a `Snackbar` with Undo, anchored over the bar when it shows.
- **What's sent is `sendable()`**: the rows shown (after the type chips) that are ticked, not hidden and not on their way. `startSync` cancels a read in flight, runs `SyncRunner.send` in `runJob`, and on its report hands what landed to `SyncProgress` (`landed`: a session's id added to `known`, a recording dropped, both kept in `SyncProgress`) before `show` writes the results and problems.
- **What's on its way is `sync/SyncProgress`**, a process-wide object like `imports/FileImports` (§5.4): the candidates sent whose ingest hasn't finished, for the account they were sent from. While it holds any and has a listener, it asks `HoldMyTrackApi.syncKnown` every 2 s, per source, for their ids (root `docs/IMPLEMENTATION.md` §4.0.3): one still in `processing` stays; one `known` and not processing has landed; one in neither failed — it's kept for `takeFailed`, and a recording is put back in `RecordedActivityStore`, since the phone held its only copy. A dropped read decides nothing. `MapFragment` listens from `onStart` to `onStop` and runs `onSyncedFromPhone` for each landing, so the list, its days and the tiles catch up whichever tab shows — before, the job was only queued, with no row to show Pending, so `trackPending`'s poll had nothing to wait on. `onSyncedFromPhone` fetches the tracks tile again at once (`MapOverlays.refreshTracks`): it's read from the activities as they are, while the tile version `checkTileVersion` watches only moves once the coverage render after the ingest has finished, so waiting on it left a landed track undrawn until then (found on the emulator). `SyncTab` listens from `start` to `stop`: `all()` and `shown()` add `SyncProgress.candidates` to `SyncCandidates.listed` (`withInFlight`), and each change renders again; a failure (`showFailed`, also on `start`, for one that failed while the tab was away) adds a line to `problems`, takes the session out of `known` and reads the list again. `load` adopts a session the server says is still processing — sent before the tab last closed, or from another phone — so it reads the same. A processing row (`Row.processing`) swaps the tile for `candidate_processing`, a `CircularProgressIndicator`, says `sync_row_processing` in `candidate_overlap`, and can't be ticked, swiped, edited or deleted; it isn't drawn on the map (`onCandidates`), framed, or sent to the overlap hint, since it would only overlap itself once it lands.
- **The empty map's notice steps aside on the tab** (`updateNoticeVisibility`, called again on every panel tab change), as it does while recording: it points to Sync, and would cover the candidates' lines.
- **The demo account** reads no Health Connect and has no bar; its rows can't be ticked (`RowHolder.bind`), and the Health Connect card and Upload files are hidden (`render`).
- **`SyncActivity` is Settings › Sync** (`activity_sync`), opened from the You tab (§2.7), the Sync tab's two links and Health Connect's entry points (§4.3), signed out included: the Health Connect card (`include_health_connect_card`), the Recorded on this phone card (`sync_recorded_section`, no switch; `renderRecorded` tints `sync_recorded_icon` and `sync_recorded_status` `hmt_success` while `ACCESS_FINE_LOCATION` and `POST_NOTIFICATIONS`, the record button's two, are both granted), its own permission launcher, `HealthConnect.access` on every resume, the rationale on a fresh start, and **Choose what to sync** (`sync_open_list`, `MainActivity.openTab(Tab.SYNC)`) for a signed-in, verified, non-demo account. **The switch is `sync/SyncSources`**: `hc_enabled.$account` in the `holdmytrack.sync` file beside the hidden rows (§5.3), false until the user turns it on, whatever Health Connect already granted; `WaitingLoader` reads Health Connect only while it's true. Turning it on sets `hc_first_load.$account` (`firstLoadPending`); turning it off clears that and `WaitingStore`. `firstLoadIfDue`, from each `render`, runs `WaitingLoader.load` on this screen once Health Connect is readable, showing `sync_first_load` in the card (reading, then the `sync_first_load_found` count or the failure); `onStop` cancels it, and the flag, still set, has the Sync tab's next `restore` run it instead. Turned on with `NEEDS_EXERCISE_PERMISSION`, `switched` calls `HealthConnectCard.requestNext`, the same dialog the card's step opens. `sync/HealthConnectCard` is the card's code: `render(on, access)` draws it off (`renderOff`, the switch disabled when Health Connect is `UNAVAILABLE`) or on — `renderChecklist` ticks `sync_check_sessions`, `_routes` and `_history` from `access.granted` (`ic_check` in `hmt_success`, else `ic_circle_dot` in `hmt_ink_faint`, each with an allowed/not-yet `contentDescription`) — and then the six-state switch `apps/android/docs/SPEC.md` FR-3.1 specifies; a `rendering` flag keeps its own `isChecked` from reading as the user's flip; `openSettings()` catches broadly (`Exception`, not just `ActivityNotFoundException`) because the failure actually met in development was a `SecurityException` from an earlier attempt at `ACTION_MANAGE_HEALTH_PERMISSIONS` (§4.1) — a button that can't open a screen says so in the status text rather than crashing the app around it.

### 5.2 `sync/SyncCandidates` and `sync/SyncRunner`

What's waiting, and sending what's ticked.

- **`SyncCandidates.readHealthConnect`** pages `readRecords(ExerciseSessionRecord)` with `TimeRangeFilter.after(now − WINDOW)` (90 days), newest first, 100 a page, keeping each `ExerciseRouteResult.Data` with at least 2 points and counting the rest of the non-`NoData` results as `refused` — `ConsentRequired`, a route that's there but wasn't handed over. Without `READ_HEALTH_DATA_HISTORY`, Health Connect itself cuts the window to 30 days.
- **A `Candidate`** carries what the list, the map and the send need: `key` (`source:externalId`, unique across both origins — what the hidden set stores), the start, type and distance, a recording's name, `line` (the route through `map/Simplify`, `[lon, lat]` pairs) and `bbox`, the point count, and `origin` — `HealthConnectSession` (the record and its route as read) or `Recording` (the stored record). A session's distance is `map/Geo.lengthM` over its route, since no distance is read from Health Connect; a recording's is the one it was saved with. `build` is pure, and `listed` — sessions not `known`, plus recordings, minus hidden unless shown, newest first — is the whole of the list's rule; `SyncCandidatesTest` covers both.
- **"Known" is the server's** (`HoldMyTrackApi.syncKnown`, `POST /v1/sync/known`, chunked at 5,000 ids), asked with every session's id on each Load (§5.7); recordings aren't asked about, since one that synced is deleted from the phone. There is no cursor: each Load works the list out again from Health Connect and the server, which is what lets a reinstall or a second phone agree with the server and an activity deleted on the web come back.
- **`SyncRunner.send(ticked, onProgress)`** sends Health Connect's ticked sessions in batches — up to 25 activities or 20,000 points, stricter than the server's 100 so one request stays modest on mobile data — under `healthconnect`, then each ticked recording in a request of its own under `recorded`, deleting it from `RecordedActivityStore` once the server has it. A session restored from `WaitingStore` has no `origin`; `withRoute` reads it again by its id (`SyncCandidates.reread`: `readRecord`, then its `exerciseRouteResult`) through the `HealthConnectClient` the tab passes in, and reports one that's gone (`sync_refusal_gone` — `readRecord` throws for a missing id) or whose route isn't handed over (`sync_refusal_route`) as refused. A route of more than 50,000 points (`MAX_POINTS_PER_ACTIVITY`, the server's own ceiling, root `docs/IMPLEMENTATION.md` §4.0.3) is reported as refused rather than sent. `flush` sorts the per-activity verdicts into `landed` (`enqueued` or `already_processed`) and `Rejection`s with the server's reason; a failed request returns its message and stops the run, leaving the rest ticked. The report is what the tab takes off the list and what it says.
- **`prepare()` builds each activity's JSON off the main thread** (`Dispatchers.Default`) from the route as read, never the simplified line: a session's points with elevation only when the location carries it — there is no default-to-zero, because zero is a real, wrong value for "unknown altitude" — and a recording's own `toSyncJson()`.

### 5.3 `sync/HiddenCandidates`

The rows swiped aside: a string set of candidate keys under `hidden.$account` in the `holdmytrack.sync` `SharedPreferences` file — per account, like the recordings (§7.2), so two people on one phone each set aside their own. It's pruned with `retainOnly`: a recording's key by `SyncTab.restore` once the recording is gone; a session's by `WaitingLoader` only after a Load that refused nothing, so a route that merely couldn't be read this time keeps its place. `settings/AccountDeletion.forget` clears it with the account's recordings. The same file keeps Settings › Sync's switch and whether its first load is still due (`sync/SyncSources`, §5.1).

### 5.4 `UploadActivity` and `imports/FileImports` — uploading files

The Upload screen (`apps/android/docs/SPEC.md` FR-3.6), from Sync's Upload files tile, is the web's Upload menu (`services/server/internal/web/static/upload.js`) ported, against the same `POST /v1/activities/upload` (root `docs/IMPLEMENTATION.md` §4.0.1), with no Android-only server work.

- **A process-wide object, not the screen's.** `FileImports` holds the queue, the transfers and the notes and runs on its own `CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)`, so an upload outlives a rotation or a trip to another app, unlike a Health Connect read or send, which `onStop` cancels on purpose (§5.1). `UploadActivity` registers a listener in `onStart`, removes it in `onStop`, and redraws from `transfers` and `notes` on each change (`render`). `sentCount` moves each time a file has gone, and once it's above zero the screen shows See them in Sync history, which opens Sync history, the web's `/sync` page (§6), in its place.
- **`enqueue` is `upload.js`'s `enqueue`**: more than `MAX_FILES` (20) files are all refused, and a `.zip` is named as not imported (`upload_zip_refused`, ADR-0039). Two checks the web doesn't make: a name that isn't `.gpx`/`.fit`/`.tcx` gets a note rather than being dropped silently, and a file over the server's limit (16 MiB, `services/server/internal/httpapi/server.go`) is refused before it's sent.
- **The picker asks for `*/*`.** Providers label these files inconsistently — the emulator's Downloads called a `.gpx` a "BIN file", `application/octet-stream` — so filtering by MIME type would hide the very files asked for, and `enqueue` decides by name instead.
- **One file at a time**, as on the web. `HoldMyTrackApi.uploadActivityFile` streams the file into the multipart body (`UriRequestBody`, read 64 KiB at a time from `ContentResolver.openInputStream`, and opened afresh on each `writeTo`, so OkHttp's retry resends all of it) rather than reading it into memory, since a file can be 16 MiB. Progress comes back on OkHttp's thread and is posted to the main thread once per percent. The call goes through `uploadClient`, the app's client with a 2-minute write and 10-minute read timeout: a 16 MiB file over a slow connection takes longer than the default ten seconds.
- **`UploadOutcome`** is what the response says: `already_processed` for a file, noted as the web notes it. A non-2xx answer is an `ApiException` with the server's own text, noted as "{file}: {reason}".
- **Opened or shared files.** `UploadActivity` has `VIEW` and `SEND`/`SEND_MULTIPLE` filters for `application/gpx+xml`, `application/vnd.garmin.tcx+xml`, `application/zip` and `application/x-zip-compressed`; `importShared` (from `onCreate` and `onNewIntent`) hands their URIs to `enqueue` when `canUpload()`. A `.fit` has no MIME type apps agree on, and most hand a `.gpx` over as `application/octet-stream`, which the app doesn't claim, since it would then offer itself for every binary file; those are picked in the screen.

### 5.6 `map/SyncCandidatesOverlay`, `map/Simplify` and `map/Geo` — the candidates on the map

- **The account's tracks step aside on the tab**: `MapOverlays.setSyncing`, after `setEditingTrack`, sets a flag `setMode` reads, hiding the track layers and the bands while it's set. `MapFragment` sets it from the panel's `onTabChanged` and again when a new style is attached, so only the candidates are drawn, not the date range's slice of what's already synced.
- **`SyncCandidatesOverlay` is `TrackEditOverlay`'s pattern** (§3): one `GeoJsonSource` (`sync-candidates`) and three `LineLayer`s filtered on a `role` property, added under the basemap's first symbol layer by an idempotent `ensure`, then a second source and layer for the bands. In paint order: `sync-candidates-halo` is the picked one's halo, `MapOverlays.CASING_*`; `sync-candidates-line` is every candidate dashed (`lineDasharray(1.5, 1.5)`) in `MapOverlays.TRACK_COLOR`; `sync-candidates-highlight` is the picked one, solid at `MapOverlays.SELECTED_WIDTH`, drawn last; `sync-candidates-bands` is its pace bands, `MapOverlays.bandFeatures` of its `Candidate.metrics` — the same features `setTrackBands` draws for the Map tab's selected activity. `set(style, candidates, highlight)` rebuilds both `FeatureCollection`s, each line carrying its `key`; `clear` empties them; `keyAt` queries the line and highlight layers within 14dp of a tap. `MapFragment.renderTrackMetrics` leaves the Map tab's own bands off while the Sync tab shows, so only one set is on the map.
- **`MapFragment.drawSyncCandidates`** is `SyncTab`'s `onCandidates`: it keeps the list and the highlight (`syncCandidates`, `syncHighlight`) and draws them if the style's overlays are attached, and the overlay attach block draws them again after a style reload, which drops every custom layer. `SyncTab.render` calls it on every change, and `stop()` with nothing, which clears it. The account's own tracks stay drawn under the candidates, so what's already on the map shows beside what isn't.
- **A tap on the map while the Sync tab shows** goes to `keyAt` before anything else in Normal mode's tap handling, and a candidate under it is `SyncTab.focus`ed — picked out and its row scrolled to; a tap elsewhere does nothing there. The sheet stays visible on the Sync tab while recording (`renderDateFooter`'s `syncing`), so what's on the phone can be sent with a walk under way.
- **`Simplify.indexes`** is Douglas–Peucker over a route in metres, on a local equirectangular plane around its first point, iterative so a long ride can't overflow the stack; points under `TOLERANCE_M` (15 m) off the line go, and past `MAX_POINTS` (500) the tolerance doubles until the line fits. For drawing only — `SyncRunner` sends the route as read. `SimplifyTest` covers it.
- **`SyncCandidates.metrics`** gives each kept vertex its speed by the server's `track-metrics` rule (`docs/IMPLEMENTATION.md` §4.3.1): haversine from the vertex before over the whole seconds between them, 0 where no second passed, the first vertex taking the second's. `build` reads the times from a Health Connect `ExerciseRoute.Location` or a `RecordedPoint`. The phone's 15 m tolerance is coarser than the server's (about 3 m), so a candidate's bands are a little smoother than the same activity's once synced. `SyncCandidatesTest` covers the rule.
- **`Geo`** is the server's haversine on the IUGG mean radius, `haversineM` and `lengthM` — a Health Connect session's distance, and `MapFragment`'s photo-group spread.

### 5.7 `sync/WaitingLoader` and `sync/WaitingStore` — Load

Health Connect is read in one place. `WaitingLoader.load` returns `Unreadable` for the demo account, with the switch off or Health Connect not readable; otherwise it reads the sessions (`SyncCandidates.readHealthConnect`), asks `syncKnown` about them, hands those still `processing` to `SyncProgress`, prunes hidden sessions after a read that refused nothing (§5.3), and keeps the rest — `WaitingStore.replace`, the sessions, the time and the refused count in one transaction — clearing `firstLoadPending`. A failure is `Failed` with `sync_read_failed`, and changes nothing. Its callers are `SyncTab.loadUpdates` and `SyncActivity.firstLoadIfDue`, each in its own screen's scope so leaving the screen cancels it (§4.0's foreground rule).

`WaitingStore` is a second `SQLiteOpenHelper` database, `holdmytrack-sync.db`, beside the recordings' (§7.2), every row keyed by `account` (`Session.email`): `waiting`, one row per session — key, external id, start and end, type, distance, point count, bbox as text, and `vertices`, the drawn line's vertices with their speed and time packed 32 bytes each (`WaitingStore.Vertices`, round-tripped in `WaitingStoreTest`) — and `waiting_checked`, the last read's time and refused count. `Candidate.line` is rebuilt from `vertices`, since `SyncCandidates.build` keeps the same vertices for both. The route isn't kept: a restored session has no `origin`, and `SyncRunner` reads it again when it's sent (§5.2). `put` brings back a session whose ingest failed, `remove` drops what a run landed, and `clear` runs when Health Connect is switched off and in `AccountDeletion.forget`.

## 7. In-App GPS Recording

`recording/` (`RecordingService`, `RecordingActivity`, `recording/db`), the Sync tab's rows (§5.1), plus the record button and live-track layer on the map (`MapFragment`, `map/MapOverlays`) own this feature end to end. The wire contract it submits to — `POST /v1/sync/activities` under `source = "recorded"` — is specified server-side in `docs/IMPLEMENTATION.md` §4.0.4, along with [ADR-0007](../../../docs/adr/0007-in-app-gps-recording-submits-directly.md)'s decision not to add a new endpoint for it. What follows is the client half that decision left to this app to design.

### 7.1 Recording and submitting are two separate steps, not one

**Recording is one tap, and nothing is asked.** The record button is `MainActivity`'s, raised over the bottom bar's middle slot (`record_button` in `activity_main`: a surface disc ringed in the border colour, red while recording and amber while paused, its pause and play icons tinted to match), and `MapFragment` drives it — a start from Sync or You first shows Map (`MainActivity.showMap`). It is 56dp idle and 60dp while a recording is active (`sizeRecordButton`, a bigger target for the hold with less of it under the finger): tap to start, tap to pause/resume, hold for two seconds to stop. The button is `recording/RecordButton.kt`, an `AppCompatImageButton` that replaces the platform long-press with its own: while `holdEnabled` (set by `renderRecording` whenever a recording is active) an `ACTION_DOWN` starts a 2 s `ValueAnimator` that draws a 5dp white arc on a translucent black track 5dp outside the button's edge, where a fingertip on the button doesn't cover it; it gives a `SEGMENT_TICK` haptic at each quarter, reports its progress through `onHoldProgress`, and on completion gives a `CONFIRM` haptic and calls `onHoldComplete` (`MapFragment.stopRecording`). Releasing early cancels; the click that release would produce is suppressed unless it came within `ViewConfiguration.getLongPressTimeout()`, so an abandoned hold never pauses. TalkBack gets the stop as the node's `ACTION_LONG_CLICK`. While `pulsing` (recording, not paused) an infinite 1.6 s animator draws a red halo widening 8dp out from the button and fading, stopped when paused, idle or detached. Every tap is felt: `startRecording` gives `CONFIRM` and a 1.15× scale pop, `onRecordTap` gives `TOGGLE_OFF` on pause and `TOGGLE_ON` on resume — on the button, so the system's touch-feedback setting applies. A tap that pauses also shows a short "Hold to stop recording" toast (`onRecordTap`), since a tap is the obvious guess at stopping and it only pauses; resuming shows nothing. The first tap asks for `ACCESS_FINE_LOCATION` and `POST_NOTIFICATIONS` together; only location is required to start. The button only sends intents — `RecordingService.ACTION_START` (via `startForegroundService`), `ACTION_TOGGLE`, `ACTION_STOP` — and the service's own notification carries Pause/Resume and Stop actions — Pause/Resume sends `ACTION_TOGGLE` straight to the service; Stop opens `MainActivity` with `ACTION_STOP` as its intent action, which it hands to `MapFragment` (`handleStopIntent`, ignored on a relaunch from recents), because the Save screen that follows needs an app window in the foreground to open over, and because it's confirmed there first: `confirmStop` shows "Stop recording?" with the time and distance so far (`currentStats`), in the destructive dialog style, and only its Stop calls `stopRecording`. One tap in the shade is an easy mistake where the map's hold is its own confirmation, so the map's stop never asks. A Stop that arrives before the bind answers sets `pendingStopConfirm`, and `onServiceConnected` asks then; nothing is asked if the recording is already idle, a second Stop while the dialog is up is ignored, and `renderRecording` dismisses the dialog if the recording ends under it.

**The status card in the mode toggle's place** (`recording_status`, a `MapPanel` the width of the top row's start column) is the on-map "is it recording?" answer, so a start is never in doubt without opening the shade. `renderRecordingStatus`, run from `renderRecording` on every state change and fix, shows it only while a recording is active: a 10dp dot (`hmt_record` red, `hmt_record_paused` amber), a `Chronometer` in the serif title size whose base is the service's `currentStats().elapsedMs` back from now — ticking on its own while recording, stopped while paused — and a detail line: the distance, "Waiting for GPS…" until `points()` has a fix, or "Paused · distance". The Chronometer's text comes from a tick listener in `RecordingFormat.duration`'s h:mm:ss, the notification's format; stopped, nothing ticks after `setBase`'s own redraw, so the paused time is set directly. During a hold, `renderHoldProgress` replaces the detail line with "Keep holding to stop…" and shows a red `LinearProgressIndicator` filling with the ring. Its **Stop** (`recording_status_stop`) asks first, as the notification's Stop does (`confirmStop`), since a tap on a button in reach is easy to make by mistake where the record button's hold is its own confirmation. `MapFragment` binds to the service from `onStart` to `onStop` purely to watch it (`onChange`, `points()`), which is also how reopening the app mid-recording (even after swiping it out of recents — the foreground service keeps running) redraws the whole track so far.

**While recording, the map shows that recording and nothing else.** `MapOverlays.setRecording` hides every user layer (history tracks, fog, heatmap at every tier) and `MapFragment` hides the mode toggle; ending the recording restores whichever mode was selected. The live track is a `GeoJsonSource` line plus a dot at the latest fix (`MapOverlays.attachLiveTrack`/`updateLiveTrack`), added at style load on top of every other layer and redrawn from the service's point list on each fix. The camera flies to the first fix at zoom 16 (or the current zoom, if closer) and eases to each later one, so a zoom the user picks sticks. A recording's own points never reach the history layers: those are server tiles, and nothing unsynced is on the server.

**The notification is the "am I recording?" indicator and the stats readout.** One ongoing notification for as long as a recording is in progress: title "Recording" with the system chronometer counting elapsed time (so the service doesn't re-post every second), or "Paused · h:mm:ss" with the time frozen; text is distance · current speed · current altitude, re-posted on each fix and state change. Its channel is `IMPORTANCE_DEFAULT` with sound and vibration off, not `IMPORTANCE_LOW`: a low-importance notification is filed under the shade's collapsed "Silent" section, which hides its action buttons behind an extra tap — found on an emulator. Channel importance can't be raised once created, so the channel id is `recording_status` and the service deletes the earlier `recording` channel.

**Stop saves in the service, not in a screen**, because Stop can come from the notification with no screen open. `RecordingService.stop` drops the recording, with a "Too short — not saved." toast, if its moving time (pauses excluded) is under `MIN_DURATION_MS` (60 s) or it has fewer than 2 points; otherwise it inserts a row with a blank name and description and `RecordingTypes.lastUsed` as its type (§7.5), in the same transaction that clears the recording's journal (§7.9), on an application-lifetime coroutine scope, since the service itself may be destroyed as soon as it leaves the foreground. Once the insert lands it starts `RecordingActivity.saveIntent` (`FLAG_ACTIVITY_NEW_TASK`, allowed because a stop always comes from `MapFragment` in the foreground): the same edit form with `EXTRA_JUST_STOPPED`, titled "Save recording", Download GPX swapped for Discard (confirm, then `store.delete`). Saving first and asking second means Back, or the activity never getting to open, still leaves the recording stored with the last-used type — the screen only refines a row that already exists. Name, type and description are otherwise set from a Sync sheet row's Edit (the same `RecordingActivity`).

Stopping a recording only persists it to `recording/db/RecordedActivityStore.kt`; nothing reaches the network until the user ticks it on the Sync sheet and sends it (§7.1.1). `SyncRunner.send` (§5.2) submits each ticked recording, after the ticked Health Connect sessions, as its own call to `POST /v1/sync/activities`, deleting it from the device on `"enqueued"`/`"already_processed"` — from then on the activity lives on the server (the map, the activity list), and the Sync sheet only ever lists recordings that haven't synced. A rejected or failed row is left where it is, listed and still ticked, to be sent again. A recording that shouldn't reach the map is deleted, or hidden (§5.3).

`activity_type` is free text here, not the fixed vocabulary `health/ExerciseTypes.kt` (§4.2) normalizes Health Connect sessions onto — there's no platform exercise-type field to normalize from on this path. `external_id` is a UUID the app mints when a recording starts (`java.util.UUID.randomUUID()`, which also keys its journal, §7.9), not a platform record id — unlike Health Connect/HealthKit, there is no platform health store handing this activity an identity, so the client originates one itself.

### 7.1.1 A recording's row on the Sync sheet

A recording is one of the Sync tab's candidates (§5.1, §5.2): `SyncCandidates.fromRecording` makes it from the stored row, and `SyncTab`'s `RowHolder` draws it as any other, with no preview of its own — its line is on the map (§5.6) — and adds Edit and Delete as Lucide `pencil` and `trash-2` icon buttons (`Widget.HoldMyTrack.Button.RowIcon`, 48dp), Delete in the danger color, each labelled with the row's title for TalkBack. Edit starts `RecordingActivity` with `EXTRA_RECORDING_ID`; Delete confirms, then deletes the row and forgets it in the hidden set. The recordings are read again on every return to the tab (`restore`), which is how it learns of an Edit. Checked on the emulator: a recording saved through the Save screen was listed unticked as "Oct 9, 2026, 10:09 AM · 0.6 mi · Unknown · Recorded on this phone", drawn dashed on the map; ticked and sent, it left the list and reached the server as a `recorded` activity.

The Edit and Save form (`RecordingActivity`, `activity_recording.xml`) follows the web's edit window (`EditActivityWindow.tsx`): the web's 10dp gap between fields, Time and Distance as labelled figures — the label in the list-heading style (`Overline`), the value 20sp bold with tabular figures (`fontFeatureSettings="tnum"`) so the clock doesn't jitter — and the Save screen's Discard as an outlined button with a danger label (`Widget.HoldMyTrack.Button.Danger`). Checked on the emulator in English and Russian, on both the Edit and the Save screen with their Delete and Discard dialogs.

### 7.2 `recording/db/RecordedActivityStore`

Plain `SQLiteOpenHelper`, not Room: this project's Kotlin toolchain — AGP's built-in Kotlin at the time this was built — was newer than any published KSP release, confirmed by trying it (a `com.google.devtools.ksp` version matching Kotlin 2.4.0 does not exist on Maven Central) rather than assumed from documentation.

**The table is scoped per account.** Without it, a recording made under one account (or the shared demo session) would show up in another's list of recordings on the same device. An `account` column scopes every query (`all`, `get`, `update`, `delete`) to `Session.email` — the same per-account key the Sync tab's hidden rows use (§5.3), a demo account sharing one empty-string key across every demo session. That sharing is harmless: a demo account can never sync regardless (§7.4), so nothing recorded under it ever reaches the server no matter which demo session later sees it locally. `RecordingDbHelper` is at schema version 5. From version 1, `onUpgrade` drops and recreates rather than a hand-written `ALTER TABLE`, the same "no migration tooling needed pre-launch" call the server side already makes. Version 3 changes no columns: it deletes rows with a `synced` status (§7.1 — a synced row is deleted, not kept) and keeps every unsynced row, since those exist nowhere else. Version 4 adds the journal's two tables (§7.9) and touches nothing else; the database is in WAL mode, since the journal commits on every fix while other screens read. Version 5 drops `sync_status` (`ALTER TABLE … DROP COLUMN`, which the platform's SQLite has from Android 14, the app's `minSdk`): a row is deleted once sent, so there is no queued mark left to keep. Checked on the emulator by upgrading a version-4 database in place, then saving and syncing a recording.

### 7.3 Delete is local-only

Every recording row on the Sync sheet is unsynced (§7.1), so Delete, after a confirmation that says so, discards the only copy of that recording. It never reaches the server; once a recording has synced, deleting it is the server-side delete (`docs/IMPLEMENTATION.md` §4.7.4) from the web app, since the phone no longer holds it.

### 7.4 Demo accounts are blocked from sync client-side too

Matching the web's own pattern (its Upload control disabled with a tooltip saying why), not just the server's `requireNotDemo`, so a demo session never meets the block as a raw `demo_read_only` error through a generic failure path. `Session.isDemo` (§2.1, `isSignedIn && email.isEmpty()` — the emptiness the class uses to mean "demo") is checked: the Sync sheet shows an explanatory notice, reads no Health Connect, hides the bar with Sync, the Health Connect card and Upload files, and makes no row tickable — and keeps the demo account's recordings and its history listed, reading not being a mutation.

### 7.5 A recording's starting type

A recording's `activity_type` is only ever set through Edit, and until the account has set one it is `RecordingTypes.DEFAULT` (`"unknown"`). An untyped row syncs like any other: the overlap rule (`docs/IMPLEMENTATION.md` §4.6) compares time, not type, so an `"unknown"` recording still gets the ⓘ beside the same walk from Health Connect as `"walking"`.

Since recording asks nothing, most recordings would otherwise stay `"unknown"` until edited. `RecordingTypes.lastUsed` avoids that: every Edit save with a real type records it in a per-account preference (`holdmytrack.recording`, key `last_type:{Session.email}` — the same account key as the store), and each new recording starts on that type. So only an account's first recording starts untyped; after that, a recording usually carries the right type as-is and is edited only when it was a different kind of activity. A preference rather than "the newest row's type" because synced rows are deleted and the store is often empty. Clearing a row back to `"unknown"` is never remembered.

### 7.6 Type picker (`recording/ActivityTypePicker`)

The Type field on the Edit screen is the Android counterpart of the web edit dialog's `ActivityTypePicker.tsx` (`docs/IMPLEMENTATION.md` §4.7.4): a tap-to-open trigger showing the formatted type, which opens a dialog with a search field over the account's existing types, most-used first with each one's count, filtered as you type with `SearchPicker.tsx`'s own ranking (exact whole-label match, then word-start, then substring) and accent/case folding. While the search text doesn't exactly match an existing type, a last **Add "…"** row saves it exactly as typed, up to the server's 50-character `maxActivityTypeLen`; the keyboard's Done picks the top row.

The list is `RecordingTypes.known`: the server's per-type counts (`HoldMyTrackApi.activityTypeCounts`, read once when the screen opens), plus this device's recordings (all unsynced — a synced one is deleted locally and counted in the server's number instead), then any of the walk/hike/run/ride/drive `RecordingTypes.PRESETS` the account hasn't used, uncounted — so a new account still starts on the shared vocabulary `health/ExerciseTypes.kt` uses. `"unknown"` is left out as a choice, and a current value missing from the list is shown at the top so the current choice is always visible. Labels use `RecordingTypes.format`, the same `snake_case`-to-title-case display as the web's `formatActivityType`; the stored value is always the raw string. A dialog rather than a dropdown under the field, because the soft keyboard takes half the screen and a dialog keeps both the search field and the list above it.

### 7.8 GPX download

Edit mode's **Download GPX** writes the recording as a GPX 1.1 file (`RecordedActivityRecord.toGpx`: one `<trk>` carrying `<name>`, `<desc>` and `<type>`, one `<trkseg>` of `<trkpt>`s with `<ele>` where known and `<time>`). The file goes through the system's own save screen (`ActivityResultContracts.CreateDocument`), so the user picks the destination and the app needs no storage permission. GPX because every other mapping tool opens it, and HoldMyTrack's own upload parses it (`internal/parse/gpx.go` reads `<trk><type>`), so a downloaded track can come back in unchanged.

### 7.9 Crash and kill recovery (`recording/db/LiveRecordingJournal`)

`RecordingService` keeps the recording in memory — the point list, distance, moving time — and a foreground service survives the screen going away, not the process: a low-memory kill, a crash or Force stop takes all of it, and the notification with it. So every fix is also written to disk as it arrives, to a journal in the same database: `live_recording` (one row: id, account, moving time, distance) and `live_points` (one row per fix, keyed by recording id and sequence number). A row per fix rather than rewriting `points_json` keeps each write constant-size over a multi-hour recording; at one fix per ≥3 s that is about 1,200 small commits an hour. Writes are queued in order on one single-threaded dispatcher on an application-lifetime scope, and a failed write is logged rather than thrown, so a full disk doesn't end the recording.

What is written when: Start inserts the `live_recording` row, with the recording's id (the `external_id` it will sync under, minted here rather than at Stop) and the account signed in at that moment; each fix appends its point and updates moving time and distance in one transaction; a pause updates moving time, since the time moved since the last fix would otherwise be lost. Moving time is stored as a number rather than as `elapsedRealtime` marks, which reset on reboot. Stop (or a too-short drop) moves the recording into `recorded_activities` — or nowhere — and deletes the journal in one transaction (`finish`), so there is no moment when a stopped recording is in neither place. A journal row with no recording running in this process is therefore always a leftover from one that died.

**Recovery is offered, not automatic.** The service stays `START_NOT_STICKY`: a sticky restart counts as a start from the background, which gets no while-in-use location access, so a location foreground service restarted that way could fail or record nothing, and it would resume without the user knowing. Instead, whenever `MapFragment` binds and the service is idle, `findLeftover` looks for a journal row — queued behind pending writes, so a Stop that has only just happened is never mistaken for one — and, if there is one under the signed-in account, the map shows a non-cancellable "Unfinished recording" dialog with its moving time and distance: **Resume** loads the points and totals back into the service as **paused**, with `lastFix` cleared, so the time the process was dead adds neither moving time nor distance, and starts it as a foreground service again (allowed, the map being in the foreground); it fails with the location-needed toast if location access has been revoked since. **Save** goes the way Stop does — the minimum-length check, the row, the Save screen. **Discard** confirms first ("Discard this recording?"), since the journal holds the only copy; Cancel brings the prompt back. Another account's leftover isn't offered, since its Save screen would find nothing under the signed-in account; it waits for that account. A Start that finds a leftover the prompt never got to (another account's, or a tap before the prompt came up) saves it as it stands, under its own account and that account's last-used type, rather than overwriting it — the journal holds one recording at a time.

### 7.10 Verified on device

The map-button flow, on an emulator (the `fitmap` AVD, against a local `db`/`api`/`worker` stack, GPS fed with `adb emu geo fix`): the first tap raised the location and notification prompts and started recording; the mode toggle disappeared and the live line grew with the camera following; tapping paused (the notification read "Paused · 0:01:44" and a far-off fix sent while paused added no point) and Stop from the notification saved a 26-point row; a ~20 s recording stopped by long-press was dropped (no database created, notification gone); swiping the app out of recents mid-recording and reopening it redrew the full track and recording continued; the first recording saved as `"unknown"`, was set to walking in Edit, and ticked and sent from the Sync tab it became a `walking` activity server-side and left the device; the next recording then saved as `walking` with no Edit.

Resume came back paused with the same totals in the notification; resuming there and recording from ~850 m away brought the distance to 478 m, with nothing counted across the gap, and Stop saved all 30 points under the journal's id and opened the Save screen. Save from the prompt, after a second kill, saved the row and opened the Save screen; Discard asked for confirmation, Cancel brought the prompt back, and Discard emptied the journal and left the saved rows alone; the next launch offered nothing. The database upgraded from version 3 on that install. Russian strings not yet checked on screen.

On a Pixel 10a: a recording made under the demo session was kept on the phone, and after signing out and into a real account it wasn't listed there (`apps/android/docs/SPEC.md` FR-5.3).

## 8. Build Configuration

`BuildConfig.API_BASE_URL` is the one build-time value that comes from outside the build, set per build type from a Gradle property: debug from `holdmytrack.apiBaseUrl` (`gradle.properties` defaults it to `http://10.0.2.2:8080`, the emulator's alias for the host loopback), release from `holdmytrack.releaseApiBaseUrl` (`https://holdmytrack.com`), so the Play build can't pick up a dev stack's address. The release build is signed by the `release` signing config, which reads the upload keystore's path, alias and passwords from `holdmytrack.upload*` properties kept outside the repository (`apps/android/holdmytrack/README.md`, Release build). Pointing a physical device at a host dev stack over USB requires `adb reverse` for both the API port and the web dev server port the style document's asset URLs resolve against (`BASEMAP_ORIGIN`, `docs/ARCHITECTURE.md` §2.1) — documented with exact commands in `apps/android/holdmytrack/README.md`. The other, `BuildConfig.DONATE_LINK`, is set per build type: `true` in debug, the APK the website offers (`docs/DEPLOY.md`), and `false` in release, the Play build, whose payments policy doesn't allow a link to payment outside Play's billing (`apps/android/docs/ROADMAP.md` Phase 6). `MapFragment.showMenu` leaves Donate out when it's false.

**The version comes from git.** `app/build.gradle.kts` sets `versionCode` to the commit count (`git rev-list --count HEAD`), so it rises with every commit and never needs bumping — Play refuses an upload whose code isn't higher than the last — and bakes the short SHA in as `BuildConfig.GIT_SHA`, the same one the server's `/healthz` reports. `versionName` is the release number, `0.13`, changed by hand when a release means something. Outside a git checkout the code is 1 and the SHA `dev`. `HoldMyTrackApi.appVersion` joins the two — "0.13 (62da50b)" — for the You tab's last line (`apps/android/docs/SPEC.md` FR-2.9) and the `User-Agent` the app sends on its own API requests (`HoldMyTrack-Android/0.13 (62da50b)`, `UserAgentInterceptor`); other origins keep MapLibre's own. Nothing on the server records the User-Agent yet: neither the API nor Caddy writes access logs.

**Cleartext `http://` traffic is permitted in debug builds only** (`app/src/debug/AndroidManifest.xml`), so a release build cannot be pointed at a plaintext dev endpoint by accident — the network security configuration itself is what enforces this, not a code-review convention.

`libs.versions.toml` pins every dependency version with an inline rationale for why that version specifically (MapLibre's pmtiles-support floor, the Health Connect version the device measurements were taken against, OkHttp pinned to what MapLibre's own POM resolves to rather than left implicit) — the versions themselves are covered in `apps/android/docs/ARCHITECTURE.md` §2; this file is where the *reasoning* for each pin lives, so an upgrade is a decision made against that reasoning rather than a blind bump.

**Languages: English and Russian** (root `docs/IMPLEMENTATION.md` §4.21). All the app's text is in `res/values/strings.xml`, with Russian in `res/values-ru/strings.xml`. Strings that are the same in every language (`app_name`, the placeholder dash, the Health Connect/HealthKit product names) are `translatable="false"`, so lint's `MissingTranslation` checks everything else in both files. The Russian avoids plural forms by phrasing counts as "label: N" ("Прочитано тренировок: 5"), so the English strings' `%d` stay plain `<string>`s. `res/xml/locales_config.xml`, referenced as the manifest's `android:localeConfig`, puts HoldMyTrack in Android's per-app language list (minSdk 34, so it's the platform's own setting, with no AppCompat per-app-locale API needed). `build.gradle.kts`'s `androidResources.localeFilters` keeps only `en` and `ru` resources in the APK, so a phone set to a language the app doesn't have gets the English app, not English mixed with a library's own translations. Two pieces of code followed the strings: `recording/RecordingFormat` takes `Resources` and formats its units through `unit_km`/`unit_m`/`unit_kmh` in the device's locale, and `sync/SyncRunner` takes `Resources` for the refusal and stop reasons it reports (`sync_refusal_too_many_points`, `sync_request_failed`, `sync_no_report`). `HoldMyTrackApi`'s `LanguageInterceptor` sends `LocaleList.getDefault()` as `Accept-Language` on the API origin's requests, read per request, so the server's messages come back in the app's language. The account's Language setting is applied as the app's per-app language (§2.5).

## 9. Verification Methodology & Known Gaps

**Automated tests are few**: JUnit unit tests over the pure logic (`app/src/test`, §3.2), which CI runs on every push and pull request, uploading their JaCoCo coverage to Codecov (root `docs/DEVELOPMENT.md`, "CI"), and no instrumentation tests. Every behavior described in `apps/android/docs/SPEC.md` has instead been verified manually against a live `db`/`minio`/`api`/`worker` stack, with the specific steps and observed results recorded narratively in `apps/android/docs/ROADMAP.md` under each phase while it was open (a finished phase is removed from that file; `git log -p` on it still has the record) — for example, the layer-ordering/visibility logic in `map/MapOverlays` was verified by screenshotting all three map modes against a real account. FR-1 through FR-4 (`apps/android/docs/SPEC.md`) were verified this way on a physical device (a Pixel 10a running Android 17/API 37); FR-5's in-app recording (`apps/android/docs/SPEC.md` §7), and FR-3.6's file uploads, were instead verified on an emulator (a Pixel 7 AVD, Android 16) against the same kind of live stack — noted there specifically, since it's the one exception to this file's otherwise-consistent "physical device" claim.

This is a real gap relative to the server codebase, which the app inherits no test infrastructure from, and is worth naming rather than leaving implicit:

- **Regressions are only caught by re-running the manual verification steps**, which do not run automatically and are not gated in CI. A change to `SyncCandidates`, `SyncRunner` or `SyncTab` in particular should be re-verified against real Health Connect data in the scenarios a quick smoke test tends to skip: a run cut off midway, a `ConsentRequired` route, a reinstall (synced sessions mustn't come back), and an activity deleted on the web (its session must).
- **Verification has only ever run against one physical device and one Health Connect data provider (Fitbit).** The empirical Samsung Health check (`apps/android/docs/ROADMAP.md` Phase 1) remains unresolved for lack of a Galaxy Watch to test against — the current "Samsung is unsupported" conclusion rests on Samsung's own published documentation plus this app's design stance, not on a device-level measurement the way every other finding in this document is.
- **No test double exists for Health Connect.** `SyncCandidates.readHealthConnect` and `SyncRunner` are exercised only against a real `HealthConnectClient` on a real device; there is no fake or mock implementation of the client to run these classes against in isolation.
