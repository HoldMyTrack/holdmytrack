# ADR-0003: Precomputed raster fog pyramid, not per-request geometry union or H3

## Status

Accepted.

## Context

Fog of War needs to answer, for every map tile a user's browser requests, "how much of this area has this account ever covered." The original design computed that live: `ST_Union()` the user's covered geometry (buffered hexes) against the requested tile envelope, on every tile request. That is a union of potentially thousands of polygons, per user, per viewport, per pan — the first hard scaling wall the system would hit, and one that gets worse, not better, as exactly the users who use the product the most (the ones with the most history) load it the slowest.

A second original assumption — H3 hexagonal cells as the coverage unit — also didn't hold up once measured: H3 resolution 10 cells are roughly 130–150 m across, an order of magnitude coarser than the ~15 m originally assumed, and hexagonal cell edges are visibly serrated compared to a smooth reveal.

## Decision

**Coverage is precomputed on ingest, not assembled per request**, stored as a **raster bitmap pyramid**, not a set of vector cells (`IMPLEMENTATION.md` §4.2). For each z14 map tile a user's activity has touched, a 512×512 single-channel PNG is rendered once, at ingest time (~4.8 m/px at that zoom — finer than GPS accuracy) — every line segment of the raw trajectory is rasterized directly into the mask, not sampled point-by-point (see the "index raw points, simplify only for display" and "segment-rasterized coverage" decisions in `docs/ARCHITECTURE.md` §1.1, both load-bearing for this one). Lower zoom levels are generated by successive 2×2 downsampling from z14 rather than re-rendered from source. A new activity marks only the handful of z14 tiles it actually touches `dirty`; a worker re-renders just those and walks the pyramid upward — incremental cost stays near-constant regardless of how much history an account already has.

Slippy tiles were kept as the coverage grid (not H3), specifically because they align 1:1 with the same MVT/raster grid the rest of the tile-serving stack already uses.

## Alternatives considered

- **Per-request `ST_Union()` over vector geometry.** Rejected — the scaling wall this decision exists to avoid; cost grows with a user's own history, on every request, from every user simultaneously.
- **H3 hexagonal cells as the coverage unit.** Rejected once measured: real resolution (~130– 150 m at res 10) was far coarser than assumed, and hex edges read as visibly serrated next to a smooth reveal — a real render-quality regression for a product whose stated differentiator is render quality (`VISION.md` §1).
- **Point-sampled coverage** (mark cells at each recorded fix, not along the path between fixes). Rejected — 1 Hz at 40 km/h leaves ~11 m between fixes, which is gappy at the resolution the mask actually renders at; segment rasterization (stroking the line between consecutive points, not just the points themselves) closes those gaps.

## Consequences

- Reading the fog for any tile is now a single stored-PNG fetch (or, unfiltered, a cache hit) instead of a live geometry computation — the render-time cost this decision was built to avoid.
- The real cost moved to ingest and storage instead: every new activity requires a real rendering pass over the tiles it touches, and every touched tile's bitmap persists indefinitely (measured at a few KB per mostly-empty tile, megabytes per active user — `IMPLEMENTATION.md` §4.2's own "Volume" note).
- Filtering the fog by date range or hidden-activity set can't just read the precomputed aggregate anymore once that's a real requirement — this is what drove the later per-activity mask redesign (`IMPLEMENTATION.md` §4.2.3), a direct downstream consequence of choosing a precomputed aggregate in the first place.
- A raster mask can't be queried or reasoned about the way vector geometry could (e.g., "which specific activity covered this pixel" isn't answerable from the bitmap alone) — the per-activity mask redesign above is also what recovered that capability, by keeping the masks split per activity rather than merged into one aggregate per user.
